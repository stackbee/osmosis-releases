Rescued Data 列 — 壊れた値を捨てずに退避させる

取り込むデータがスキーマと合わなかったとき、その値は消えるのか残るのか。 Databricks は「捨てずに専用の列へ退避させる」を選んでいます。 サイレントなデータ損失を防ぐための仕組みです。

型が合わない行が来たとき素朴な設計はどちらも値を失う

取り込みでは、入力データがテーブルのスキーマと合わないことがあります。 素朴に考えると選択肢は2つ — 行ごと落とすか、その値を NULL にするか。 どちらも元の値が消えるという同じ問題を抱えています。

怖いのは「気づかないまま消える」こと

取り込みは成功したように見える。テーブルにも行が入っている。 でもある列だけが静かに NULL になっている。 あとから調べようにも、元の値がもうどこにも残っていません。

Databricks はこれを別の形で解きます。スキーマに合わなかった値を捨てず、 _rescued_data という専用の列へ退避させる。 使えるのは read_files()・spark.read・Auto Loader の3つで、 第2回で見た CTAS・COPY INTO・Auto Loader の経路がそのまま対応します。

具体例で追う2行のデータで挙動が全部わかる

生ファイルに users と cost の2列、2行のデータがあるとします。

users（期待する型: STRING）cost（期待する型: BIGINT）
Peter$100 ← 整数として読めない
zebi300

これを取り込むと、ブロンズテーブルはこうなります。

userscost_rescued_data
Peter null {"cost": "$100", "_file_path": "<file_path>"}
zebi 300 null

ここが要点

問題があった行だけ _rescued_data が埋まり、問題のない行は null。 だから取り込んだあとにこの列でフィルタすれば、型が合わなかった行だけを抜き出せます。 _file_path も一緒に入るので、どのファイルが原因かまで辿れます。

なぜこの設計なのかブロンズ層の考え方そのもの

従来のやり方だと、型が合わない値は消えます。しかも取り込み自体は成功として扱われるので誰も気づかない。 数か月後に集計が合わないと分かって原因を探すころには、元の値がもうありません。

_rescued_data があると話が変わります。値は残っている。どのファイルから来たかも記録されている。 だから取り込みのあとで検査して直せます。

順序が逆になっている

取り込む前にすべての型を完璧に揃えるのではなく、まず取り込んで、合わなかったものを後から見る。 ブロンズ層の考え方そのものです。ブロンズはまず全部受け止める層で、整えるのはシルバー層の仕事。

運用の勘所
_rescued_data が null でない行を定期的に数える。ゼロなら健全、増えていたらソース側で何かが変わったサイン。

まとめ4行
  • スキーマに合わなかった値は捨てられず、_rescued_data にJSON 形式の文字列として入る。
  • 使えるのは read_files()・spark.read・Auto Loader。
  • スキーマに合う値は普通に取り込まれ、その行の _rescued_data は null。
  • サイレントなデータ損失を防ぎ、取り込んだあとに不一致を調べて対処できる。
