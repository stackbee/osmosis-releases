エンタープライズデータの取り込み — マネージドコネクタの2つの形

ここまでは「置かれたファイルを拾う」話でした。今回は「接続して取りにいく」話です。 Managed Connectors のアーキテクチャは SaaS とデータベースで形が変わりますが、 その差はすべて相手が公開されているかどうかの一点から出ています。

ファイルにならないソース自作するとソースの数だけ実装が増える

Salesforce、Workday、PostgreSQL、SQL Server。こうしたソースはファイルをどこかに置いてくれません。 API を叩くか、データベースに接続するかしないとデータが手に入らない。

自作すると何が起きるか

認証の方式がソースごとに違う。増分の取り方も違う。エラーの出方も違う。 ソースの数だけ、別々の実装を抱えることになります。

これを引き受けるのが Lakeflow Connect の Managed Connectors です。 Databricks に組み込まれた、ローコードでフルマネージドの仕組みで、 手作業の設定や独自の連携コードがほとんど要りません。

使う前に確認すること

Managed Connectors はソースごとにリリース状態が違います。 Public Preview のものも GA のものもある。動きが速い領域なので、 使う前に公式ドキュメントで確認してください。

SaaS の取り込み — 素直な形サーバーレスが直接取りにいく3段

この経路は マネージド取り込みパイプラインという専用のパイプライン型で動きます。 ソースごとの細かい事情はあらかじめ定義され、Databricks が面倒を見ます。

データがどこを通るか

データの移動はすべてデータプレーンで起きます。 コントロールプレーンが使われるのは、パイプラインのセットアップ・監視（イベントログの読み取り）・管理だけ。 データそのものはコントロールプレーンを通りません。

なぜゲートウェイを挟むのか段を増やすだけの理由が2つある

段を増やすのはコストです。それでも挟むのは、理由が2つあるからです。

理由1 — ネットワーク

企業のデータベースはファイアウォールの内側にいたり、インターネットから到達できなかったりします。 SaaS のように「公開されているから接続すればいい」とはいかない。 Private Link のような選択肢がない場合、ゲートウェイを顧客のネットワークの内側に配置できます。 外から届かないなら、内側に置く。

理由2 — データベースへの負荷

ソースへの直接接続の数は少ないほうがいい。ゲートウェイをパイプラインから切り離しておくと、 1つのゲートウェイがデータベースと話し、そこから複数のパイプラインへ分配できます。 データベースから見た接続は1本のまま、下流は好きなだけ増やせる。

2つのアーキテクチャの差は一点から出ている

相手が公開されているかどうか。 公開されていればサーバーレスで直接いける。公開されていないなら、内側に置けるゲートウェイを挟む。 段数の違いも、クラシックコンピュートを使う理由も、すべてここから導けます。

ネイティブコネクタが無いときPartner Connect

使いたいソースに Managed Connector が無い場合は Partner Connect です。 Databricks のテクノロジーパートナーの試用アカウントを作り、ワークスペースをパートナー製品につなげられます。 しかも Databricks の画面から直接できる。レイクハウスにあるデータで試し、業務に合うものを採用する流れです。

パートナーのコネクタは幅が広く、機能も深い。専任のエンジニアチームが保守しています。 ネイティブのコネクタがあるソースでも、パートナー製を選び続けられます。 Databricks はその選択肢を残す方針だと明言しています。
