クラウドストレージからの取り込み — CTAS・COPY INTO・Auto Loader

クラウドストレージに置かれた生ファイルを Delta テーブルに変える道具は3つあります。 違いは「前回どこまで読んだかを覚えているか」と「どこまで規模が伸びるか」の2点に集約されます。 この回はその2点だけで3つを振り分けられる状態を目指します。

CTAS の適域
一度きり

冪等でない。毎回すべて読み直す

COPY INTO の適域
数千

ファイル数。冪等

Auto Loader の適域
数百万〜

数十億まで。冪等

生ファイルを Delta テーブルに変えるこの回の目的は1つだけ

出発点はクラウドオブジェクトストレージに置かれたファイルです。形式は CSV・JSON・Parquet など。 柔軟で扱いやすいぶん、生ファイルのままでは ACID トランザクションも、タイムトラベルも、 スキーマの強制も効きません。だから Delta テーブルに変換します。

経路は Lakeflow Connect の Standard Connectors です（前回 §コネクタの3分類）。

CTAS — まとめて一度だけ読むバッチ。冪等ではない

CREATE TABLE AS (CTAS)構文

CREATE TABLE new_table AS
SELECT * FROM read_files(
  '<path_to_files>',
  format => '<file_type>',
  <other_format_specific_options>
);

要は read_files() です。指定した場所の下にあるファイルを読み、表の形にして返します。 読める形式は JSON・CSV・XML・TEXT・BINARYFILE・Parquet・Avro・ORC。 形式を自動判別し、複数ファイルにまたがって共通のスキーマを推論することもできます。

CTAS は冪等ではない

動かすたびに対象のファイルを全部読み直します。前回どこまで読んだかを覚えていません。 定期実行に載せることはできますが、その場合も毎回すべてを読み直すことになります。 向いているのは一度きりの取り込みと、小さめのデータセットです。

COPY INTO — 読んだファイルを覚えている増分バッチ。冪等で再試行できる

COPY INTO構文

CREATE TABLE new_table;

COPY INTO new_table
FROM '<dir_path>'
FILEFORMAT = <file_type>
FORMAT_OPTIONS (<options>)   -- ファイル側: どう解釈するか
COPY_OPTIONS   (<options>)   -- コマンド側: どう振る舞うか

いちばん大事な性質が冪等性です。COPY INTO はすでに読み込んだファイルを記録しています。 二度目以降は記録にあるファイルを飛ばし、新しいファイルだけを取り込む。 だから同じコマンドを何度流してもデータが重複しません。 継続的にファイルが追加される場所に向いています。

オプションは2系統ある

系統何を決めるか代表的な指定
FORMAT_OPTIONS ファイル側。ソースのファイルをどう解釈するか ファイル形式ごとに異なる
COPY_OPTIONS コマンド側。COPY INTO 自身がどう振る舞うか mergeSchema（新しい列を足して取り込む）
force（読み済みの記録を無視して全部読み直す）

混ざらない覚え方

FORMAT はファイル側、COPY はコマンド側。 なお force は冪等性を外すためのスイッチです。そう位置づけておくと 「通常は使わないもの」だと分かります。

Auto Loader — 億のファイルまで伸びる増分バッチにもストリーミングにもなる

実体は Spark Structured Streaming です。Python でも SQL でも書けます。

Auto Loader — Python構文

(spark.readStream
  .format("cloudFiles")                                  # これが Auto Loader を有効にする合図
  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", "<checkpoint_path>")
  .load("/Volumes/catalog/schema/files")
 .writeStream
  .option("checkpointLocation", "<checkpoint_path>")
  .trigger(processingTime="5 seconds")
  .toTable("catalog.database.table"))

Auto Loader — SQL（宣言的パイプライン）構文

CREATE OR REFRESH STREAMING TABLE catalog.schema.table
SCHEDULE EVERY 1 HOUR
AS SELECT * FROM STREAM read_files(
  '<dir_path>', format => '<file_type>'
);

強みは規模です。新しく届いたファイルを自動で検出し、スキーマの変化にも自分で追随します （新しい列が現れたら扱えるように進化させる）。数十億のファイルまで伸びます。 そのぶん、スキーマの置き場所とチェックポイントが必ず要るのが前の2つとの違いです。

3つをどう選ぶか規模で決まる。冪等性が第2の軸

公式ドキュメントが示している閾値

数千ファイルまでは COPY INTO で足りるが、数百万を超えるなら Auto Loader。 理由は Auto Loader のほうがファイルを見つけるための操作数が少なく、 規模が大きいほど安く速いから。逆に、特定のファイルだけを選んで入れ直したいときは COPY INTO のほうが扱いやすい、とも書かれています。

取り込みの途中で形の壊れたレコードに出くわしたとき、それを捨てずに退避させる仕組みが rescued data column です。この回では名前だけ。中身は第4回で扱います。
