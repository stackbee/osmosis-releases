統合テストの実行 — Expectations で書くか、Jobs のタスクで書くか

ピラミッドの土台から真ん中へ上がります。実行方法は2つありますが、 どちらも新しい道具ではありません — 既にある道具を検証の目的に向け直すだけです。

道具が2つあり、どちらも既習新しい機能を覚える回ではない
方法どこで学んだかやること
SDP の Expectations コース3（品質の検査） パイプラインの中のテーブルの結果を検証する
Lakeflow Jobs のタスク コース2（タスクと依存） 検証用のノートブックをタスクとして足す

この回の性格

統合テストは新しい機能を覚えることではなく、既にある道具を検証の目的に向け直すことです。 素材も「テスト自体は似ているが、実行するのに違う道具を使っている。 必要に一番合うほうを選べばよい」と書いています。

方法1 — Expectations で検証する共通のパイプラインを、環境ごとに検証する

要点

対象の環境がどれであっても、実行されるパイプラインは同じものです。 変換のロジックも自作関数も3環境で共通。違うのは 設定変数で決まる読み先のカタログだけです。

素材が挙げる検証例は行数を数えることと新しい列の異なる値を検証すること。 ただし素材自身が「これは説明のための単純なもので、 通常はもっと的を絞ったテストを作る」と断っています。

方法2 — Jobs のタスクとして書くテストが関門になる並び

書ける統合テストの例（素材より6つ）

  • 行数を数える
  • テーブルが正しく作られたか確かめる
  • 指定した列を含んでいるか
  • 異なる値が正しいか
  • 列の値が特定の範囲に収まっているか
  • 重複がないか

対象の環境（dev / stage / prod）に応じた正しいパラメータの設定が必要です。

どちらを選ぶかテストをどこに置きたいか
ExpectationsJobs のタスク
テストの置き場所パイプラインの定義の中独立したノートブック
利点パイプラインとテストが1か所にまとまる。実行も1回好きな検証を書ける。パイプライン以外も確かめられる
制約Expectations が表現できる範囲に収まるジョブの構成が長くなり、パラメータの設定も要る

判断の軸

さきほどの6つの検証はどちらの方法でも書けます。 決め手はテストをどこに置きたいか — パイプラインと一体にしたいなら方法1、分離して自由に書きたいなら方法2。

これでピラミッドの土台と真ん中が埋まりました。 残る頂点のシステムテストは端から端までのパイプラインをジョブの中で走らせることで、 方法2の4段目が実質それにあたります。
