条件分岐と繰り返し — Run-if・If/Else・For Each

ここまでのワークフローは決まった順に流れる一本道でした。 この回から、実行時の状況を見て枝を選び、繰り返す形になります。 3つの道具は何を材料に判断するかが違うので、そこを混ぜないのが要点です。

3つの道具、判断の材料が違う混ぜると選べなくなる

Run-if — 条件は6つある3つしか挙げていない資料は不完全

補完 — 公式には6つ載っています

3つ（All succeeded / At least one succeeded / None failed）だけを挙げている資料がありますが、 選べる条件は全部で6つです。そして足りない3つが全部エラー処理向けなので、 知らないと「失敗したときの枝」が作れません。

群条件意味
成功側All succeededすべての依存が実行され成功した。既定値
At least one succeeded少なくとも1つが成功した
None failedどれも失敗しておらず、かつ少なくとも1つが実行された
結果を問わないAll doneすべて実行されたあと、結果に関係なく動く。後片づけ向け
失敗側At least one failed少なくとも1つが失敗した。エラー時だけの枝
All failedすべてが失敗した

連鎖的な失敗を防げる

Task-4 が Task-2 と Task-3 に依存し、条件が At least one succeeded なら、 Task-3 が失敗しても Task-2 が成功していれば Task-4 は動きます。 現実の業務では成功への経路が複数あることが多いので、一部の失敗で全体を止めない設計ができます。

除外は連鎖するRun-if の条件が何であっても効かない場合がある

公式が明記している規則

あるタスクの依存がすべて除外された場合、そのタスク自身も除外されます。 Run if の条件が何であっても、です。

これは効きます。All done を設定して「必ず走る」つもりでいても、 上流が全部除外されていたら走りません。 Run-if の条件は、上流が実行された上でどうだったかを見るものであって、 上流が存在しないところには効かない。そして除外は下流へ波及します。

If/Else — 値で分けるタスク値と組み合わせて効く

使える演算子は6つ — == != > >= < <=。 比較の対象はタスクの結果、パラメータの値、計算した指標です。

前々回のタスク値とつながる

上流で数えた件数を dbutils.jobs.taskValues.set で残しておけば、 それをここで判定できます。これが「実行してみないと分からない値で分岐する」の実装です。

データ品質のゲート
レコード件数・欠損の割合・検証結果で分ける
処理量による判断
大きいデータセットと小さいもので戦略を変える
環境ごとの処理
パラメータを見て開発と本番で違うタスクを動かす
業務ルールの実装
複雑なルールをワークフローの中に直接置く

評価されるのは依存がどれも失敗しておらず、かつ少なくとも1つが実行されたとき。 意味のある上流の結果が揃ってはじめて判定する設計です。 真の枝と偽の枝には、それぞれ複数のタスクを置けます。

For Each — 繰り返し下流は入れ子ではなく容器に依存する

入力の配列を受け取り、要素ごとに同じ入れ子のタスクを回します。 要素は {{ input }} として渡されます。構成する部品は2つです。

For Each タスク
繰り返しを管理する外側の容器。同時実行数と入力配列を扱う。
入れ子のタスク
実際に働く中身。どんなタスク型でもよい（ノートブック / SQL / Python …）。

いちばんの注意点

下流の依存は、入れ子のタスクではなく For Each という容器に付きます。 個々の繰り返しに依存を張るのではありません。 すべての繰り返しが終わってから下流が動きます。

使いどころは、地域ごと・期間ごと・顧客セグメントごとの処理、複数ファイルの処理。 同じロジックを違う切り口に当てるときです。
