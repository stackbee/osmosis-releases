失敗からの復旧と性能の監視 — Repair run と system.lakeflow

実際に失敗したジョブをどう立て直すか。そして動いているジョブの性能をどう見るか。 監視の道具は2つあり、横に広く見るものと縦に深く掘るもので役割が分かれます。

失敗したところだけやり直すRepair run

ジョブの途中でタスクが1つ失敗したとき、素朴にやるとジョブ全体を流し直すことになります。 成功していたタスクまで動き直す。Repair 機能はここを変え、失敗したタスクだけを再実行できます。

場面Repair で直すもの
設定の修正値が間違っていて失敗したパラメータ
リソースの調整メモリや計算資源が足りず落ちたもの
コードの修正ロジックの誤りを直し、影響のあったタスクだけ流し直す
データ品質への対応実行して初めて分かった問題に処理を合わせる

操作は、失敗したタスクをクリックして実行の詳細を開き、Repair run を押すだけです。

リペアはジョブを直さないこの回いちばんの落とし穴

タスクを直すことは、ジョブを直すことではない

間違ったパラメータを渡してタスクが失敗した。Repair 実行で上書きして無事に通った。 解決したように見えます。しかしジョブの定義は元のままです。 次にそのジョブが動くと、また同じ間違ったパラメータで走ります。

Repair はその実行に対する応急処置であって、定義への修正ではありません。 通したあとに必ずジョブ側の編集をしてください。 忘れると、同じ失敗が定期実行のたびに再発します。

システムテーブルで全体を見るsystem.lakeflow — 傾向を見る道具

system.lakeflow は組み込みの読み取り専用カタログで、 そのリージョンの全ワークスペースにわたるジョブの活動を記録しています。 1つのジョブではなく、全体を横断して見る道具です。

テーブル中身
jobsジョブの基本情報
job_tasksタスクの定義
job_run_timelineジョブの実行の履歴
job_task_run_timelineタスクごとの実行の履歴
pipelinesパイプラインの基本情報

timeline が付くテーブルの特徴

長い実行を1時間ごとに切り分けて記録します （period_start_time / period_end_time）。 何時間も走るジョブは開始と終了の2点だけでは扱いにくい。 時間ごとに切ってあると、所要時間の分析・同時実行数の把握・合意水準の計測が正確にできます。

Spark UI で1本を掘る時間の内訳が読めると次の手が決まる

まずタイムライン。タスクがいつ始まっていつ終わったか、どれとどれが重なっていたかが出ます。 個別のタスクをクリックすると、状態・時刻・所要時間・クラスターとランタイム・ログ・入出力の概要が見られます。

クエリやコードの詳細を開くと、実際の時間の内訳が出ます — 最適化と枝刈りに使った時間と、実行そのものに使った時間が分かれます。 読み書きしたファイル、パーティション、そしてスピル（メモリに乗り切らずディスクへ書き出した量）も見られます。

見えたもの意味次の手
計画の時間が長い 読む必要のないデータを、読む前に切り落とせていない 枝刈り・パーティション分割の改善
実行の時間が長い 処理そのものが重い 結合・集計の最適化（ブロードキャスト、データの偏りへの対処）
