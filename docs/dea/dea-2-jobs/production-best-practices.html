本番運用のベストプラクティス — コンピュート・料金・モジュール設計

開発で動いたものを本番に載せるとき、何を見るか。 料金の判断では請求書に出てこない費用が効いてきます。 最後に、守るべき具体的な数字を4つ押さえます。

1ジョブのタスク上限
1,000

超えるならモジュール分割

同時実行数の既定
1

明示的に上げる必要がある

ワークスペースの上限
2,000

同時タスク実行。超過は 429

本番へ移すとき見るのは4つ確認する領域
コンピュート
性能・費用・運用の要件に合ったものを選ぶ。
モジュール設計
保守しやすく、再利用でき、チームで協業できる形にする。
Git
バージョン管理とデプロイの手順を整え、一貫性を保ち CI/CD を可能にする。
性能の監視
先回りして監視し、合意した水準と費用効率を守る。

コンピュートは3つ、答えは2つ本番の視点で見直す
本番で使えるか理由 / 代償
Interactive Cluster 使わない 実行していない間も動き続けて費用がかかる / 共有ゆえ取り合いが起きて性能が読めない / 衝突でジョブが遅れる
Job Cluster 使える 終了で停止するので遊休費用が消える。専用リソースで性能が読める
代償：起動の遅延（SLA に織り込む）／ 設定と管理の手間
Serverless 多くの本番に最適 VM の種類を選ばなくてよい / Photon が既定で有効 / 起動が速い / クラウド障害から遮蔽

Serverless の起動が速いのは、VM が Databricks 側のアカウントで動いていて、 過去のデータと機械学習にもとづいて十分なノードが用意されているためです。

見えていない費用がある単価だけ比べると判断を誤る

判断の置き方

運用の手間を勘定に入れると総所有コストは下がることが多い。 とくに専任のプラットフォームエンジニアリングチームを持たない組織では、その差が大きくなります。

モジュール設計と Git切り方は技術ではなく業務の単位で

分け方の指針

技術的な単位ではなく、業務の論理的な単位で切る。 それぞれのモジュールが、独立して開発・テスト・デプロイできる まとまった業務機能を表すようにします。実装は親子 — 親のジョブが子のジョブを呼ぶ （前回の Run Job タスク）。

得られるもの中身
保守しやすさ小さいジョブのほうが理解も修正も原因究明も楽
再利用子のジョブを複数の親から使える
チームの協業チームごとに別のモジュールを持ちながら全体では協力できる
テスト個々のモジュールを独立して試せる。デプロイの危険が減る

Git 連携

ジョブが Git からノートブックを実行できる、という形です。

意図しない変更を防ぐ
誰かが本番リポジトリでローカル編集やブランチ切り替えをしても、本番ジョブは影響を受けない。
拠り所が1つ
どの版が本番で動いているのか迷わなくなる。
CI/CD が組める
デプロイの前に自動で検証できる。
対応する提供元
GitHub / GitLab / AWS CodeCommit ほか。

守るべき数字ベストプラクティスと具体的な制限
領域やること
費用 本番では Job Cluster か Serverless / インタラクティブを本番で使わない / Photon を有効にする（速く、そして安い）/ クラスターをタスク間で再利用する
設計 複雑なパイプラインをモジュールに分ける / マルチタスクジョブで並列化 / Run If・If/Else・For Each で条件を扱う / 1ジョブ 1,000 タスクまで
運用 サービスプリンシパルをジョブ所有者とデータアクセスに使う（個人アカウントではなく）/ 失敗・遅延・完了にアラート / Repair & Run で再処理費用を減らす / タスクをパラメータ化

補完 — 公式にある制限3つ

1. 同時実行数の既定値は 1。並行して走らせたいなら詳細設定で明示的に上げる。
2. ワークスペース全体では 2,000 の同時タスク実行が上限。 超えると、すぐ開始できない実行に 429 Too Many Requests が返る。
3. パイプラインタスクを含むジョブは、同時実行数を 1 より大きくしても 1 に制限される。 パイプラインタスクは並行して走りません。

  • ★ Configure and edit Lakeflow Jobs — 同時実行数の既定と上限
  • Jobs with a large number of tasks
