まず測る「遅い」は単独の数字では判断できない

ガイドのキーワードは compare current execution times against historical baselines。過去との比較です。

「今日は40分かかった」——これは遅いでしょうか。答えられません。 普段が10分なら異常、38分なら誤差です。単独の数字では判断できません。 当たり前に見えますが、実務ではここが飛ばされます。「なんか重い」「遅い気がする」という 感覚から対応が始まってしまう。run history があれば 「過去30日の平均は12分。今日は40分」と言えます。しかもいつから変わったかまで分かります。

ここは変換とモデリングで出てきた measure → 手を打つ → re-measure の、最初の measure にあたります。 測らずに手を打つ選択肢は、この試験では誤答です。 「遅いのでクラスタを大きくした」は測っていません。 「run history を見たら、ある日から急に伸びていた」は測っています。

run history 画面で見るもの

実行ごとに、開始時刻・所要時間・ステータスが一覧で並びます。失敗した実行は色分けされ、 各実行を開けばタスク単位まで展開できます。ここでのコツは1つです。

見るべきは1本の実行ではなく、並んだ実行の傾向です。 グラフで言えば、点ではなく線を見る。どこで折れ線が跳ねたか。それが原因を探す起点になります。

run history の傾向から読めること

履歴の形疑うこと
ある日を境に急に伸びたその日のデプロイ・設定変更・上流の変化
少しずつ伸び続けているデータ量の増加／小さなファイルの蓄積
日によって大きくばらつく他ジョブとのリソース競合／入力データ量の変動
特定の曜日だけ遅い週次バッチと実行時間帯が重なっている
失敗が断続的に起きる一時的な障害 → retry の設定
毎回失敗するretry は無意味。コード・権限・スキーマを疑う

急に伸びた → 変更を疑う。じわじわ伸びた → 蓄積を疑う。 この切り分けが、対処の方向を決めます。

2行目の「じわじわ」に理由があります。データを書き込むたびに新しいファイルが作られ、 ファイル数が少しずつ増えていきます。読むときに開くファイルの数が増えるので、少しずつ遅くなる。 これが小さなファイル問題の典型的な現れ方です。

DAG で震源地を探す

ガイドは viewing DAG-based task graphs to spot upstream blockers と書いています。

タスクが A → B → D、C → D と依存しているジョブを考えます。 A は実行中で45分経過、B は待機中、C は3分で完了、D は待機中。 上がってくる報告は「ジョブ全体が終わりません」「D がずっと待機のままです」です。

ここで D を調べても、何も出てきません。D は待っているだけで、エラーもログもありません。 詰まっているのは A です。A が終わらないから B が始まらず、D も始まらない。 症状が出ている場所と、原因の場所は違います。 DAG を見る目的は、詰まりの震源地を特定することです。

Jobs で見た DAG と同じ画面ですが、目的が違います。 設計時は「構造」——どういうタスクがあってどう依存しているか。 運用時は「状態」——いまどこまで進んで、どこで止まっているか。 同じ画面を2つの目的で読み分けます。

ステータス別・次に見る場所

ステータス意味次に見るもの
Failedエラーで停止したログとエラーメッセージ
Running（長時間）進んではいるが遅いSpark UI
Pending / Queuedまだ始まっていない上流タスク／コンピュートに空きがあるか
Skipped条件で飛ばされた依存条件（Run if）
Timed out上限時間を超えた遅い原因を追うので Spark UI

落ちたのか、遅いのか

この2つは見る場所が違います。落ちたならログ——エラーメッセージから原因が辿れます。 遅いなら Spark UI——エラーは出ていないので、ログを見ても何も書いてありません。 「遅いのでログを見たが、何も出ていない」は当然です。エラーではないからです。 ここを取り違えると、調査が空回りします。

失敗も「単独の事象」では判断できない

ガイドの3つ目のキーワードが failure rates、失敗率です。 30回に1回程度なら一時的な障害の可能性が高く、 retry が効きます。100%失敗しているなら retry は無意味です。 3回リトライしても3回失敗するだけで、疑うべきはコード・権限・スキーマです。

そして重要なのは、1回の失敗だけでは、たまたまなのか毎回なのかが分からないことです。 失敗率という「複数回の集計」を見て、初めて判断できます。 「遅い」も「失敗する」も、単独では判断できない。このドメインは一貫してこの考え方です。

症状から入る診断フロー入口は3つしかない——遅い / 落ちる / 容量が増える

このドメインは道具の数が多く、機能名から覚えると混ざります。 実務でも試験でも、入ってくるのは症状です。 そこで、症状から辿れる形に組み替えておきます。入口は3つです。

このフローを使う理由

症状を見た瞬間に原因を当てにいくと、「遅い → クラスタを大きくする」に吸い込まれます。 これはこの試験で最も頻繁に出てくる誤答です。 上から順に絞り込めば、増強が答えになる枝が1本も無いことが分かります。 ガイドの動詞が diagnose（診断する）であって fix でないのは、そういう意味です。

Spark UI の Stages タブからステージの詳細を開くと、 Summary Metrics という表があります。ここに、そのステージのタスクの分布が並びます。

読む順序と、それぞれの閾値感

順序は ① Max と Median の差（skew）→ ② Shuffle のサイズ → ③ Spill の有無。 この順に見れば、名指しされた3つを一通り確認できます。目安はこう持っておきます。

分布の形が効きます。なだらかに伸びているなら全タスクが等しく重い—— データ量やリソースの問題です。Max だけ跳ねているなら一部のタスクだけ重い——skew です。 同じ「遅い」でも、打つ手が変わります。

① data skew — 偏り

同じステージのタスクなのに、1つだけ極端に遅い状態です。 タスク1が2秒、タスク2が2秒、タスク3が2秒、タスク4だけ18分。 このステージ全体は18分かかったことになります。タスク4が終わるまで次に進めないからです。

原因は、特定のキーにデータが集中していることです。よくあるのは2つ。 NULL や既定値が大量にある——たとえば customer_id が未入力のレコードが すべて NULL になっていて、それが1つのパーティションに集まる。 もう1つは巨大な1件が混じっている——売上の9割を占める取引先がいれば、 その1社ぶんだけで巨大なパーティションになります。

なぜ skew はノードを増やしても直らないのか

問題は「1つのタスクが重いこと」であって、並列度ではないからです。 ノードを10台に増やしても、そのタスクを処理するのは1台です。その1台が18分かかることに変わりはありません。 「遅いのでクラスタを大きくした。でも変わらなかった」は skew の典型的な症状です。

② shuffling — データの移動

groupBy・join・distinct を実行するとき、 同じキーのデータを同じノードに集める必要があります。そのための通信がシャッフルです。 打てる手は3つ——broadcast join で回避する、 autoBroadcastJoinThreshold を調整する、shuffle.partitions を調整する。

変換とモデリングでは、これらを 「こういう手法があります」として学びました。いつ使うのかが決まるのが、ここです。 broadcast join を使う判断は、Spark UI で Shuffle のサイズを見て決めます。 知識と使いどころが結びつく場所です。

③ disk spilling — ディスクへの溢れ

メモリに乗り切らず、ディスクに書き出しながら処理している状態です。 ディスクへの読み書きはメモリに比べて圧倒的に遅いので、これが起きると処理が大幅に遅くなります。 打てる手は3つ——shuffle.partitions を増やして1タスクの担当量を減らす、 メモリの大きいノードにする、そしてそもそも skew を直す。

3つ目が大事です。skew があると1つのタスクに大量のデータが集まり、だから溢れます。 skew と spill は同時に起きることがあります。 Spill だけ見て shuffle.partitions を増やしても、 偏りが原因なら効きが悪い、ということが起こります。

症状 → 原因 → 手

Spark UI で見えるもの原因打つ手
Max だけ桁違いに長いdata skewキーの偏りを解消
Shuffle Read/Write が巨大shufflingbroadcast join / 閾値調整
Spill (Disk) に数字が出るメモリ不足shuffle.partitions を増やす
タスク数が異常に多く各々短いパーティション過多shuffle.partitions を減らす
読むファイル数が異常に多い小さなファイル問題OPTIMIZE / Liquid Clustering

どの行も「クラスタを大きくする」が答えになっていません。1行もありません。 原因ごとに打つ手が違い、原因を特定せずに増強するのは常に誤答—— これがこの試験の一貫した姿勢です。

小さなファイル問題の全体像なぜ起きる → どう気づく → どう直す → どう防ぐ

このドメインの半分は、突き詰めるとファイルの置き方の話です。 その中心にあるのが小さなファイル問題（スモールファイル問題）で、 OPTIMIZE も Liquid Clustering も Predictive Optimization も、ここに接続しています。 4段階で通して見ておきます。

① なぜ起きるのか

Databricks では、データを書き込むたびに Parquet ファイルが作られます。 書き込みの回数だけファイルが増える、という単純な仕組みです。 そのため、書き込みが細かく・頻繁になるほど、小さなファイルが溜まります。

溜まり方起きる場面
頻繁な追記短い間隔のマイクロバッチ／ストリーミング取り込み
更新の繰り返しMERGE・UPDATE・DELETE。書き換えのたびに新しいファイルが書かれる
分割しすぎshuffle.partitions が大きく、1タスクあたりの出力が小さい
パーティションの切りすぎ高カーディナリティの列で PARTITIONED BY。ディレクトリの数だけ小さなファイルができる

② どう気づくのか

症状は地味です。壊れないので、気づかないまま進行します。

  • run history がじわじわ伸びる——急な跳ねではなく、緩い右肩上がり
  • Spark UI で読むファイル数が異常に多い
  • タスク数が多く、それぞれが短い——処理より段取りに時間を使っている状態
  • データ量はさほど増えていないのに、読み取りだけが重くなっている

1000個の小さなファイルを開くより、10個の適切なサイズのファイルを開くほうが圧倒的に速い。 ファイルを開く操作には、1つずつオーバーヘッドがあるからです。

③ どう直すのか — OPTIMIZE

OPTIMIZE prod.silver.orders;
-- 小さなファイルを読み直して、適切なサイズのファイルに再構成する
-- CLUSTER BY を指定したテーブルなら、同時にクラスタリングも実行される

コマンドは1行です。実行すると何が変わるかを整理しておきます。

項目OPTIMIZE 実行後
ファイル数減る。小さなファイルがまとめられる
行数・データの中身変わらない。行は1行も減らない
読み取り性能開くファイル数が減るので速くなる
ストレージ使用量一時的にむしろ増える。新しいファイルを書き、古いファイルは VACUUM するまで残る
テーブル履歴新しいバージョンが記録される。Time Travel は引き続き使える

OPTIMIZE は削除しない

目的はファイルをまとめて読み取り効率を上げることであって、消すことではありません。 「ストレージを減らしたい → OPTIMIZE」は誤答です。 減るどころか、旧ファイルが残るぶん一時的には増えます。ここが VACUUM との決定的な違いです。

実行コストも意識してください。 OPTIMIZE はテーブルを読み直して書き直す処理なので、そのぶんコンピュートを消費します。 月に1回しか更新されないテーブルに毎晩流しても、改善は起きず費用だけがかかります。 「全テーブルに一律で OPTIMIZE」は、改善の対象になる運用だと覚えておいてください。 その答えが Predictive Optimization です。

④ どう防ぐのか

打ち手効き方
Liquid Clusteringファイルサイズの管理も込みで面倒を見るため、そもそも起きにくい
高カーディナリティ列でパーティションを切らない発生源そのものを絶つ。日付程度の粒度に留める
Predictive Optimization断片化したテーブルを検出して、必要なものだけ自動で OPTIMIZE
書き込み間隔の見直し取り込み側の設計。細かすぎる追記は、そのままファイル数になる

「じわじわ遅い」の答えがここにあります。 run history の傾向で緩い右肩上がりを見つけたら、 まず小さなファイルの蓄積を疑ってください。 データ量の増加と違って、これは掃除すれば直ります。

Liquid Clustering新ガイドが名指しした、レイアウト最適化の主役

目的は Data Skipping を効かせること

WHERE customer_id = 10001 というクエリを考えます。 テーブルに1000個のファイルがあるとして、データが散らばっていれば、 どのファイルに 10001 が入っているか分からないので1000個すべてを開いて確認します。 値が近いデータが同じファイルに寄っていれば、1個だけ開けば済みます。

これを可能にしているのが Data Skipping です。仕組みは統計情報です。 Delta は各ファイルについて、列の最小値と最大値を記録しています。

ファイルの統計（min / max）customer_id = 10001 のとき
10000 〜 10500範囲に含まれる → 読む
50000 〜 50500含まれない → 読み飛ばす
1 〜 999999
（データが散らばっている）		含まれるかもしれない → 読むしかない

3行目が問題です。データが散らばっていると、どのファイルも 「10001 が含まれるかもしれない」範囲になり、1つも読み飛ばせません。 統計情報はあるのに、効かない状態です。 データの置き方が、そのまま読み取り性能に効きます。 その置き方を最適化するのが Liquid Clustering です。

書き方

CREATE TABLE prod.silver.orders (
  order_id BIGINT, customer_id BIGINT, order_date DATE, amount DOUBLE
)
CLUSTER BY (customer_id, order_date);      -- 作成時に指定（複数列を指定できる）

ALTER TABLE prod.silver.orders CLUSTER BY (customer_id);   -- 後から変更できる
ALTER TABLE prod.silver.orders CLUSTER BY AUTO;            -- 列選びを Databricks に任せる

OPTIMIZE prod.silver.orders;               -- クラスタリングを実行する

いちばん大きいのはキーを後から変更できることです。 パーティションは一度決めると変えられず、変えるにはテーブルを作り直す必要がありました。 つまり最初に正しく選ばなければならない仕組みだった。 しかし最初の時点では、どのクエリがよく実行されるか分かりません。 「この列で絞ることが多い」と分かるのは、運用が始まってからです。 Liquid Clustering なら、そのときに ALTER で変えられます。

パーティションの弱点

customer_id でパーティションを切ると、顧客が100万人いれば100万個のディレクトリができ、 それぞれに小さなファイルが入ります。これが小さなファイル問題です。 日付なら1年で365個——適度な数です。 日付で切るのは良くても、高カーディナリティの列で切ると破綻します。

つまりパーティションは「切る列を正しく選ぶ」ことが前提の仕組みでした。 Liquid Clustering は、その選択自体を不要にします。 カーディナリティを気にせず、絞り込みに使う列を指定すればいい。ここが大きな進歩です。

パーティションと併用できるのか

できません。Liquid Clustering はパーティションや ZORDER BY を置き換える機能であって、 その上に重ねる機能ではありません。CLUSTER BY を使うテーブルでは PARTITIONED BY を指定しませんし、ZORDER BY も併用しません。 「パーティションを残したまま Liquid Clustering も有効にする」という選択肢が出たら、 そこが誤りです。

何をキーにするか

良いキーは WHERE でよく使う列 / JOIN のキー / MERGE のキー—— 共通しているのは絞り込みに使われる列だという点です。 逆に、絞り込みに使わない列を指定しても意味がありません。

迷うなら CLUSTER BY AUTO です。列を自分で選ばず、 クエリ履歴から「どの列でよく絞り込まれているか」を Databricks が判断します。 選定の判断自体を任せる形で、人が決めることを減らしていくという Databricks 全体の方向性とも一致しています。

MERGE が遅い問題の答えがこれです。 MERGE は ON の条件で target を探すため、そのキーでクラスタリングすれば探索範囲が減ります。 「クラスタを大きくする」でも「VACUUM する」でもありません。

Predictive Optimizationメンテナンスを自分で回すのをやめる

自前で回すと、夜間バッチに「全テーブルへ OPTIMIZE」「全テーブルへ VACUUM」 「ANALYZE で統計更新」を並べることになります。これで動きはします。 ただし「いつ、どのテーブルに必要か」を人が決めている状態です。

毎日更新されるテーブルと月1のテーブルに、同じ頻度の OPTIMIZE は要りません。 月1のテーブルに毎晩流しても、改善は起きずコンピュート費用だけがかかります。 しかしテーブルが100個あれば、1つずつ判断するのは現実的ではないので、結局一律で流すことになります。

"Predictive" ＝ 効果を予測して、やる価値のあるものだけ実行する。 どのテーブルが断片化しているか、どこに効果があるかを Databricks が判断して動きます。 全テーブルに一律で流すのとは、コストの意味が違います。

ANALYZE統計情報を更新し、クエリ計画を改善—

対象は Unity Catalog の managed table です。 カタログで有効にすれば、配下のスキーマ・テーブルに継承されるので、 個別に設定して回る必要はありません。 UC の階層（カタログ → スキーマ → テーブル）に沿って上から効く—— 権限や ABAC とまったく同じ構造です。 UC の階層は、いろいろな設定の土台になっていると理解しておくと、覚えることが減ります。

hands-off という語

Serverless のガイド原文 use serverless for a hands-off, auto-optimized compute と同じキーワードです。 「運用を手放したい」という要件が出たら、対象を見ます。 コンピュートなら Serverless、テーブル保守なら Predictive Optimization。 対象が違うだけで、思想は同じです。

覚え方

誤答パターン

  • 「検索が遅い → VACUUM」 — VACUUM は性能改善の機能ではない。古いファイルを消しても、現行データの読み方は変わらない
  • 「ストレージを減らしたい → OPTIMIZE」 — OPTIMIZE は削除しない。新しいファイルを書くので一時的にはむしろ増える
  • 「MERGE が遅い → クラスタを大きくする」 — 探索の範囲は減らない。Liquid Clustering の担当
  • 「読むファイル数が多い → メモリを増やす」 — ファイル数の問題は OPTIMIZE の担当。メモリとは関係がない
  • 「特定列の検索が遅い → ZORDER BY」 — 誤りではないが、新ガイドの主役は Liquid Clustering。両方あれば後者

VACUUM と Time Travel「削減したい＋Time Travel も維持」が試験の定番

なぜ古いファイルが残っているのか

Delta では、UPDATE・DELETE・MERGE を実行しても、 古いファイルは物理削除されません。新しいファイルが書かれ、ログが切り替わるだけです。 古いファイルは一定期間ストレージ上に残ります。

残す理由は Time Travel です。過去のバージョンを参照するには、 そのバージョンが使っていたファイルが必要だからです。消してしまえば戻れません。 しかし残し続ければ、ストレージは増え続けます。そこで VACUUM です。

VACUUM prod.silver.orders;                    -- 既定の保持期間（7日）を過ぎたものを削除
VACUUM prod.silver.orders RETAIN 168 HOURS;   -- 7日ぶんは残す（168 = 24 × 7）
VACUUM prod.silver.orders RETAIN 720 HOURS;   -- 30日ぶんは残す
VACUUM prod.silver.orders DRY RUN;            -- 何が消えるかだけ確認（削除はしない）
書き方意味
VACUUM テーブル名既定の保持期間は7日。それより古い未参照ファイルを削除
RETAIN n HOURS保持期間を明示する。単位は時間のみ——日で書く構文はない（7日なら 168 HOURS）
DRY RUN削除せず、対象ファイルの一覧だけを返す。本番前の確認に使う

7日より短くはできない — 既定では止められる

ここに知らないと必ず引っかかる仕様があります。 RETAIN に 168 HOURS 未満を指定すると、 Databricks は実行せずにエラーで止めます。 「ストレージをすぐ減らしたいので24時間だけ残す」は、そのままでは動きません。

止める理由は実行中の読み取りです。 Delta では、クエリが開始した時点のバージョンを見続けます。長く走っているクエリやストリームは、 いま現行ではないファイルをまだ参照していることがあります。 そこを消すと、実行中の処理が「ファイルが無い」で落ちます。 この事故を防ぐための安全弁が、既定で入っています。

VACUUM prod.silver.orders RETAIN 24 HOURS;
-- エラー。既定では168時間（7日）未満を受け付けない

-- どうしても短くしたいときは、安全弁を外してから
SET spark.databricks.delta.retentionDurationCheck.enabled = false;
VACUUM prod.silver.orders RETAIN 24 HOURS;

安全弁を外す選択肢は、まず正解にならない

retentionDurationCheck を無効化する選択肢が並んでいたら、疑ってかかってください。 この試験は「要件を満たす安全な方法」を選ばせます。 短い保持期間が本当に必要なら、テーブルの設定 delta.deletedFileRetentionDuration を下げるのが筋であって、 セッション設定で検査を切って回避するのは応急処置です。

そもそも「ストレージを削減したい」という要件に対して、 保持期間を極端に短くする必要はありません。 既定の7日ぶんを残すだけでも、それより古いファイルは全部消えます。

消すのは「もう参照されていない」ファイルだけです。 現行のテーブルが使っているファイルは消しません。「VACUUM したらデータが消えた」は起きません。 消えるのは過去バージョンだけです。

トレードオフの正体

トレードオフは ストレージ ⇄ 遡れる期間。 古いファイルを残せば Time Travel はできるがストレージが増え、 消せばストレージは減るが過去に戻れなくなります。

ただしこれはどちらか一方を選ぶ話ではありません。 「7日前までは戻れるようにしたい」なら、7日ぶんを残してそれより古いものを消せばいい。 全部残すか全部消すかの二択ではなく、保持期間をどこに置くかの調整です。 ここを理解しておくと、選択肢を正しく読めます。

この形で出る

「ストレージを削減したい。ただし Time Travel は今後も利用したい」

条件が2つ並んでいます。「保持期間を短くして VACUUM」は前半しか満たしていません。 ストレージは減りますが、その期間より前には戻れなくなります。 正解は必要な遡り期間を RETAIN で確保した上で VACUUM するか、 Predictive Optimization に判断を委ねることです。

問題文に2つの条件が並んでいたら、両方を満たす選択肢を探します。 片方だけ満たす選択肢が必ず混ぜてあります。条件を1つ読み落とすと、そちらを選んでしまいます。 問題文を読むときは、条件がいくつあるかを数えてください。

小さなファイルをまとめるしない。それは OPTIMIZE
現行データを削除するしない。参照されていないものだけ

4つ目が効いてきます。ログは残っていても、ログが指すファイルが消えれば復元できません。 DESCRIBE HISTORY を実行すれば「バージョン10はこの日にこの操作でできた」と表示されるのに、 そのバージョンを SELECT するとエラーになる。 「履歴は見えるのに、戻れない」——これが VACUUM のあとに起きる現象です。 この理屈を理解しておけば、暗記しなくても判断できます。

① クラスタ起動失敗

最大の特徴は処理が始まる前に失敗することです。コードの問題ではありません。 典型的な原因は5つ——クラウド側のクォータ超過（インスタンス数の上限）、 インスタンスタイプが利用不可（そのリージョンで在庫がない）、 権限不足（インスタンスプロファイルやサービスプリンシパルの設定）、 ネットワーク設定（VPC・サブネット・セキュリティグループ）、 そしてinit script の失敗です。

起動失敗なら、コードをいくら直しても解決しません。ノートブックを見直しても無駄です。 見るべきはクラスタのイベントログやクラウド側の設定です。 試験ではこの形で問われます—— 「ジョブが失敗する。ノートブックのコードを確認したが問題ない。次に何を見るか」。 答えは、クラスタが起動しているかどうかです。

② ライブラリ競合

同じライブラリの異なるバージョンが同居して、実行時に壊れる現象です。よくある形が3つあります。

よくある形中身
Runtime 同梱 vs 自前インストールDatabricks Runtime には多くのライブラリが最初から入っている。別バージョンを入れると、どちらが使われるかが不安定になる
クラスタ全体 vs ノートブックスコープ%pip はノートブックスコープ。クラスタライブラリとして入れたものと混ざる
依存の噛み合わせA が C のバージョン1を要求し、B が C のバージョン2を要求する

切り分けの手は3つ。Runtime のバージョンを確認する—— Runtime が変われば同梱ライブラリも変わるので、「昨日まで動いていたのに」はここを疑います。 スコープを揃える——%pip かクラスタライブラリか、どちらかに統一します。 別のクラスタで再現するか試す——再現しなければ、そのクラスタ固有の問題です。

症状の特徴も覚えておいてください。 import では通るのに実行時に落ちる。あるいは別の環境では動く。 こういう症状なら、ライブラリ競合を疑います。

③ OOM — どこで溢れたか

OOM は「どこで溢れたか」で打つ手が正反対

driver は結果を集める側、executor は分散して計算する側。 ドライバなら持ってくる量を減らし、エグゼキュータなら1タスクの担当を減らす。方向が逆です。 ドライバの OOM にエグゼキュータを増やしても直りません。 溢れているのはドライバだからです。 OOM という症状を見たら、まず「どこで?」を確認してください。

ドライバの OOMエグゼキュータの OOM
典型的な原因collect() / toPandas() で全件を集める。autoBroadcastJoinThreshold を上げすぎた大きな broadcast1タスクの担当量が大きすぎる。data skew／shuffle.partitions が小さい
打つ手持ってくる量を減らす（集約してから collect、broadcast 閾値を下げる）1タスクの担当を減らす（分割を増やす、偏りを直す）
やってはいけないことエグゼキュータを増やす（効かない）ドライバのメモリだけ増やす（効かない）

処理は始まったか
 ├─ No  → クラスタ起動失敗（クォータ / 権限 / ネットワーク / init script）

確認問題スライドを見ずに、声に出して答えられるか

このドメインは「知っている」と「使える」の差が出ます。 10問、答えを見る前に自分の言葉で言ってみてください。 言えなかったものは、リンク先の節に戻ります。

  • Q1run history を見たら、実行時間が少しずつ伸び続けていました。何を疑いますか。ある日を境に急に伸びていた場合とは、どう違いますか。

    答えを見る

    じわじわ伸びているなら、データ量の増加と小さなファイルの蓄積を疑います。書き込むたびにファイルが増え、読むときに開くファイル数が増えるためです。急に伸びたならその日の変更——デプロイ・設定変更・上流データの変化を疑います。急なら変更、じわじわなら蓄積。（まず測る／小さなファイル問題）

  • Q2Spark UI で data skew を見つけるには、どのタブのどの指標を見ますか。また、skew に対してノードを増やすとどうなりますか。

    答えを見る

    Stages タブのステージ詳細にある Summary Metrics、その Duration の Median と Max の差を見ます。Min / 25th / Median / 75th / Max のうち、Max だけが桁違い（Median 2秒に対し Max 18分など）なら skew です。ノードを増やしても直りません。問題は1つのタスクが重いことで、並列度の問題ではないからです。10台に増やしても、そのタスクを処理するのは1台です。（Spark UI の読み方）

  • Q3Spill (Disk) に大きな数字が出ていました。何が起きていて、打つ手は何ですか。

    答えを見る

    メモリに乗り切らず、ディスクへ書き出しながら処理しています（disk spilling）。Spill の欄は正常なら空か 0 で、数字が見えた時点で異常です。打つ手は3つ——shuffle.partitions を増やして1タスクの担当量を減らす、メモリの大きいノードにする、そしてそもそも skew を直す。skew があると1タスクにデータが集中して溢れるため、skew と spill は同時に起きることがあります。（Spark UI の読み方）

  • Q4OPTIMIZE と VACUUM の目的の違いを、一言で言ってください。また、OPTIMIZE を実行するとストレージ使用量はどうなりますか。

    答えを見る

    OPTIMIZE は整理整頓、VACUUM はゴミ捨て。OPTIMIZE は小さなファイルをまとめて読み取りを速くする機能で、データを削除しません。行は1行も減りません。VACUUM は参照されない古いファイルを削除する機能で、5つの手法のうち削除するのはこれだけです。ストレージは、OPTIMIZE 実行後一時的にむしろ増えます。新しいファイルを書き、古いファイルは VACUUM するまで残るからです。（比較／小さなファイル問題）

  • Q5「ストレージを削減したい。ただし Time Travel は今後も利用したい」——この問題文にどう答えますか。また、DELETE したのに容量が減らないのはなぜですか。

    答えを見る

    条件が2つあります。「保持期間を短くして VACUUM」は前半しか満たしていません。正解は必要な遡り期間を RETAIN で確保した上で VACUUM するか、Predictive Optimization に委ねることです。問題文に条件が2つ並んでいたら、片方だけ満たす選択肢が必ず混ぜてあります。DELETE で容量が減らないのは仕様です。Delta は古いファイルを物理削除せず、新しいファイルを書いてログを切り替えるだけなので、減らすには VACUUM が必要です。（VACUUM と Time Travel）

  • Q6Liquid Clustering がパーティションより優れている点を3つ挙げてください。また、両者を併用できますか。

    答えを見る

    ① キーを後から ALTER で変更できる（パーティションは作り直しが必要）。② カーディナリティを選ばない（パーティションは低カーディナリティ列に限られ、customer_id で切れば100万ディレクトリになる）。③ 小さなファイル問題が起きにくい。併用はできません。Liquid Clustering はパーティションや ZORDER BY を置き換える機能で、CLUSTER BY のテーブルに PARTITIONED BY は指定しません。（Liquid Clustering）

  • Q7「特定の列での検索が遅い」という問題で、選択肢にZORDER BY と Liquid Clustering が両方ありました。どちらを選びますか。

    答えを見る

    Liquid Clustering です。ZORDER BY でも改善はするので誤りではありませんが、新ガイドの本文に ZORDER BY の記載はありません。明記されているのは Liquid Clustering と Predictive Optimization です。旧教材はこの行の答えを ZORDER BY にしているので、まず Liquid Clustering を思い浮かべる癖をつけてください。（Liquid Clustering）

  • Q8ドライバの OOM とエグゼキュータの OOM で、打つ手はどう違いますか。

    答えを見る

    正反対です。ドライバは結果を集める側、エグゼキュータは分散して計算する側だからです。ドライバの OOM は collect()・toPandas() や大きな broadcast が原因なので、持ってくる量を減らします。エグゼキュータを増やしても直りません。エグゼキュータの OOM は1タスクの担当量が大きすぎることが原因（skew や shuffle.partitions が小さい）なので、1タスクの担当を減らします。OOM を見たら、まず「どこで?」です。（障害の切り分け）

  • Q9「ジョブが失敗する。ノートブックのコードを確認したが問題ない」——次に何を見ますか。

    答えを見る

    クラスタが起動しているかです。最初の分岐は「処理が始まったか」で、始まる前に失敗しているならクラスタ起動失敗です。クォータ超過・インスタンスタイプが利用不可・権限不足・ネットワーク設定・init script の失敗を疑い、クラスタのイベントログやクラウド側の設定を見ます。起動失敗はコードをいくら直しても解決しません。なお import は通るのに実行時に落ちる／別環境では動く、という症状ならライブラリ競合（Runtime のバージョンとスコープ）を疑います。（障害の切り分け）

  • Q10Predictive Optimization は何を自動実行し、どの単位で有効にでき、対象は何ですか。

    答えを見る

    自動実行するのは OPTIMIZE・VACUUM・ANALYZE・クラスタリングの4つです。有効化は ALTER CATALOG … ENABLE PREDICTIVE OPTIMIZATION のようにカタログ／スキーマ単位で行い、配下に継承されます。対象は Unity Catalog の managed table です。"Predictive" は効果を予測して、やる価値のあるものだけ実行するの意で、全テーブルに一律で流すのとはコストの意味が違います。「hands-off」という要件なら、コンピュートは Serverless、テーブル保守はこれです。（Predictive Optimization）
