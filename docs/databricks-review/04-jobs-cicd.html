Jobs と CI/CD

作ったものを回し、本番へ配るところです。旧版では Production Pipelines という1セクションにまとまっていた領域が、新版で3つに分割されました。とくに CI/CD は旧版でほとんど問われておらず、実務経験でもカバーしにくい領域です。

Job / Task / DAGタスクを分ける理由は、失敗の切り分けと再実行

Job が実行とスケジュールの単位、Task が1つの処理、 DAG がタスク間の依存です。依存を書けば、順序も並列度も Jobs が決めます。 依存が無いタスクは自動的に並列に走ります。

DAG は Directed Acyclic Graph の略で、日本語では有向非巡回グラフといいます。 言葉は難しいですが、中身は「矢印で繋がった図で、ループしないもの」です。

具体例で読む

タスク何をするか依存実行のされ方
Task Aデータを取り込むなし最初に走る
Task BSilver に変換するAA の完了を待つ
Task C別ソースから取り込むAA の完了を待つ。B と並列
Task DGold の集計を作るB, CB と C の両方の完了を待つ

ここで大事なのは、B と C を「同時に走らせてください」と指示していないことです。 お互いに依存していないので、勝手に並列になります。 Declarative Pipelines と同じで、 関係を書けば順序は導出されるという発想がここでも効いています。

なぜ1つのノートブックに全部書かないのか

1タスクに全部書くとタスクを分けると
どこで失敗したか分からない失敗箇所が特定できる
失敗すると最初からやり直し失敗したタスクだけ再実行できる
並列化できない依存の無いものは並列に走る
コンピュートが1種類タスクごとにコンピュートを変えられる

3時間の処理が2時間50分の地点で失敗したとき、 分けていなければまた3時間かかります。これがタスク分割のいちばんの理由です。

コンピュートを分けられる点も実務では効きます。軽い前処理は小さいクラスタ、 重い集計だけ大きいクラスタ、という配分ができるからです。 1タスクにまとめると、いちばん重い処理に合わせたクラスタで全部を走らせることになります。

%run はタスク分割の代わりにならない

%run は1つのノートブックの中で別ファイルを読み込むだけです。 実行としては1つのまとまりなので、失敗の単位にも並列の単位にもなりません。 %run を並べても、失敗したら最初からです。

「ノートブックを分けた」ことと「タスクを分けた」ことは別物だ、と押さえてください。

DAG 表示は監視でも使う

ジョブの詳細画面では、タスクが箱で並び、矢印で依存が結ばれた DAG が表示されます。 各タスクの状態と所要時間が色と数字で分かり、並列に走るタスクは横に並びます。

この同じ画面を、監視と最適化で 「上流のどこが詰まっているか」を読むときにも使います。 Jobs の運用とトラブルシューティングは、試験ガイドでは別セクションですが、実務では地続きです。

タスクの種類ガイドが4つを括弧付きで名指ししている

Configure common tasks (notebook, SQL query, dashboard, and pipeline tasks)…

括弧付きで名前が並んでいるということは、「これはタスクにできるか」を直接聞ける ということです。名前そのものが問題文に出ます。

タスク何をするかポイント

タスクごとに何を設定するのか

タスク主に設定するもの
Notebookノートブックのパス／パラメータ／実行するコンピュート
SQL対象のクエリ・アラート・ファイル／SQL Warehouse／パラメータ

task_key は DAG の中でタスクを指す名前です。 依存関係も、値の受け渡しも、この名前で書きます。あとで出てくる YAML でも同じ名前が使われます。

パラメータの渡し方と受け取り方

「処理対象の日付」「書き込み先のカタログ」のように、 実行のたびに変えたい値は、コードに埋め込まずジョブから渡します。 渡す側はタスクの設定、受け取る側は dbutils.widgets です。

# 渡す側（ジョブのタスク設定 / YAML では base_parameters）
#   run_date = 2026-08-05
#   catalog  = prod

# 受け取る側（ノートブックの冒頭）
dbutils.widgets.text("run_date", "")        # 名前とデフォルト値を宣言
dbutils.widgets.text("catalog", "dev")

run_date = dbutils.widgets.get("run_date")  # 値を取り出す
catalog  = dbutils.widgets.get("catalog")

spark.sql("USE CATALOG " + catalog)
df = spark.read.table("bronze.orders").filter("order_date = '" + run_date + "'")

dbutils.widgets はノートブック上ではセルの上に入力欄として現れますが、 ジョブから実行されたときはその入力欄がジョブのパラメータで埋まります。 つまり「手で試すときの入力欄」と「ジョブから値を受け取る口」が同じ仕組みです。

Declarative Pipelines は単体でスケジュールできない

定義を書いただけでは動きません。定期実行するには Jobs の Pipeline タスクとして置く必要があります。

役割分担で覚えます。パイプラインの中身は LDP、いつ動かすかは Jobs。 「LDP だけでスケジュールできる」と考えていると、選択肢を間違えます。

ガイドの4つ以外に置けるもの

Python script / Python wheel（ノートブック以外のコード）、JAR（Scala・Java）、dbt。 さらに Run job（別ジョブの呼び出し）、 If/else condition、For each。 後ろの3つは処理をするタスクではなく、DAG に分岐やループを持ち込むための制御用です。

逆引き

やりたいこと答え

データ更新後にダッシュボードを最新化したいDashboard タスクを後段に置く

JDBC / REST から取り込むコードを回したいノートブックに書いて Notebook タスクとしてスケジュール

取り込みで 「JDBC や REST の取り込みは通常 Lakeflow Jobs によって編成・スケジュールされる」と出てきました。 その実体がこれです。API を叩くコードをノートブックに書き、Notebook タスクとして置く。それだけです。

トリガーと駆動方式ガイドが「choose between」と書いている＝選ばせる問題
トリガー起動条件向いている場面
Scheduled時刻（cron）締め処理・定時レポート。上流が確実に間に合う場合
File arrival指定した場所にファイルが置かれたら到着時刻が読めないデータ。待ち時間も空振りも無い
Table update指定した Delta テーブルが更新されたら前段の完了に連動させたい

後ろの2つが新版で明記されたものです。 旧版はスケジュール実行が中心でしたから、 「時刻で動かす以外の選択肢を知っているか」が新たに問われるようになった、と読めます。

Scheduled — cron の書式感

時刻は cron 形式で指定します。細かい書式を暗記する必要はありませんが、 フィールドが並んだ文字列で時刻を表すという形は見て分かるようにしておきます。

cron 式意味
0 0 2 * * ?毎日 2:00
0 0 * ? * MON-FRI平日の毎時 0 分
0 30 3 1 * ?毎月 1 日の 3:30
0 */15 * * * ?15 分ごと

タイムゾーンの指定は定番の事故

cron 式とセットでタイムゾーンを指定します。ここを既定のまま放置すると、 UTC で解釈されて日本時間と9時間ずれるという事故になります。 「毎晩2時のはずが、朝11時に動いていた」という形で表面化します。

さらに厄介なのが夏時間のある地域です。 現地時刻を指定すると、切り替えの日にその時刻が来ない日・2回来る日が発生します。 日次の締め処理では、この日だけ結果がずれます。

File arrival — 何を監視するのか

監視するのはストレージ上の「場所」です。 外部ロケーションや Volume として参照できるパスを指定し、 そこに新しいファイルが現れたことをきっかけにジョブが起動します。

  • 外部システムがファイルを置く → その場所を Databricks が見ている → ジョブが起動する、という3段の流れ
  • 待ち時間が生まれない。時刻で組むと「余裕を見て遅めに設定」することになり、 その余裕がそのまま待ち時間になる
  • 空振りしない。届いていないのに起動する、ということが起きない

Auto Loader の file notification（新着の検出方式）と、 Jobs の file arrival トリガー（ジョブの起動条件）は層が違います。 前者は Auto Loader が読む対象を見つける仕組み、後者はジョブそのものを起動する条件です。 「ファイルが来たら」という言葉は共通ですが、何が起動するかが違います。

時間駆動とデータ駆動の本質的な違い

ガイドは Choose between time-based and data-driven triggers based on data availability and pipeline dependencies と書いています。判断材料は2つ明示されています。

時間駆動
「3時になったから動く」。その時刻にはデータが揃っていると仮定している。 揃っていなくても走る。
データ駆動
「データが来たから動く」。事実を確認してから動く。来なければ動かない。

一言にすると、仮定するか、確認するかです。 時間駆動は「上流が時間どおりに動いている」という仮定の上に成り立っていて、 その仮定が正しいかどうかが分かれ目になります。

判断軸① データがいつ手に入るか

データの届き方選ぶもの
毎日必ず決まった時刻までに揃う時間駆動でよい
到着時刻がばらつく（「午前中のどこか」）データ駆動（file arrival）
来ない日があるデータ駆動（時間駆動だと空振りする）
到着と無関係に、決まった時刻に出したい時間駆動

データ駆動が常に優れているわけではない

「毎朝9時にレポートが出ていること」自体が要件なら、時間駆動が正解です。 データが早く揃ったからといって7時に出しても意味がありません。 問題文に「決まった時刻に」とあれば時間駆動です。

新しく明記された機能ほど「新しいほうが正解だろう」と選びたくなりますが、 ここは要件で決まります。

判断軸② パイプラインの依存関係

依存を時刻で繋ぐのは「たぶん終わっているだろう」という賭けです。 Silver を2時、Gold を3時に置くのは1時間の余裕を見ているだけで、 遅れれば壊れ、早く終われば待ちます。 Silver が2時10分に終わっても、Gold は3時まで50分待ちます。

問題文に依存関係が書かれていたら、データ駆動を疑ってください。

もう1つの選択肢 — 同じジョブの別タスクにする

依存を表現する手段は Table update トリガーだけではありません。 Silver と Gold を同じジョブの別タスクにして矢印を引くのも、依存の表現です。 選択肢に両方が並ぶことがあるので、使い分けを持っておきます。

同じジョブの別タスクにする別ジョブ＋Table update にする
同じサイクルで動くサイクルが違う（Silver は毎時、Gold は日次）
一連の処理として扱いたい所有しているチームが違う
まとめて再実行したい片方だけ止めたいことがある

判断の分かれ目は「ジョブをまたぐかどうか」です。 またがないなら DAG の矢印、またぐなら Table update トリガー。

制御フローと repairretry が効く失敗と、効かない失敗がある

Implement control flows (retries and conditional tasks such as branching and looping) using Lakeflow Jobs… retries・branching・looping の3つが名指しされています。

retry

retry はタスクごとに設定します。設定するのは主に2つ、 最大再試行回数と再試行までの間隔です。 「タイムアウト時にも再試行するか」を選べる場合もあります。

retry が効くretry が効かない
一時的なネットワーク断コードのバグ
外部 API のレート制限スキーマの不一致
クラスタの起動失敗権限不足
一時的なリソース不足データそのものの不正
時間を置けば直るもの何度やっても同じもの

回数と間隔の決め方にも考え方があります。

  • 回数を増やしすぎない — 効かない失敗に何度も再試行すると、 失敗を知るのが遅れ、コンピュートの料金だけがかさみます
  • 相手がレート制限なら間隔を長めに — すぐ再試行しても同じ壁に当たります
  • 後段の締め時刻から逆算する — 「回数 × 間隔 ＋ 実行時間」が 納期を超えるなら、その retry 設定は意味がありません

retry の前提は処理が冪等であることです。 データを半分書いたところで落ちたタスクを再実行したとき、 冪等でなければ半分が二重になります。 取り込みで COPY INTO や Auto Loader が冪等だったのは、 まさに安心して再試行できるようにするためでした。

分岐 — If/else condition と Run if

If/else condition は、条件で行き先を分けるタスクです。 たとえば「件数を数える」タスクの結果を見て、0 件なら通知だけ、1 件以上なら変換して書き込む、という形。

ここで問題になるのが、前のタスクの結果をどうやって条件に渡すかです。 その口が dbutils.jobs.taskValues です。

# 前のタスク（task_key: count_rows）の中で値を置く
n = spark.read.table("bronze.orders").count()
dbutils.jobs.taskValues.set(key="row_count", value=n)

# 後続のタスクから読む（既定値は必須）
n = dbutils.jobs.taskValues.get(
        taskKey="count_rows", key="row_count", debugValue=0)

# If/else condition タスクの条件欄には、この値を参照する式を書く
#   {{tasks.count_rows.values.row_count}}  >  0

プラットフォーム基盤で dbutils.fs・dbutils.widgets・dbutils.secrets を扱いました。 もう1つ dbutils.jobs.taskValues がある、と足しておいてください。 widgets は「ジョブから受け取る」、taskValues は「タスク間で受け渡す」です。

Run if は、依存の矢印そのものに条件を付ける仕組みです。 既定は「すべての依存が成功したら」ですが、これを変えられます。

Run if の条件走るのはどんなとき
All succeeded既定。依存タスクがすべて成功したとき
At least one succeeded1つでも成功していれば
None failed失敗が無ければ（スキップは許す）
All done成功・失敗を問わず、すべて終わったら
At least one failed1つでも失敗したら。失敗時だけの通知タスクに使う

ループ — For each

For each は、リストの各要素に対して同じタスクを繰り返します。 30 個のテーブルを同じ処理で更新する、国ごと・店舗ごとに同じ集計をする、といった場面です。

「タスクを 30 個作ればいいのでは」とも思えますが、 対象が増減するたびにジョブ定義そのものを直すことになります。 For each ならリストを変えるだけで、DAG の構造は変わりません。 判断基準は「対象が増減するか」。増減するなら For each、固定なら並べてもかまいません。

並列度（concurrency）の指定を忘れない

For each には同時に走らせる数の指定があります。既定のまま全部同時に投げると、 外部 API のレート制限に当たります。30 個の対象に一斉にリクエストすれば、 相手側から 429 を返されて全滅、ということが起こります。

相手が外部サービスなら並列度を絞る。相手が自前の Delta テーブルなら広げてよい。 ボトルネックが自分の外にあるかどうかで決めます。

repair run — 失敗した後

4タスクのうち3番目で失敗した場合、repair run は 3・4 だけを実行します。 成功した 1・2 はスキップされます。1・2 に2時間かかっていたなら、その2時間を節約できます。

repair が使えない場合

repair は「1・2 は正しく終わっている」ことを前提に続きから走ります。 もし 1 の出力自体が間違っていた場合、間違った出力を使って 3 が処理し、正常終了します。 エラーが出ないので気づけません。

判断軸は「成功したタスクの出力を、そのまま信じてよいか」。 信じられないなら全体を rerun します。

repair でよい全体を rerun すべき
失敗したタスクのコードだけを直した上流タスクの出力そのものが間違っていた
一時的な障害で落ちただけ上流のソースデータを取り直した
成功分の出力は正しいと確認できる複数タスクで使う共通ロジックを直した

retry は自動・その場、repair は手動・確認してから。 retry で拾えるのは「その場でやり直せば直るもの」だけです。 repair は人が原因を確認し、必要なら直してから使います。

実務の流れは、run history で失敗タスクを特定 → DAG 表示で上流の詰まりを確認 → ログとエラーメッセージで原因を特定 → repair か rerun を判断、という順になります。 最初の2ステップは監視と最適化の内容です。

Git folders での開発フローCI/CD の出発点は「コードが Git にあること」

Manage code development workflows within the Databricks workspace UI, including creating and switching branches, committing and pushing changes, and creating pull requests using Databricks Git integration.

Databricks Git folders（旧 Databricks Repos）は、 ワークスペースの UI からブランチ操作・commit / push・PR 作成ができる仕組みです。 ガイドが操作を1つずつ名指ししているので、操作名がそのまま問題文に出ます。 なお、ガイド本文はいまも旧称の「Databricks Repos」を使っている箇所があります。

これが無いと何が起きるか

動いているノートブックを壊したくないので、コピーします。 notebook_v2 を作って編集し、また変えたくなって notebook_v3、 本番用に notebook_final、さらに直して notebook_final_2。 見覚えのある形だと思います。

  • 誰が何を変えたのか分からない
  • 以前の状態に戻せない
  • レビューができない
  • 本番と開発の区別が曖昧

Git folders があれば、履歴が残り、ブランチで並行作業でき、PR でレビューでき、 本番と開発をブランチで区別できます。

6ステップの流れ

#ステップ何が起きるか
1ブランチを作成main から作業用ブランチを切る。UI のプルダウンから作成・切替できる
2編集ノートブックや YAML を Git folder の中で直接編集する
3commit / push変更ファイル一覧と差分を UI で確認し、Commit and Push。リモートに反映される
4Pull Request を作成UI のリンクから PR を作る。ここで CI が動く
5レビュー・マージ中身を人が見て main へ取り込む。CI が通らなければマージしない
6デプロイマージをきっかけに CD が走る（次のセクション以降）

問われているのは「UI だけで完結すること」

ターミナルで git コマンドを打つ必要も、IDE を用意する必要もありません。 within the Databricks workspace UI という一句が、そのまま出題の狙いです。

Git folders は、自動化の引き金を引ける状態を作るためのものです。 コードが Git にあり、「マージ」という明確なイベントがあるから、そこに CI/CD を繋げられます。 ここが無いと、このあとの Bundles も CLI も成立しません。

Declarative Automation Bundles旧 DAB。CI/CD の中核

ジョブやパイプラインの定義を YAML にし、環境ごとにデプロイする仕組みです。 旧 Databricks Asset Bundles、略称 DAB のまま流通しています。

# databricks.yml
bundle:
  name: sales_pipeline

include:
  - resources/*.yml            # 定義が大きくなったら分割できる

variables:
  catalog:
    description: 書き込み先カタログ
    default: dev
  warehouse_id:
    default: abc123
  schedule_cron:

4つのブロックの役割

resources が「何を」、targets が「どこへ」、 variables が「その差分」。 この3語の役割分担を答えられるかが、この領域の中心です。 残る bundle は名前など全体の設定です。

ディレクトリの形と include

1つのファイルに全部書く必要はありません。include: で分割できます。

sales_pipeline/
├── databricks.yml          ← バンドルの定義（include で下を読み込む）
├── resources/
│   ├── jobs.yml            ← ジョブだけを切り出す
│   └── pipelines.yml       ← パイプラインだけを切り出す
└── src/
    ├── ingest.py
    └── silver.sql

ここで気づいてほしいのは、定義（YAML）と実装（ノートブック・SQL）が同じリポジトリに同居する ことです。「この処理を追加して、このスケジュールで動かします」を 1つの Pull Request としてレビューできます。 コードだけ、あるいは設定だけを別々に見る、という分断が起きません。

同じコードベースを配る

ガイドのキーワードは promoting the same codebase です。 コードは同じまま、環境ごとの差分だけを外から与えます。 「dev 用と prod 用でコードを分ける」は、この思想の逆で、誤答の方向になります。

なぜ分けてはいけないのか。dev でバグを直したら、その修正を prod にもコピーすることになります。 コピー漏れが起き、prod 側に独自の修正が入り、やがて別物になります。 そうなると「dev で動作確認した」ことの意味が消えます。 「dev では動いたのに prod では動かない」は、こうして生まれます。

上の YAML でも、ジョブの定義は1つしかありません。 変わるのは ${var.catalog} のような参照が解決される値だけです。

mode何が変わるか狙い
developmentリソース名にユーザー名が付く／スケジュールは一時停止／開発者個人の領域にデプロイ複数人が触っても衝突しない。本番を誤って上書きしない
production名前はそのまま／スケジュールが有効／検証が厳しくなる本番として扱われる

「複数人が同時に開発しても衝突させたくない」と問われたら、 答えは mode: development です。 名前が変わるのでそもそも別のジョブになるからです。

何を変数にすべきか

変数にすべきもの理由
カタログ名・スキーマ名dev は dev カタログ、prod は prod カタログ
SQL Warehouse・クラスタの ID環境ごとに実体が違う
スケジュールdev では動かしたくないことが多い
通知先dev は自分、prod は運用チーム
データのパス環境ごとにバケットが違う
認証情報 → 変数にしないYAML は Git に入る＝リポジトリを見られる全員が読める。シークレットで管理する

resources に書けるもの、promote の意味

jobs・pipelines のほか、 schemas・volumes・clusters・dashboards・ models・experiments なども書けます。 ガイドは Lakeflow Jobs, Lakeflow Spark Declarative Pipelines, and other workspace assets と書き、動詞に package / configure / promote を並べています。

スキーマや Volume まで書けることには意味があります。 手作業だと dev にはあるスキーマが prod に無い、権限が片方だけ違う、といったずれが生まれ、 しかもデプロイして初めて気づきます。バンドルなら、コマンド1つでその環境があるべき形になります。

promote は「作り直す」ではなく「同じものを次の環境へ上げる」ことです。 dev で確認 → test で検証 → prod へ。途中で作り直さないから、環境差で壊れません。

Databricks CLIvalidate / deploy / manage の3動詞

Understand the Databricks CLI for validating, deploying, and managing Declarative Automation Bundles and other workspace assets in automated CI/CD workflows.

末尾の automated が効いています。人が手で叩くだけでなく、 CI から呼ばれることが前提に置かれています。

databricks bundle validate -t prod   # 定義を検証（デプロイはしない）
databricks bundle deploy   -t prod   # 配る
databricks bundle run daily_etl -t prod
databricks bundle summary  -t prod   # 何が配られるか確認
databricks bundle destroy  -t dev
コマンド何をするいつ使う
validate定義を検証する。配らないPR ごとに CI で／手元で書いた直後
deploy定義どおりに配るマージ後に CD で／dev で試すとき
run配ったジョブを実行するデプロイ直後の動作確認
summary何が配られるかを表示する本番へ配る前の確認
destroy配ったものを削除する開発環境の片付け

validate を挟む意味

validate が無いと、YAML の書き間違いや変数の未定義にデプロイの実行時に初めて気づきます。 しかも悪い場合には、途中まで配られた状態で止まります。 ジョブは配られたがパイプラインは配られていない、という中途半端な状態です。

PR の CI で validate を自動実行しておけば、壊れた定義が main に入ることを防げます。

-t の指定ミスは事故になる

-t は target の指定です。間違えると dev のつもりで prod に配り、本番のジョブを開発中のコードで上書きします。

指定しない場合は default: true の target が使われます。 だから prod に default: true を付けてはいけません。 dev に付けておくのが安全側の設定です。

認証はサービスプリンシパル

CI から CLI を実行するときの認証には、サービスプリンシパルを使います。 個人のアクセストークンを CI に置いてはいけません。

  • その人の異動・退職で CI が壊れる
  • 監査ログ上、誰の操作なのかが曖昧になる（実際には CI が動かしている）
  • 個人の権限がそのまま CI の権限になり、必要以上に強くなりがち

サービスプリンシパルは人ではなく、システムのための識別子です。 ガバナンスで出てくる principals の3種類 （ユーザー・グループ・サービスプリンシパル）の、3つ目がここで使われます。

CI/CD の全体像実体は「決まったタイミングで走るコマンド」

CI/CD という言葉は抽象的ですが、やっていることは具体的です。 決まったタイミングで、決まったコマンドを自動実行する。それだけです。

きっかけ走るもの目的
ブランチに push（任意）lint・単体テスト早い段階で明らかな誤りを弾く
PR を作成・更新bundle validate -t dev ＋ テスト＝ CI。壊れた定義が main に入るのを防ぐ
レビュー通過 → main へマージbundle deploy -t prod＝ CD。本番へ配る
デプロイ直後bundle run（スモークテスト）配ったものが動くかを確認する
その後Jobs のスケジュール／トリガーで自動実行配られたジョブが回り始める
障害時Git で前の版に revert → bundle deploy素早く元に戻す

CI と CD の実体

CI ＝ PR ごとに bundle validate とテストを走らせること。 YAML の書き間違いや変数の未定義を、マージ前に検出できます。
CD ＝ マージをきっかけに bundle deploy が走ること。

3つの道具の役割分担

Git folders
起点。コードを Git に置き、「マージ」という引き金を作る。
Automation Bundles
定義。何を、どこへ、どんな差分で配るかを YAML に書く。
Databricks CLI
実行手段。その定義を検証し、配り、動かす。

試験でこの領域が問われたときは、「この流れのどこの話か」を先に決めると、 選択肢が絞れます。「配る前に検出したい」なら validate、「マージをきっかけに」なら deploy、 「そもそもコードが Git に無い」なら Git folders です。

巻き戻しに注目してください。本番でトラブルが起きたとき、いちばん重要なのは 素早く元に戻せることです。定義が Git にあるので revert して再デプロイすれば戻ります。 UI で作ったものは「昨日の設定、どうなってたっけ」から始まります。

【判別】バンドル vs 従来デプロイobjective は「違いを識別せよ」

Identify the difference between DAB and traditional deployment methods. 使い方より従来との対比が問われる、という書き方です。 つまり「従来の方法が何であり、何が問題だったか」を言えることが前提になります。

従来の方法と、その問題

従来の方法何が問題か
UI で手作業設定が Git に残らない。再現できない。「どういう設定だったっけ」となる
ノートブックのコピーどのバージョンをコピーしたか分からない。コピー漏れが起きる
REST API を自作スクリプトで叩く自動化としては前進だが、自作なので保守が必要。仕様変更に追随し続けることになる
汎用の IaC ツール動くが、Databricks 固有の概念とずれることがある

4つに共通する問題は「あるべき姿がコードとして1箇所にない」ことです。 だから環境間でずれ、再現できず、レビューもできません。

従来（UI / コピー）Automation Bundles
定義の置き場所ワークスペースの中Git（YAML）
レビューできないPR でできる
環境の出し分け手作業で個別にvariables ＋ targets
再現性低い同じ定義から同じ結果
巻き戻し手作業Git で前の版に戻して再デプロイ
自動化難しいCLI で CI/CD に組み込める

手続き的か、宣言的か

従来のやり方は手続き的です。「ジョブを作る」「タスクを追加する」「スケジュールを設定する」 という操作の列を順に実行します。途中で失敗すれば、 ジョブは作られたがスケジュールは設定されていないという中途半端な状態が残ります。

バンドルは宣言的です。「この環境はこうあるべき」と書き、 現状との差分は CLI が埋めます。既にあれば更新し、無ければ作り、不要なものは消す。 あるべき姿に合わせにいくのはこちらではなく、仕組みのほうです。

これで「宣言的」が4回目

Declarative Pipelines、Expectations、Jobs の DAG、そして Automation Bundles。 すべて「手順ではなく、あるべき姿を書く」という同じ思想です。 Databricks 全体がこの方向に進んでいるため、 迷ったらこの思想に沿った選択肢が正解になりやすくなります。

このドメインの問題は、たいてい「手作業をやめる」方向が正解になります。 UI で作る・コピーする・手で設定する、は誤答になりやすく、 コードにする・自動化する・一元管理する、が正解の方向です。

このドメインでよくある誤解選択肢に混ぜられる形で出る

ここに挙げたものは、いずれももっともらしく見える誤りです。 誤答の選択肢はこういう形で作られます。

よくある誤解正しくは
Declarative Pipelines は単体でスケジュールできるできない。Jobs の Pipeline タスクとして起動する。中身は LDP、いつ動かすかは Jobs
%run でノートブックを分ければタスク分割になるならない。実行としては1つのまとまりで、失敗の単位にも並列の単位にもならない
データ駆動トリガーのほうが常に優れている要件次第。「決まった時刻に出す」こと自体が要件なら時間駆動が正解
file arrival トリガーと Auto Loader の file notification は同じもの層が違う。前者はジョブの起動条件、後者は Auto Loader の新着検出方式
retry を多めに設定しておけば安全効かない失敗には無意味。失敗を知るのが遅れ、料金だけがかかる。前提は処理が冪等であること
repair run はいつでも安全に使える成功タスクの出力を信じてよいときだけ。上流の出力が誤っていると、誤りのまま正常終了する
dev 用と prod 用でコードを分けるべき思想の逆。promoting the same codebase。コードは同じまま、差分だけ variables で外から与える
バンドルで配れるのは Jobs だけpipelines・schemas・volumes・clusters・dashboards なども配れる
環境ごとの接続情報は variables に書けばよい認証情報は書かない。YAML は Git に入る＝全員が読める。シークレットで管理
CI には自分のアクセストークンを置けばよいサービスプリンシパルを使う。個人トークンは異動・退職で壊れ、主体も曖昧になる
-t を省略しておけば事故らない省略すると default: true の target に配られる。prod に default を付けていたら本番に配られる
Git folders を使うには IDE やターミナルが要るワークスペースの UI だけで完結する。ガイドの一句がまさにそこ

迷ったときの指針は2つ。 ①「手作業をやめる」方向を選ぶ。 ②「仮定せず、確認する」方向を選ぶ。 この2つで、このドメインの多くの問題は方向が定まります。

確認問題答えを見る前に、声に出して答えてみる

スライドを見ずに答えてみてください。 言葉に詰まったところが、そのまま復習すべき箇所です。

  • Q1resources・targets・variables は、それぞれ何を定義しますか。

    答えを見る

    resources が「何を」（jobs・pipelines・schemas など配る対象）、targets が「どこへ」（dev / test / prod）、variables が「その差分」。残る bundle は名前など全体の設定です。

  • Q2mode: development にすると、何が変わりますか。

    答えを見る

    リソース名にユーザー名が付き、スケジュールが一時停止され、開発者個人の領域にデプロイされます。複数人が同じバンドルを触っても衝突せず、本番を誤って上書きすることもありません。

  • Q3bundle validate と bundle deploy は、CI と CD のどちらに対応しますか。

    答えを見る

    validate が CI（PR ごとに走らせ、壊れた定義が main に入るのを防ぐ）、deploy が CD（マージをきっかけに本番へ配る）。

  • Q4Declarative Pipelines を毎晩定期実行したい。何が必要ですか。

    答えを見る

    Jobs の Pipeline タスクとして置くこと。LDP は定義を書いただけでは動きません。中身は LDP、いつ動かすかは Jobs です。

  • Q5従来のデプロイ方法（UI で手作業・コピー・自作スクリプト）に共通する問題は何ですか。

    答えを見る

    あるべき姿がコードとして1箇所にないこと。だから環境間でずれ、再現できず、レビューもできず、巻き戻せません。

  • Q6retry が効く失敗と効かない失敗を、それぞれ2つ挙げてください。また、retry の前提は何ですか。

    答えを見る

    効く＝一時的なネットワーク断、外部 API のレート制限、クラスタの起動失敗など時間を置けば直るもの。効かない＝コードのバグ、スキーマの不一致、権限不足など何度やっても同じもの。前提は処理が冪等であることです。

  • Q74タスクのジョブの3番目で失敗しました。repair run では何が実行されますか。また、repair を使ってはいけないのはどんなときですか。

    答えを見る

    3 と 4 だけが実行され、成功した 1・2 はスキップされます。使ってはいけないのは上流タスクの出力そのものが疑わしいとき。誤った出力のまま処理が進み、エラーを出さずに正常終了してしまいます。

  • Q8タスク間で値を渡す仕組みと、ジョブからノートブックへパラメータを渡す仕組みは、それぞれ何ですか。

    答えを見る

    タスク間は dbutils.jobs.taskValues（set / get）。ジョブ→ノートブックはタスクのパラメータと dbutils.widgets（受け取り側）。

  • Q9For each タスクで並列度を絞る必要があるのは、どんな場面ですか。

    答えを見る

    外部 API を叩くループ。30 個の対象に一斉にリクエストするとレート制限に当たります。ボトルネックが自分の外にあるときは絞り、自前の Delta テーブルが相手なら広げてよい、と考えます。

  • Q10CI から Databricks CLI を実行するときの認証は、何を使いますか。理由も。

    答えを見る

    サービスプリンシパル。個人のアクセストークンだと、その人の異動・退職で CI が壊れ、監査上も誰の操作か曖昧になり、権限も必要以上に強くなりがちです。

最後の確認をもう1つ。 「決まった時刻にレポートを出すこと自体が要件」なら、時間駆動とデータ駆動のどちらですか。 答えは時間駆動です。新しい機能のほうを選びたくなるところですが、要件が決めます。
