何が変わったか

2026年5月4日、試験が5セクションから7セクションへ再編されました。市販教材の多くは旧構成のままです。何が消え、何が入り、何の扱いが大きくなったのかを先に押さえます。ここを知らないまま古い教材で勉強すると、丸ごと無駄になる範囲が出ます。

なぜ最初にこれを読むか抜けているものは、読んでいても気づけない

普通なら機能の説明から入るところを、あえて差分から始めます。理由は単純です。

世の中に出回っている教材の多くは、まだ旧5セクション構成で作られています。 問題集も、対策ブログも、動画講座もそうです。 内容が誤っているわけではありません。ただ、新しく入った範囲が丸ごと抜けています。

そして抜けているものは、読んでいても気づけません。 「載っていない」ことに気づく方法が無いからです。 自分がどこを知らないかを知らない状態で本番に向かうことになります。だから、先に差分を知っておく必要があります。

差分と言っても、性質の違うものが混ざっています。 対処の仕方が変わるので、最初に4つに分けておきます。

類型何が起きたか古い教材で起きる症状対処
消えた試験範囲から外れた熱心にやるほど空振りになるその章は飛ばす
入った新しく試験範囲になったそもそも載っていないので気づけない別の情報源で補う
格上げされた1セクションが3セクションに分割された分量が足りず、浅いまま本番へ行く割く時間を増やす
名前が変わった機能は同じで、呼び名だけ新しくなった範囲内の機能を範囲外だと誤認する対応表で読み替える

このページでは、上の3つ（消えた・入った・格上げされた）を扱います。 4つ目の「名前が変わった」は数が多く、単独で1枚の表になるので 総合インデックスの対応表に切り出してあります。

旧版の適用期限

2026年5月3日までの受験には旧ガイドが適用されました。 5月4日以降の受験はすべて新ガイドです。公式 PDF には両方のガイドが併記されているため、 読むときは「NEW EXAM GUIDE」以降を見てください。 前半だけ読んで「セクションは5つだ」と思い込む事故が起きやすい箇所です。

試験そのものの条件（45問 / 90分 / 有効期間2年 / 前提資格なし）は改訂で変わっていません。 変わったのは中身の配分です。

旧5セクション → 新7セクションの対応表増えたのではなく、割り直された

「5から7に増えた」と言うと、2つ足されただけのように聞こえます。実際には違います。 既存の領域が割り直され、そのうえで新しい項目が差し込まれています。 旧版で勉強した人ほど、この地図を先に持っておく価値があります。

比率を根拠に捨てるドメインは作らない

非公式の比率は時間配分の参考程度に留めてください。全45問しかないので、 10% は約4〜5問です。1ドメインを丸ごと落とすと、それだけで合格ラインに届かなくなります。 「CI/CD は10%だから捨てる」という判断は、この問題数では成立しません。

なお、旧版でも新版でも「変換」がいちばん重い領域である点は変わっていません。 変わったのは、その周り——入口（取り込み）と出口（Jobs / CI/CD / 運用）が 独立した領域として立ち上がったことです。

Lakehouse Federation外部データソースへ接続し、コピーせずにクエリする同上。ユースケースを問う出題があった

この2つは、新ガイドの本文から消えています。 そして重要なのは、旧版においてこの2つがガバナンス領域のかなりの部分を占めていたことです。 体感で半分近くあります。つまり旧版のガバナンス章は、半分が空振りになる計算です。

古い問題集を使うときの落とし穴

旧版の問題集でガバナンスを一通りやると、体感でかなりの分量が Delta Sharing に割かれます。 そこを熱心にやっても、そのぶんは空振りになります。 実務では使う機能なので知識として無駄ではありませんが、この試験の対策としては優先度を大きく下げて構いません。

ここで、消えた枠に何が入ったかを見ると、改訂の意図が読めます。 ガバナンス領域は「無くなった」のではなく、主題そのものが移動しています。

「消えた」の意味は、新ガイドの本文に語として現れないということです。 公式が「絶対に出題しない」と宣言したわけではありません。 ただ、出題範囲はガイドのアウトラインに沿って作られるため、対策の優先度としては最下位で構いません。 実務で Delta Sharing を使う予定があるなら、試験が終わってから学び直すのが効率的です。

入口が広がった
Lakeflow Connect と COPY INTO。旧版の取り込みは 「クラウドストレージにファイルが置かれる」前提がほとんどでした。 新版は、ファイルになっていない業務システムから直接引く経路と、 SQL だけで完結する冪等ロードが加わっています。
出口が広がった
Declarative Automation Bundles と Databricks CLI。 作ったものを dev / test / prod へどう届けるか、という工程が試験範囲に入りました。 ノートブックを本番ワークスペースに手でコピーする世界観は、もう想定されていません。
運用の解像度が上がった
Liquid Clustering、Predictive Optimization、Spark UI 診断、 そして ABAC・行レベルセキュリティ・列マスキング。 「動いたあと」をどう速くし、どう安全に見せるか。 作って終わりではなく、回し続ける側の知識が問われます。

いずれも旧版には存在しませんでした。裏を返せば、 この領域は受験者間で差がつきやすいということです。 さらに言えば、新規領域はまだ問題集の蓄積が薄いので、 公式ガイドに書かれた語をそのまま拾って押さえるのが最短経路になります。

新規項目はなぜ入ったのか手動から自動へ、手続き的から宣言的へ

追加された9項目を、暗記リストとして眺めるともったいないです。 1本の方向性が通っています。それを掴んでおくと、 知らない機能名が選択肢に出てきたときにも当たりを付けられます。

方向性は2語で言えます。手動から自動へ。手続き的から宣言的へ。 「人が手順を書いて実行する」から「望ましい状態を宣言して、実現は任せる」への移行です。 追加項目は、ほぼすべてこの軸の上に乗っています。

テーブルのメンテナンスOPTIMIZE / VACUUM を定期ジョブで回すPredictive Optimization が効果のあるテーブルにだけ自動実行
パイプラインの記述タスクの実行順を自分で組み立てるDeclarative Pipelines が依存関係を自動解決
デプロイUI で手作業。ノートブックを環境ごとにコピーAutomation Bundles の YAML ＋ targets で環境を出し分け
アクセス制御テーブルごとに個別に GRANT を積むABAC ポリシーでタグに対して一度定義し、横断的に効かせる
取り込みいったんファイルに落としてから読むLakeflow Connect が業務システムから直接引く

機能名そのものにも痕跡があります。 Declarative（宣言的）、Predictive（予測的）、 Auto（自動）。この3語が付いた機能名は、新ガイドが主役側に置いたものだと考えてほぼ外しません。 Declarative Pipelines、Declarative Automation Bundles、Predictive Optimization、Auto Loader、 CLUSTER BY AUTO——並べると一目瞭然です。

迷ったときの重心

選択肢に「人が手作業で回す案」と「宣言して任せる案」が並んでいたら、 後者に重心を置いて読む。これが新ガイドの空気に合っています。 知らない機能名が出てきても、名前に Declarative / Predictive / Auto が入っていれば、 それは新ガイド側の語である可能性が高いです。

ただし万能ルールではない

「自動と書いてあれば正解」ではありません。 トレードオフを問う問題では、手動側が正解になります。 典型が VACUUM と Time Travel です。 ストレージを削減するために古いファイルを消せば、そのぶん過去バージョンを参照できなくなります。 ここは自動化の話ではなく、保持期間をどう決めるかという判断の問題です。 自動化の流れは当たりを付けるための重心であって、判断を省く道具ではありません。

格上げされたもの1セクションが3つに分割された＝出題数が増えた

消えたものでも入ったものでもなく、扱いが大きくなった領域があります。 旧版で「Production Pipelines」という1つのセクションにまとまっていた領域が、 新版では3つの独立したセクションに分かれました。

独立したセクションになったということは、それだけ出題数が増えたということです。 非公式の目安比率で合算すると、16% だった領域が 36%（16 + 10 + 10）前後になります。 比率そのものは公式値ではありませんが、1つが3つに割れたという事実だけで、 割く時間を2倍以上にする理由になります。

CI/CD がいちばん手薄になりやすい

旧版では CI/CD はほとんど問われていませんでした。そのため、 実務経験でもカバーできない人が多い領域です。 データエンジニアの仕事の中で、デプロイの仕組みまで自分で作る機会は意外と少ないからです。 すでにある CI/CD パイプラインに乗って仕事をしていると、 YAML の中身を読んだことがないまま何年も過ぎます。意識して時間を取ってください。

具体的な到達目標は1つで足ります。バンドルの YAML を1本、上から下まで 「これは何を宣言している行か」と説明できる状態にする。 試験ではこの形の設問が出ます。

Troubleshooting も似た事情があります。 障害対応は経験でカバーできそうに見えますが、 Spark UI の stage 指標を読んで skew と spill を区別する、という粒度で聞かれると、 「なんとなく直した」経験は答えに変換できません。

ZORDER BY の立ち位置この改訂で最も注意すべき一点

旧版では、こういう問題が定番でした。

「大きなテーブルの検索が遅い。特定の列で頻繁に絞り込んでいる。どうするか」

答えは OPTIMIZE ... ZORDER BY (col) でした。 ところが新しい試験ガイドを読むと、ZORDER BY という語が本文に出てきません。 代わりに明記されているのが Liquid Clustering と Predictive Optimization です。

旧版の答え新版で明記されているもの
検索が遅いOPTIMIZE ... ZORDER BYLiquid Clustering
メンテナンス手動で OPTIMIZE / VACUUM を回すPredictive Optimization
キーの変更都度 OPTIMIZE で指定ALTER TABLE ... CLUSTER BY で変更可
列の選定カーディナリティを考慮して選ぶCLUSTER BY AUTO で任せられる

書き方の対比も見ておきます。同じ「この列での絞り込みを速くしたい」に対する、旧と新です。

-- 旧版の定番（新ガイド本文に ZORDER BY の記載は無い）
OPTIMIZE sales
  ZORDER BY (customer_id);

-- 新版で明記されている書き方
CREATE TABLE sales (
  customer_id BIGINT,
  amount      DECIMAL(10,2)
) CLUSTER BY (customer_id);

-- 既存テーブルに後から指定する／キーを変更する
ALTER TABLE sales CLUSTER BY (customer_id, order_date);

-- 列の選定自体を任せる（クエリ履歴から Databricks が決める）
ALTER TABLE sales CLUSTER BY AUTO;

なぜ入れ替わったのか。土台にあるのは Data Skipping です。 Delta は各ファイルについて列の最小値と最大値を記録していて、 クエリの条件に合わないファイルは開かずに読み飛ばします。 値の近いデータが同じファイルに寄っているほど、読み飛ばせる量が増える。 だからデータの置き方が、そのまま読み取り性能になります。 その置き方を最適化する手段が、パーティション・ZORDER BY・Liquid Clustering の3つです。

観点パーティションZORDER BYLiquid Clustering
指定の仕方PARTITIONED BYOPTIMIZE ... ZORDER BYCLUSTER BY
キーの変更テーブルの作り直しが必要OPTIMIZE のたびに指定できるALTER TABLE で変更できる
カーディナリティ低い列に限られる中〜高でも使える選ばない
小さなファイル問題起きやすいOPTIMIZE で解消する起きにくい
新ガイドでの扱い特に記載なし記載なし明記されている

パーティションの弱点を1つだけ補足しておくと、理解が固まります。 customer_id のようなカーディナリティの高い列でパーティションを切ると、 顧客が100万人いれば100万個のディレクトリができ、それぞれに小さなファイルが入ります。 日付で切れば1年で365個で済むので、パーティションは「切る列を正しく選ぶ」ことが前提の仕組みです。 Liquid Clustering は、その選択自体を不要にしました。

では ZORDER BY は捨ててよいのか

そこまでは言えません。Delta Lake の基本機能として出題される可能性は残っています。 ただし主役ではありません。 選択肢に Liquid Clustering と ZORDER BY が並んでいたら、Liquid Clustering を選びます。 問題文を読んだとき、まず Liquid Clustering を思い浮かべる——これを癖にしてください。

逆向きの注意もあります。ZORDER BY が誤りだと覚えないでください。 ZORDER BY でも性能は改善します。技術的に間違いではありません。 試験で問われているのは「新ガイドがどちらを想定しているか」であって、 「どちらが動くか」ではない、という切り分けです。

同じ理由で、OPTIMIZE そのものは今も生きています。 小さなファイルが大量にある場合の答えは OPTIMIZE のままです。 消えたのは ZORDER BY という列指定の句のほうだ、と分けて覚えると混ざりません。

古い教材の使い方捨てる必要はない。読み替えれば使える

旧版向けの教材が手元にある場合、全部捨てる必要はありません。次の3つを意識すれば使えます。

教材の種類ごとに、扱い方が少し変わります。

教材の種類使えるか注意点
旧版の問題集使える（S1・S3 は特に有効）ガバナンス章は半分ほど空振り。CI/CD・Spark UI 診断・Liquid Clustering は載っていない。最適化の設問は答えが ZORDER BY になっているので、読み替えて解く
旧称で書かれたブログ・動画使える。むしろ数が多く解説も丁寧対応表で読み替える。特に DLT と DAB は略称のまま流通しているので、知らないと何の記事か分からない
公式ドキュメント最優先常に最新に追随している。試験ガイド本文と語が一致しているものを優先して読む
旧版の模擬試験部分的に使える新規領域が出題されないので、スコアをそのまま合否の目安にしない。弱点の洗い出しには使えるが、点数を信用しない

むしろ古い記事のほうが、数が多く解説も丁寧なことがよくあります。 翻訳表を1枚持っているかどうかで、使える情報源の量が変わります。 古い教材の問題は「間違っていること」ではなく「足りないこと」だと押さえておけば、 捨てずに使い切れます。

移行チェックリスト旧版で勉強済みの人が、何をやり直すか

旧版で一度勉強した人、あるいは旧版の教材で学習を始めてしまった人向けの棚卸しです。 ゼロからやり直す必要はありません。作業は5種類しかありません。 捨てる・読み替える・上書きする・足す・増やす、です。

#作業対象なぜ
1捨てるDelta Sharing / Lakehouse Federation の暗記新ガイド本文から消えた。覚えていても加点されない
2読み替えるDLT / DAB / Repos / Workflows / SQL Endpoint / クラスター機能は同じ。名前だけ違う。読み替えないと範囲外と誤認する
3上書きする「検索が遅い → ZORDER BY」という反射新ガイドの想定解は Liquid Clustering。知識を足すのではなく、反射そのものを差し替える必要がある
4ゼロから足すCI/CD（Git folders / Automation Bundles / variables・targets / CLI）旧版でほぼ問われていない。実務経験でも埋まりにくい最大の穴
5ゼロから足すSpark UI 診断（data skew / shuffling / disk spilling）「どの画面のどの数字を見て何を判断するか」の粒度で問われる
6ゼロから足すABAC ポリシー / 行レベルセキュリティ / 列マスキング旧ガバナンスの空いた枠に入ってきた新主題
7足すLakeflow Connect / COPY INTO / Liquid Clustering / Predictive Optimization取り込みと最適化の新項目。既存知識の隣に置けるので負荷は軽い
8増やすLakeflow Jobs（トリガー3種、制御フロー、repair run）独立セクションに格上げされた。旧版の分量では足りない

順番に迷ったら、4 → 5 → 6 → 3 → 7 → 8 → 2 → 1 で構いません。 「そもそも載っていなかったもの」から手を付けるのが、いちばん取りこぼしが減ります。

確認問題改訂差分だけに絞った8問

このページの内容だけで答えられる問題です。 機能そのものの知識ではなく、「旧版と何が違うか」を問うています。 答えを見る前に、口に出して答えてみてください。

  • Q1新ガイドの本文から消えた機能を2つ挙げてください。また、それらを覚えていた場合、試験対策としてどう扱えばよいですか。

    答えを見る

    Delta Sharing と Lakehouse Federation。どちらも旧版ではガバナンス領域のかなりの部分を占めていましたが、新ガイド本文から消えています。実務では使う機能なので知識として無駄ではありませんが、この試験の対策としては優先度を最下位に下げて構いません。

  • Q2旧版で1つだったセクションが、新版で3つに分割されました。旧セクション名と、分かれた先3つの名前を答えてください。

    答えを見る

    旧 Production Pipelines（旧ガイドで16%）が、Working with Lakeflow Jobs／Implementing CI/CD／Troubleshooting, Monitoring, and Optimization の3つに分割されました。1つが3つになった＝出題数が増えた、と読みます。

  • Q3「大きなテーブルの検索が遅い。特定の列で頻繁に絞り込んでいる」——この設問に対する新ガイドの想定解は何ですか。旧版の答えはどうなりましたか。

    答えを見る

    新ガイドの想定解は Liquid Clustering。旧版の答えだった OPTIMIZE ... ZORDER BY は、ZORDER BY という語が新ガイド本文に出てきません。ただし ZORDER BY が誤りになったわけではなく、Delta Lake の基本機能として出題される可能性は残ります。主役から降りた、という位置づけです。

  • Q4Liquid Clustering がパーティションより優れている点を2つ挙げてください。

    答えを見る

    (1) キーを後から変更できる——ALTER TABLE ... CLUSTER BY でいつでも変えられます。パーティションはテーブルの作り直しが必要です。(2) カーディナリティを選ばない——パーティションは低カーディナリティの列に限られ、customer_id のような列で切ると小さなファイルが大量に発生します。Liquid Clustering ではその問題が起きにくくなっています。

  • Q5DLT / DAB / Repos / Workflows は、新ガイドではそれぞれ何と呼ばれていますか。

    答えを見る

    DLT → Lakeflow Spark Declarative Pipelines、DAB → Declarative Automation Bundles、Repos → Databricks Git folders、Workflows → Lakeflow Jobs。ネット上の情報は旧称で書かれたものが大半なので、この4つを押さえておくと調べ物でつまずかなくなります。

  • Q6旧版と新版で、ガバナンス領域の「主題」はどう変わりましたか。

    答えを見る

    組織の外へどう出すか（Delta Sharing / Lakehouse Federation）から、組織の中で誰に何を見せるか（行レベルセキュリティ / 列マスキング / ABAC ポリシー）へ移りました。制御の粒度も、オブジェクト単位から行・列・タグ単位へ細かくなっています。枠は残っていますが中身は入れ替わっている、と捉えてください。

  • Q7旧版の教材で勉強すると最も手薄になる領域はどこですか。また、なぜ実務経験でも埋まりにくいのですか。

    答えを見る

    CI/CD（Git folders / Automation Bundles / variables・targets / CLI）。旧版ではほとんど問われていませんでした。そして実務では、すでにある仕組みに乗って開発することが多く、デプロイの仕組みを自分で作る機会が少ないため、経験でもカバーしにくい領域です。到達目標は「バンドルの YAML を1本、上から下まで説明できる」こと。

  • Q8新規に追加された項目に共通する方向性を一言で言うと何ですか。また、その方向性を機械的に当てはめてはいけないのはどんな場面ですか。

    答えを見る

    手動から自動へ、手続き的から宣言的へ。Declarative Pipelines、Declarative Automation Bundles、Predictive Optimization、CLUSTER BY AUTO など、名前自体に Declarative / Predictive / Auto が現れます。ただしトレードオフを問う設問では手動側が正解になります。典型は VACUUM と Time Travel の関係で、ストレージ削減と過去バージョン参照のどちらを取るかという判断の問題です。
