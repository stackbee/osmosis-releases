Lakehouse 以前の何が問題だったのか製品名としてではなく、困りごとへの回答として覚える

Lakehouse を「新しい製品の名前」として覚えると、試験でも実務でも効きません。 これは特定の困りごとに対する回答として出てきた構成です。 何に困っていたのかを先に押さえると、Delta Lake も Unity Catalog も 「その困りごとのどこを埋める部品なのか」で位置づけられます。

2つの基盤を、両方持っていた

データを扱う基盤には、長いあいだ大きく2種類ありました。

観点データウェアハウス（DWH）データレイク
得意なこと構造化データ。トランザクションが効き、スキーマが決まっていて、BI から使いやすい何でも安く置ける。非構造化データもそのまま。機械学習との相性がよい
苦手なこと非構造化データ、機械学習ワークロード、そしてコスト信頼性。スキーマ管理が甘くなり、更新が難しく、同時書き込みで壊れる
データの持ち方専用フォーマットに取り込む（外に出しにくい）オブジェクトストレージ上のファイルのまま
主な利用者アナリスト / BIデータエンジニア / データサイエンティスト

二重管理が何を壊すか

どちらも一長一短なので、現場は両方持ちました。 生データはデータレイクへ置き、加工したものをデータウェアハウスにも入れる。 同じデータが2か所に存在する状態です。ここから弊害が連鎖します。

  • コストが二重にかかる — 保存料金だけでなく、2つを同期し続けるパイプラインの開発費と運用費が乗る
  • どちらが正しいのか分からなくなる — 数字が合わないとき、レイク側の加工が悪いのか、ウェアハウス側の取り込みが悪いのかを毎回調べることになる
  • 鮮度がずれる — 同期はたいてい日次バッチ。BI が見ている数字は常に「昨日まで」になる
  • ガバナンスが二重になる — 権限設定を2か所に書く。片方だけ直して穴が空く、が典型的な事故
  • 機械学習が DWH のデータを使えない — 取り出すのにまたコピーが要り、3つ目の置き場が生まれる

Lakehouse の主張は単純です。安いオブジェクトストレージを唯一の置き場のままにして、 その上にデータウェアハウスの信頼性を後から載せる。 そうすればコピーそのものが要らなくなる、という発想です。

この節が試験でどう効くか

「なぜ Delta Lake が要るのか」を問う問題は、ほぼこの二重管理の話に還元できます。 データレイクに足りなかったのは信頼性で、それを埋める部品が Delta Lake。 さらに足りなかったのが統制で、それを埋める部品が Unity Catalog。 この対応関係を持っていれば、機能名を丸暗記する必要がありません。

4段の積み上がり問題を読んだら、まずどの層の話かを決める

Lakehouse は「安いストレージの上に、データウェアハウスの信頼性を載せる」という発想です。 実現の仕方は、下から4段の積み上がりとして理解できます。

層構成要素やっていること
4. 計算するComputeSQL Warehouse / Job / All-Purpose / Serverless
3. 統制するUnity Catalog誰が何を見られるか、どこから来たか
2. 信頼できる形にするDelta LakeACID・スキーマ・Time Travel
1. 置くクラウドオブジェクトストレージS3 / ADLS / GCS。安く、いくらでも置ける

この4段は並列ではなく、下に依存しています。 Delta Lake は下のストレージが無ければ何も置けません。 Unity Catalog は、統制する対象が「テーブル」という形になっていて初めて権限を付けられます。 Compute は、その両方が揃って初めて「安全に読み書きする」ことができます。 だから順番に意味があります。置く、信頼できる形にする、統制する、計算する。

層の見分け方

問題文に出てくる言葉から、逆に層をたどれます。

この言葉が出てきたら層理由
ACID / MERGE / Time Travel / VACUUM / OPTIMIZE2. 信頼性（Delta Lake）ファイルの集合を「テーブル」として成立させる話
GRANT / リネージ / 監査ログ / Volume / 3階層の名前3. 統制（Unity Catalog）誰が何をできるか、どこから来たかの話
クラスタ / Warehouse / DBU / 自動停止 / オートスケール4. 計算（Compute）いくら払って、どれだけ回すかの話
S3 / ADLS / GCS / 外部ロケーションのパス1. 置く（オブジェクトストレージ）物理的にどこにバイトがあるかの話

4段の外側に、作業と実行の場所としてワークスペースと Lakeflow があります。 ノートブックで書き、Jobs で回し、Connect で取り込む部分です。 これはデータの階層ではなく「人と処理が触る面」なので、4段には数えません。

この4段が効く場面

問題文を読んで機能名を思い出そうとするのではなく、まず「これは4段のどの層の話か」を決めます。 「同時書き込みで中途半端な状態を見せない」なら信頼性の層＝Delta Lake。 「部署ごとに見えるテーブルを変える」なら統制の層＝Unity Catalog。 「終わったら止めたい」なら計算の層＝Compute。層が決まれば、選択肢はほぼ1つに絞れます。

迷ったときの確かめ方は「その部品が無かったら何が困るか」です。 Delta が無ければ壊れたデータを読むことになる。UC が無ければ全員が全部見えてしまう。 困りごとが言えれば、層は当たっています。

Delta Lake の中身なぜファイル置き場の上でトランザクションが効くのか

実体は Parquet ＋ ログ

Delta テーブルの実体はディレクトリです。中には2種類のものが入っています。

  • Parquet ファイル — データそのもの。特別なものではない、普通の Parquet
  • _delta_log — 連番の JSON。 「今この瞬間、どのファイルの集合がテーブルなのか」を記録している
s3://lake/prod/sales/
  part-00000-a1b2....snappy.parquet
  part-00001-c3d4....snappy.parquet
  part-00002-e5f6....snappy.parquet
  _delta_log/
    00000000000000000000.json      <- コミット 0
    00000000000000000001.json      <- コミット 1
    ...
    00000000000000000010.checkpoint.parquet
    _last_checkpoint

特別なのはログのほうです。ファイルの集合に対して「これが今のテーブルです」という定義を与えています。

ログには何が書かれているのか

各 JSON は「このコミットで何が変わったか」を並べたものです。 中身のアクションを知っておくと、以降の機能がどこから出てきているのかが一気に見えます。

アクション記録している内容これがあると何ができるか
metaDataスキーマ、パーティション列、テーブルプロパティスキーマ強制。形の合わない書き込みを弾ける
add追加されたファイルのパス・サイズ・パーティション値・列ごとの統計（min / max / null 件数 / 行数）データスキップ。WHERE に合わないファイルを開かずに飛ばせる
removeもう使わなくなったファイルのパスと、外した時刻VACUUM の判断材料。Time Travel の復元元でもある
commitInfo操作の種類（WRITE / MERGE / DELETE …）、実行時刻、実行者、影響行数DESCRIBE HISTORY に出てくるのはこれ
protocol読み書きに必要な最低バージョン新機能を使ったテーブルを、古いクライアントが壊さない
txnストリーム書き込みのアプリ ID と処理済みバッチ番号再実行しても二重に書かない（冪等な書き込み）

ここで大事なのは、ログが「変更の記録」であって「テーブルの全体像」ではないことです。 テーブルの現在の姿を知るには、0 番から順にすべてのコミットを積み上げる必要があります。 コミットが数千になると、それだけで重くなります。 そこで Delta は一定数のコミットごとにチェックポイント （そこまでの状態をまとめた Parquet）を書きます。 読み手は直近のチェックポイントと、その後の JSON だけを読めば済みます。

更新は上書きではなく追記

UPDATE / DELETE / MERGE を実行しても、 既存のファイルを書き換えることはありません。新しいファイルを書き、ログで参照を切り替えます。 古いファイルは、ログ上は「もう使わない」扱いになりますが、物理的には残ります。

-- 1行だけ直しても、ファイルは書き換わらない
UPDATE sales SET amount = 1200 WHERE order_id = 'A-0007';

-- 何が起きたかはログに出る
DESCRIBE HISTORY sales;

-- version | operation | operationMetrics
--      11 | UPDATE    | {numRemovedFiles: 1, numAddedFiles: 1, numUpdatedRows: 1}

numRemovedFiles と numAddedFiles が両方 1 になっています。 1行の修正でも、その行を含むファイルを丸ごと読み、直して、新しいファイルとして書き直しているからです。 この方式を copy-on-write と呼びます。 だから小さな更新を大量に打つと、小さなファイルが増えていきます。 この副作用が 最適化 の OPTIMIZE の話につながります。

なぜこの方式か。読んでいる人を壊さないためです。 読み手は読み始めた時点のログを見続けるので、一貫した状態のまま最後まで読めます。 これが Delta における ACID の実現方法です。難しい仕組みで守っているのではなく、書き換えないことで守っています。

楽観的並行制御 — なぜロックを取らないのか

同時に2つの書き込みが来たらどうなるか。Delta は先にロックを取りません。 楽観的並行制御（optimistic concurrency control）という方式で、手順は3つです。

  1. 読む — 開始時点の最新バージョン（たとえば 10）を記録し、その状態を前提に処理する
  2. 書く — 新しい Parquet ファイルを書く。この時点ではまだテーブルは変わっていない
  3. コミットを試みる — 「11 番のログを作る」ことを試す。 誰かが先に 11 を作っていたら、そこで失敗する

失敗したとき、Delta はすぐ諦めずに、相手のコミットを読み直して 本当にぶつかっているかを確かめます。判定はファイル単位です。 相手が触ったファイルと、自分が読んだ・消そうとしたファイルが重なっていなければ、 番号を 12 に振り直して自動で通ります。重なっていれば例外になり、処理からやり直します。

ここから実務上の性質が出ます。追記どうしはほとんどぶつかりません。 触るパーティションが違えばぶつかりません。 ぶつかるのは、同じ範囲を同時に更新・削除したときです。 「同時書き込みで衝突する」という問題を見たら、 まず2つの書き込みが同じファイル群を触っているかを考えます。 解き方は、書き込みを時間でずらすか、パーティションで分けるか、どちらかになります。

Time Travel

ログには全バージョンが残っています。過去のログを読めば、その時点のテーブルが再現できます。 特別な機能を後付けしたのではなく、この構造から自然に出てくるものです。

SELECT * FROM sales VERSION AS OF 10;
SELECT * FROM sales TIMESTAMP AS OF '2026-07-01';
DESCRIBE HISTORY sales;

-- 巻き戻しは SELECT ではなく RESTORE
RESTORE TABLE sales TO VERSION AS OF 10;

RESTORE は過去を上書きで戻すのではなく、 過去の状態を新しいバージョンとして追記します。 つまり「バージョン 12 で、10 の内容に戻した」という履歴が残ります。だから復元そのものも巻き戻せます。

どこまで遡れるのか — 2つの保持期間

Time Travel は無条件ではありません。遡れる範囲は、性格の違う2つの設定で決まります。

プロパティ既定何を保持するか切れると何が起きるか
delta.logRetentionDuration30日_delta_log のコミット記録そのバージョンが履歴に出てこなくなる
delta.deletedFileRetentionDuration7日参照されなくなった Parquet ファイルの実体VACUUM の削除対象になり、消えれば復元できない
ALTER TABLE sales SET TBLPROPERTIES (
  'delta.logRetentionDuration'         = 'interval 90 days',
  'delta.deletedFileRetentionDuration' = 'interval 30 days'
);

VACUUM sales;                   -- 既定は 7 日より古い不要ファイルを削除
VACUUM sales RETAIN 720 HOURS;  -- 30 日ぶんは残す
VACUUM sales DRY RUN;           -- 何が消えるかを確認するだけ（削除しない）

実務でも試験でも効くのは、短いほうが先に効くという点です。 ログを90日に伸ばしても、データファイルが7日で消えていれば、8日前のバージョンは 「履歴には見えるのに SELECT するとエラー」という状態になります。 Time Travel を長く使いたいなら、両方を伸ばす必要があります。

ここが試験で効く

ログが残っていても、ログが指すファイルが消えれば復元できません。 VACUUM は、参照されなくなったファイルを物理削除します。 「ストレージ使用量を削減したい。ただし Time Travel は今後も利用したい」という条件が付いているときに、 素の VACUUM を選ぶと誤答になります。

そして DELETE してもストレージは減りません。 新しいファイルを書いてログを切り替えるだけだからです。減らすのは VACUUM。 この2段構えを理解していないと、最適化の章で必ず詰まります。

Delta と素の Parquet の違いデータは同じ。違うのは、その周りに何があるか

「Delta って結局 Parquet でしょう」と言われることがあります。半分正しく、半分違います。 データファイルは本当にただの Parquet です。違いはその周りに何があるかだけ。 ただ、その差でできることが大きく変わります。

やりたいこと素の Parquet（ディレクトリを直接読む）Delta
特定行の UPDATE / DELETE不可。自分で読み直して全体を書き直すUPDATE / DELETE / MERGE が使える
書き込み中の読み取り書きかけのファイルが見える。壊れた結果になりうるコミット済みのバージョンだけが見える
スキーマの強制無い。列が増減したファイルが混ざっても気づけないスキーマ強制。mergeSchema で明示的に進化させる
過去に戻る不可。自分でコピーを取っていた場合のみVERSION AS OF / RESTORE
どのファイルがテーブルかディレクトリ一覧を取る。ファイルが多いほど遅いログに書いてある。一覧を取らなくてよい
要らないファイルを飛ばすパーティションのディレクトリ名まで列統計によるデータスキップ、Liquid Clustering
ストリーミングの取り込み先追記のみ。重複排除は自分で作るテーブルをそのままソースにもシンクにもできる
誰がいつ何をしたか残らないDESCRIBE HISTORY

逆に、Delta にしても変わらないことも押さえておきます。 列指向であることも、圧縮方式も、Parquet のままです。 だから読み取り性能そのものが魔法のように上がるわけではありません。 速くなるのは「読まなくていいファイルを開かずに済む」からで、 1ファイルを読む速さが変わるからではありません。

既存の Parquet を Delta にするのは、データを書き直さずにできます。ログを作るだけだからです。

CONVERT TO DELTA parquet.`s3://lake/raw/sales`;

-- ディレクトリでパーティション分けされているなら、列と型を伝える
CONVERT TO DELTA parquet.`s3://lake/raw/sales`
  PARTITIONED BY (dt DATE);

-- 逆方向（Delta を素の Parquet として読ませたい）は変換ではなく書き出しになる
CREATE TABLE archive_sales USING PARQUET AS SELECT * FROM sales;

「Delta にしたらストレージが増えた」の正体

変換した直後は増えません。増えるのは更新を始めてからです。 copy-on-write なので、更新のたびに新しいファイルが増え、古いファイルは保持期間のあいだ残ります。 これは不具合ではなく仕様で、その代わりに Time Travel とロールバックが手に入っています。 「保持している期間ぶんの容量」と「戻せる安心」を交換している、と理解してください。

Unity Catalog の3階層住所の形が、そのまま権限の形になる

テーブルは prod.sales.orders の形で指定します。 カタログ・スキーマ・テーブルの3階層です。

階層例備考
Metastore—リージョンに1つが基本。3階層の外側で、名前空間には書かない
Catalogprod環境で分けることが多い（dev / staging / prod）
Schemasales業務領域で分けることが多い
Table 他orderstable / view / volume / function / model

よくある取り違え

「3階層」を metastore → catalog → schema と数えてしまうパターンです。 正しくは catalog / schema / object。名前空間として実際に書くのがこの3つだからです。 metastore は数えません。

ワークスペースは階層ではない

ワークスペースはデータの階層ではなく、作業する場所です。 1つの metastore を複数ワークスペースが共有していれば、 どこからでも同じ prod.sales.orders を参照できます。 「ワークスペースが違えばデータも別」ではありません。画面が別なので別物に見えるだけです。

裏を返すと、metastore がリージョンに1つという性質から、 「別リージョンのワークスペースから同じテーブルを使いたい」は単純な共有では解けない、 という含みも出ます。ここは ガバナンス で扱います。

スキーマの下に置けるもの

スキーマの下はテーブルだけではありません。 Unity Catalog が「データの入れ物」ではなく資産の名簿である、という性格がここに出ます。

オブジェクト何か使いどころ・押さえどころ
Table（managed）UC が実体の置き場まで管理するテーブル基本はこちら。DROP するとデータも消える
Table（external）実体は指定した外部パス。UC は登録だけを持つ既存のデータ資産をそのまま登録したいとき。DROP してもファイルは残る
Viewクエリに名前を付けたもの。実体を持たない列や行を絞って見せる。権限の境界としても使える
Materialized Viewクエリ結果を実体として保持し、更新できるもの重い集計を何度も見るとき。鮮度と引き換えに速さを取る
Volumeテーブルにならないファイルの置き場PDF・画像・生ログ・取り込み前の CSV。managed / external の別がある
Functionユーザー定義関数（UDF）共通の計算ロジックを1か所に置く。関数にも EXECUTE 権限が付く
Model登録された機械学習モデル学習済みモデルもテーブルと同じ住所と権限の仕組みで扱える

この一覧が意味しているのは、「UC の外に置かれるものを減らす」という方針です。 モデルだけ別のレジストリ、ファイルだけ生の s3:// パス、という状態だと、 権限もリネージもそこで途切れます。同じ名簿に載せることで、統制が1か所で完結します。

Volume — テーブルにならないものの置き場

PDF・画像・生ログのように表の形にならないデータを、Unity Catalog の管理下に置くための場所です。 「非構造化ファイルを UC 配下に置きたい」→ Volume、と引けるようにしておきます。

CREATE VOLUME prod.sales.raw_files;

-- 参照するパスは /Volumes/<catalog>/<schema>/<volume>/... の形になる
LIST '/Volumes/prod/sales/raw_files/2026/07/';

COPY INTO prod.sales.orders_bronze
FROM '/Volumes/prod/sales/raw_files/2026/07/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true');

覚えておくと得なのはパスの形です。 /Volumes/ で始まる3階層のパスは、それだけで「UC の管理下にあるファイル」を意味します。 問題文に生の s3:// が出ていたら UC の外、 /Volumes/ なら中、と読み分けられます。

住所の形が権限の形になる

テーブルを読むには、テーブルの SELECT だけでは足りません。 上の階層を通り抜ける権限も要ります。

GRANT USE CATALOG ON CATALOG prod            TO `analysts`;
GRANT USE SCHEMA  ON SCHEMA  prod.sales      TO `analysts`;
GRANT SELECT      ON TABLE   prod.sales.orders TO `analysts`;

-- 付いている権限を確かめる
SHOW GRANTS ON TABLE prod.sales.orders;

USE CATALOG → USE SCHEMA → SELECT。 部屋の鍵をもらっても、エントランスと廊下を通れなければ部屋にたどり着けません。 「SELECT を付与したのに読めない」は、ほぼこれです。 公式のサンプル問題にも「アナリストグループはすでに USE CATALOG と USE SCHEMA を持っているものとする」という但し書きが出てきます。 わざわざ書いてあるということは、この階層構造を分かっているかを試している、ということです。 詳細は ガバナンスで扱います。

棚卸しは information_schema から

各カタログには information_schema が自動で用意されます。 何がどこにあるかを、SQL でそのまま問い合わせられます。

SELECT table_schema, table_name, table_type
FROM   prod.information_schema.tables
WHERE  table_schema = 'sales'
ORDER  BY table_name;

SELECT grantee, privilege_type, table_name
FROM   prod.information_schema.table_privileges
WHERE  table_schema = 'sales';

コンピュートの選び方判別の軸は「誰が使うか」と「いつ止まるか」の2つだけ

試験ガイドは select the most suitable option for each workload use case と書いています。 種類を知っているかではなく、選べるかが問われます。

種類誰が使うかいつ止まるか典型的な用途
All-Purpose人が対話的に明示的に止めるまでノートブックでの開発・探索
Job機械が自動でジョブ終了とともに本番バッチ・定期実行
SQL WarehouseSQL / BI から自動停止の設定ありダッシュボード・SQL 分析
Serverless（提供形態）Databricks が管理運用を手放したいとき

アクセスモード — 「誰として実行されるか」

クラスタを作るときに、もう1つ決めるものがあります。アクセスモードです。 これは性能の設定ではなく、そのクラスタが誰の権限で動き、Unity Catalog の統制が効くかの設定です。

アクセスモード誰が使えるか性格
標準（Standard / 旧 Shared）複数ユーザーで共有ユーザーごとに実行が分離され、UC の権限がそのまま効く。既定はこちら
専用（Dedicated / 旧 Single user）1人（または1グループ）指定した主体の権限で動く。共有クラスタでは制限される一部の機能を使いたいときに
分離なし共有（No Isolation Shared）複数ユーザーだが分離されない旧来の形。UC 非対応。新規に選ぶ理由はない

問題文に「複数のアナリストが同じクラスタを使うが、見られるテーブルは人によって違う」とあれば、 答えの方向は Unity Catalog ＋ 標準アクセスモードです。 分離されないモードでは全員が同じ資格情報で動いてしまうため、この要件は満たせません。

台数の決め方 — オートスケールとインスタンスプール

  • オートスケール — ワーカー数に下限と上限を決めておくと、待っているタスクの量に応じて Databricks が増減させます。 効くのは負荷が波打つワークロードです。 一定量を流し続けるジョブでは、増減の判断そのものが無駄になることもあります。
  • 自動停止（auto termination） — 一定時間アイドルなら落とす設定。All-Purpose の請求を止める最大の手段がこれです。 SQL Warehouse も同じ考え方の設定を持ちます。
  • インスタンスプール — 起動済みの VM をあらかじめ待機させておく仕組みです。クラスタはプールから VM を取るので 起動が速い。待機中の VM にはクラウドの VM 料金がかかりますが、 Databricks の DBU はかかりません（仕事をしていないため）。 「起動時間を短縮したい」＝プール、と引けるようにしておきます。

コストの構造 — DBU とは何か

試験は金額を聞きません。「なぜ安くなるのか」の理屈を聞きます。 そのために、請求が2本立てであることだけ押さえます。

請求の相手何に対して払うか効く操作
クラウド事業者実際に動いている VM・ディスク・通信台数を減らす、止める、適したインスタンスを選ぶ
DatabricksDBU（処理能力 × 時間を表す単位）止める、単価の安いコンピュート種別で動かす

DBU は「1時間いくら」という金額そのものではなく、 使った処理能力の量を表す単位です。 同じ 1 DBU でも、All-Purpose・Job・SQL Warehouse で単価が違います。 つまり同じ仕事をしても、どの入れ物で動かすかで請求が変わる。ここが本質です。

典型的な高コストパターンは、本番の定期ジョブを All-Purpose で回すことです。 単価が高く、処理が終わっても動き続け、誰も使っていない時間も課金されます。 夜中に5分だけ動く処理のために、24時間ぶんを払っている形です。 Job Compute なら、動いている時間がそのまま仕事をしている時間になります。

覚え方

All-Purpose は「人間用」、Job は「機械用」。 そして「コストを抑えたい」＋「自動実行」の組み合わせを見たら、まず Job Compute を疑う。

Serverless の位置づけ

ガイドの objective は Use serverless for a hands-off, auto-optimized compute managed by Databricks。問題文に hands-off・自動最適化・運用負荷を下げたいとあれば合図です。 「インスタンス種別を選ぶ手間をなくしたい」「起動待ちを減らしたい」も同じ合図になります。

Serverless は Job や SQL Warehouse の置き換えではなく、それぞれに Serverless という提供形態があります。 対立軸は「Job か Serverless か」ではなく、「自分で管理するか、任せるか」です。 VM の管理が Databricks 側に移るため、さきほどの2本立ての請求が利用者から見て実質1本になります。

よくある思い込み実際はどうかなぜそう思ってしまうか
Delta Lake は Databricks 独自のファイル形式データは普通の Parquet。Delta はその上に載るログの取り決め「独自形式」という語感で決めてしまう

確認問題答えより、答えの理由が言えるかを確かめる

ここまでの内容を、問題文の形で確かめます。 選択肢を当てるのではなく、なぜそうなるのかを声に出して言えるかで判定してください。

  • Q1Delta テーブルの _delta_log に記録されていないものはどれか。(a) 追加ファイルの列ごとの統計 / (b) 操作の種類と実行時刻 / (c) テーブルのスキーマ / (d) 実際の行データ

    答えを見る

    (d)。行データは Parquet 側にあります。ログが持つのは「どのファイルの集合がテーブルか」と、その付随情報（metaData のスキーマ、add の統計、commitInfo の操作履歴）だけです。この分担が分かっていると、Time Travel も VACUUM も同じ話の続きとして読めます。

  • Q2DELETE FROM sales WHERE order_date < '2025-01-01' を実行したが、ストレージ使用量が変わらない。理由と対処は。

    答えを見る

    Delta は既存ファイルを書き換えず、新しいファイルを書いてログを切り替えることで削除を表現します。旧ファイルは物理的に残るので容量は減りません。減らすには VACUUM が別に必要です。ただし VACUUM は Time Travel で遡れる範囲を削ります。

  • Q3「ストレージを削減したい。ただし直近30日ぶんの Time Travel は維持したい」。単に VACUUM sales; を実行してよいか。

    答えを見る

    いけません。既定の保持は7日なので、8〜30日前のバージョンが復元できなくなります。VACUUM sales RETAIN 720 HOURS; のように保持を明示し、あわせて delta.deletedFileRetentionDuration を 30 日に設定します。delta.logRetentionDuration も 30 日以上である必要があります（短いほうが先に効く）。

  • Q42つのジョブが同じ Delta テーブルに同時に書き込む。どんなときに片方が失敗し、どんなときは失敗しないか。

    答えを見る

    Delta は楽観的並行制御です。ロックは取らず、コミットしようとした時点で衝突を検出します。判定はファイル単位で、相手が触ったファイルと自分が読んだ・消そうとしたファイルが重ならなければ、コミット番号を振り直して自動的に通ります。追記どうし、あるいは別パーティションへの書き込みはほぼ衝突しません。衝突するのは、同じ範囲を同時に更新・削除したときです。

  • Q5PDF の請求書を Unity Catalog の管理下に置き、部署ごとに閲覧を制御したい。何を使うか。

    答えを見る

    Volume。テーブルにならないファイルの置き場で、/Volumes/<catalog>/<schema>/<volume>/… のパスで参照します。テーブルではありませんが、権限は他の UC オブジェクトと同じ仕組みで付けられます。生の s3:// パスに置くと、そこで統制が途切れます。

  • Q6GRANT SELECT ON TABLE prod.sales.orders TO `analysts` を実行したのに、analysts のメンバーが読めない。何が足りないか。

    答えを見る

    上位階層を通り抜ける権限です。GRANT USE CATALOG ON CATALOG prod と GRANT USE SCHEMA ON SCHEMA prod.sales が要ります。住所の形（catalog / schema / object）が、そのまま権限の形になっています。

  • Q7毎晩2時に起動し、約20分で終わる本番 ETL。コストを最小にしたい。どのコンピュートか。

    答えを見る

    Job Compute（運用も手放したいなら Serverless の Job）。All-Purpose は単価が高いうえ明示的に止めるまで動き続けるため、20分の仕事のために24時間ぶんを払うことになります。Job Compute はジョブの終了とともに停止するので、動いている時間＝仕事をしている時間になります。

  • Q8複数のアナリストが1つのクラスタを共有するが、見えるテーブルは人によって変えたい。

    答えを見る

    Unity Catalog ＋ 標準（Standard／旧 Shared）アクセスモード。このモードはユーザーごとに実行が分離され、UC の権限がそのまま効きます。分離なし共有（No Isolation Shared）は全員が同じ資格情報で動くため、この要件を満たせません。

全部答えられたら、この土台は十分です。 詰まったものがあれば、そのセクションだけ読み直してください。 とくに Delta Lake の中身 と Unity Catalog の3階層 は、 最適化とガバナンスで そのまま前提として使われます。
