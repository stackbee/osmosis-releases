DatabricksのCI/CDとDev・Staging・Prod

Databricks でも、コードや Job / Pipeline の設定を Git で管理し、テストしてから複数環境へデプロイします。 この回の軸は2つ。環境をどう分けるか、そしてそのあいだをどう進めるかです。

なぜ環境を分けるのか出発点

本番 Job を直接編集すると、設定ミスや未検証コードがそのまま本番データへ影響します。 編集した本人には影響が見えず、気づくのは利用者が誤った数字を見たあとになります。

やること
コードと Job / Pipeline 設定を Git で管理し、テストしてから複数環境へデプロイする
避けたいこと
本番 Job の直接編集。設定ミスと未検証コードが、そのまま本番データに出る
言い換えると
環境を分けるとは、失敗できる場所を用意すること

昇格で変わるもの、変わらないものここが要点

環境ごとのデプロイ手段としては Declarative Automation Bundles があります。 Bundles では同じコード・リソース定義に対して target を切り替えられ、同じプロジェクトを環境ごとに異なる設定でデプロイできます。 Bundle 自体の構造は第17回の担当なので、ここでは扱いません。

典型的な進め方検査が前、承認が後ろ

 
1. 開発者がコード変更        5. Staging へ deploy
2. Pull Request             6. Integration Test
3. Unit Test                7. 承認
4. databricks bundle validate  8. Production へ deploy

8つ並んでいますが、覚えるのは並びそのものではありません。 検査（3・4）が前に、承認（7）が後ろに置かれているという形です。

人のレビューを機械の代わりに使わない

機械で分かる誤りは Unit Test と bundle validate で落とします。 機械では判断できないものだけを、人が承認します。この順にしておくと、承認者は毎回同じ種類の判断だけをすればよくなります。

Git Folder との違い何をどこまで管理するか
Git FolderBundle
管理する範囲主にコードを Git 管理コード＋ Job / Pipeline などリソース設定まで
具体的にはNotebook、Python ファイルなどのソースコードを Git と同期Job の Task 構成・Schedule・Pipeline 設定まで含めて再現
環境の出し分けできない。スケジュールや通知先は環境ごとに手作業のまま残るtarget ごとに値を上書きして配る

Git Folder は、Notebook や Python ファイルなどのソースコードを Git と同期するために便利です。 一方で、Job の Task 構成・Schedule・Pipeline 設定などまで含めて再現性高く管理したいなら Bundles が向いています。 環境を分けるという話では、この差がそのまま効きます。

Git-backed Job の感覚層が違う

Job の実行時にリモート Git リポジトリの特定バージョンを使う構成もあります。 ただし「コードのバージョン管理」と「Job 自体の設定を IaC として管理すること」は別です。

売上の処理を本番へ出すまで具体例

 
feature/sales-fix → PR → pytest → bundle validate
  → Dev deploy → Staging でテスト → main merge → Prod deploy

注目してほしいのは、main merge の位置です。 テストと Staging での検証が先にあり、マージはそのあとに来ています。 main が本番への入口になっているので、そこへ入れる前に検証を終えているという並びです。

試験ではどう問われるかDEA 試験ポイント
問題文にこう書いてあったら答えの方向
複数環境へ一貫してデプロイ / Job 設定も含めて Git 管理 / CI/CDBundles が中心
Notebook コードだけを Git と同期したいGit Folder のような選択肢も考える
覚え方

Git = 変更履歴／CI = 変更を検査／CD = 検査済み変更を環境へ届ける／ Bundle = Databricks 側のコードと設定を再現可能に梱包。

環境のほうは一言で足ります。Dev は壊してよい場所、Staging は本番に近い場所、Prod は通ったものしか入らない場所。
