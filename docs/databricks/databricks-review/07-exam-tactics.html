誤答は6種類しかない選択肢を見た瞬間に「これはどの型か」で切る

公式サンプル問題を分解し、各ドメインで出てくる誤答を集めていくと、 作られ方が6つの型に収まります。無限にあるわけではありません。 型を知っていれば、選択肢の中身を完全に知らなくても 「これは型③だから切る」という判断ができます。

型中身代表例
① 条件を1つ外す2条件のうち片方だけ満たす「削減したい＋Time Travel も維持」に対して、単に VACUUM する選択肢
② 広すぎる目的に対して過剰読み取り専用が欲しいのに GRANT ALL PRIVILEGES
③ 守備範囲を外すその機能がやらないことを主張「Expectations で検索を速くする」「VACUUM で検索を速くする」
④ 存在しない構文それらしいが実在しないCREATE OR REPLACE TABLE t WITH COLUMNS (...)
⑤ 語順・単語が1つ違う構文としては近いINSERT VALUES (...) INTO my_table
⑥ ボトルネックが違う増強すれば直る、と誘う「検出が遅い → クラスタを大きくする」

型ごとの実例 — 2〜3個ずつ持っておく

型は名前を覚えても切れません。実例を2〜3個ずつ引き出せる状態にしておくと、 本番で「あ、あれと同じ形だ」と気づけます。

型問題文の形混ざる誤答と、なぜ切れるか
①削減したい ＋ Time Travel も維持「保持期間を最短にして VACUUM」は前半だけ。RETAIN で必要な期間を確保して VACUUM が正解
①止めたくない ＋ データも失いたくないDROP ROW は止まらないが行が消える。addNewColumns は残るが止まる。両立するのは rescue
①存在に関係なく ＋ その形にしたいIF NOT EXISTS は「関係なく」を満たさない。CREATE OR REPLACE TABLE
①値を伏せたい ＋ 件数は見せてよいrow filter は行ごと消えるので件数が変わる。column mask が正解
②グループに読み取り専用を与えたいGRANT ALL PRIVILEGES は「できる」が「適切ではない」。GRANT SELECT
②3番目のタスクだけ失敗。やり直しを最小に「全体を再実行」は成功済みまで巻き込む過剰対応。repair run
②特定の列だけ分析チームに伏せたい「テーブルを分ける」は作り替えが過剰。列単位の制御で足りる
③小さなファイルが大量にある「VACUUM する」は削除の機能で、統合はしない。OPTIMIZE
③ストレージ使用量を減らしたい「OPTIMIZE する」は統合であって容量は減らない
③列を削除する前に影響範囲を知りたいaudit log はヒトの操作の記録。モノを追うのは lineage
③NULL 行をテーブルに入れたくない「Expectations を書けば自動で除外される」は守備範囲外。DROP ROW の明示が要る
④空のテーブルを作る DDLWITH COLUMNS は実在しない句（公式サンプル問題の選択肢D）
⑤1行を追加する DMLINSERT VALUES ... INTO は INTO の位置違い。UPDATE ... VALUES は形は整うが追加しない
⑤ユニークな請求書数を数えるcount_distinct(patient_id) は列が1つ違う。sum(billing_id) は ID を合計している
⑤常時起動させず日次で回したいtrigger(processingTime="1 day") は起動したまま。trigger(availableNow=True) が正解

④⑤ は「見慣れない句を疑う」で切れる

公式サンプル問題から、実際に出た偽物を並べます。 いずれも USING DELTA や CREATE OR REPLACE といった 本物の部品が混ざっているため、それらしく見えます。

-- ④ 存在しない構文（WITH COLUMNS という句は無い）
CREATE OR REPLACE TABLE my_table WITH COLUMNS (id STRING, qty INT) USING DELTA;

-- ⑤ 語順が1つ違う（INTO の位置）
INSERT VALUES ('a1', 6, 9.4) INTO my_table;

-- ⑤ 形は整っているが、UPDATE は行を追加しない
UPDATE my_table VALUES ('a1', 6, 9.4);

Associate レベルで、見たこともない構文が正解になることはまずありません。 「知らないだけかもしれない」と思わせるのがこの型の狙いです。見慣れないものは、たいてい偽物です。

最頻出は ⑥

「遅い → もっと大きく／もっと多く」という誘導です。この試験で最も繰り返し出てきます。 計算資源を足して直る問題は、意外と少ないと覚えておいてください。

症状誘われる誤答実際の原因
ファイル検出が遅いクラスタ増強探し方の問題（file notification）
JDBC が遅いクラスタ増強並列化されていない（partitionColumn）
MERGE が遅いクラスタ増強 / VACUUM探索範囲（Liquid Clustering）
特定の列での絞り込みが遅いパーティションをその列で切る高カーディナリティ列で切ると小さなファイルが大量に生まれる
skew で1タスクだけ遅いノード追加1タスクが重い。並列度は無関係
collect() で OOMエグゼキュータ増強ドライバ側の問題。集める量を減らす
Shuffle Read/Write が巨大メモリ増強結合の仕方の問題（broadcast join で回避）
クエリが遅く、小さいファイルが多いクラスタ増強開くファイル数の問題（OPTIMIZE）

共通する対策は「まず測る → 原因に合った手を打つ → 測り直す」。 ガイドが re-measure the performance と書いている意味がここにあります。 測る場所は run history と Spark UI です。

問題文の読み方読み落としは知識では防げない。手順で防ぐ

選択肢を切る前に、問題文から条件を全部拾えているかが先です。 落とす問題の多くは「知らなかった」ではなく「書いてあったのに読まなかった」です。 これは知識では防げません。毎回同じ手順を踏むことで防ぎます。

毎回この5つを確認する

#チェック探す言葉ここで分かれるもの
1条件はいくつあるか「ただし」「かつ」「〜も」「同時に」2条件なら、両方満たす選択肢を探す（型①の対策）
2誰が使うのか「データサイエンティストが」「毎晩」「本番 ETL」All-Purpose か Job Compute か
3規模はどれくらいか「数千」「数百万」「日次で数十件」COPY INTO か Auto Loader か／directory listing か file notification か
4直前に何をしたか「結合したら」「展開したら」「DELETE したのに」同じ症状でも原因が変わる（下の callout）
5何を優先するのか「コストを抑えたい」「保守負荷を下げたい」「概数でよい」Job Compute ／ managed connector ／ approx_count_distinct

同じ症状で原因が複数ある例：「行が減った」

  • inner join — マスタに無い行が落ちた → left にする
  • explode — 配列が空 / NULL の行が落ちた → explode_outer
  • row filter — 権限で見えていない → 仕様。設定を確認

症状ではなく「その直前に何をしたか」で切り分けます。 結合した後なら join、展開した後なら explode、 何も処理していないのに減っているなら権限。 問題文には必ず文脈が書いてあります。

同じ症状で原因が分かれる、その他のパターン

症状直前の文脈見るべきところ
件数が想定と合わない結合した / 展開した / 何もしていないjoin の種類 ／ explode_outer ／ row filter
容量が減らないDELETE した / OPTIMIZE したどちらも物理削除ではない。VACUUM が要る
ストリームが止まった上流に列が増えた / チェックポイントを消したaddNewColumns の仕様 ／ 進捗が消えて全件再処理
読めないと言われたGRANT SELECT を出した直後USE CATALOG / USE SCHEMA の不足
MERGE が失敗するsource を作り直した直後source 側のキー重複

「異常」と「仕様」を取り違えない

新しい列が来てストリームが止まるのは、Auto Loader の既定 addNewColumns の仕様です。 DELETE で容量が減らないのも Delta の仕様です。 これを「異常だ」と判断すると、クラスタやコードを調べ始めて時間を失います。 選択肢に「異常。設定ミス」が混ざっていたら、まず仕様側を疑ってください。

間違いの3分類と戻り先「間違えたから復習する」ではなく、種類を判定してから戻る

間違えた問題を見て、解説を読んで、「なるほど」と思って終わる。 これでは次も同じところで間違えます。なぜ間違えたかを特定していないからです。 間違いには3種類あり、対処がまったく違います。

間違いの種類中身対処戻り先
① 知らなかったそもそもその機能を知らなかった機能の説明から読み直す該当ドメインのページ
② 取り違えた知っていたが、似た機能と混同した判別の節に戻る下の対応表
③ 読み落とした知識はあったが、条件を見落とした知識では防げない。読み方の手順を変える問題文の読み方

たとえば③の読み落としだったのに機能の説明を読み直しても、意味がありません。 知識は既にあったのですから。必要なのは問題文の読み方を変えることです。

腕試し 12問模試45問から、型の代表を1問ずつ

7つのドメインから、誤答の型がはっきり出ている12問を選びました。 答えを開く前に、①正解、②他の3つがなぜ誤りか、③その誤答は6型のどれか、 の3つを言ってみてください。②③まで言えたら、その論点は本番でも落ちません。

  • Q1【S1】 Unity Catalog で prod.sales.orders と参照するとき、「3階層」にあたるのは？
    A. metastore / catalog / schema　B. workspace / catalog / table　C. metastore / schema / table　D. catalog / schema / table

    答えを見る

    D。参照名に現れる3つが、そのまま3階層です。metastore は3階層の外側で、数えません。A を選びやすいのは「metastore が一番上にあるから」ですが、これは単語が1つ違う型⑤です。この住所の形は、そのまま権限の形（USE CATALOG / USE SCHEMA）にもなります。→ Unity Catalog の3階層

  • Q2【S2】 取り込みを止めたくない。かつ、スキーマに合わないデータも失いたくない。
    A. failOnNewColumns　B. rescue（_rescued_data）　C. none　D. addNewColumns

    答えを見る

    B。条件が2つあります。「止めたくない」と「失いたくない」。A は止まる、D も新しい列でいったん止まる、C は合わない値が落ちる。両方を満たすのは rescue で、外れた値は _rescued_data 列に残ります。典型的な型①です。→ Auto Loader

  • Q3【S2】 ランディング領域に数百万ファイルがあり、ディレクトリ一覧に時間がかかる。到着から処理までを短くしたい。
    A. directory listing のまま　B. クラスタを大きくする　C. COPY INTO に変える　D. file notification

    答えを見る

    D。「一覧に時間がかかる」のは探し方の問題なので、計算資源を足しても直りません。B が最頻出の型⑥です。C は数千規模向けで、数百万ファイルでは逆行します。→ ファイル検出方式

  • Q4【S3・公式サンプル問題】 テーブルが既に存在するかどうかに関係なく、指定した形の空テーブルを作りたい。
    A. CREATE TABLE IF NOT EXISTS t (...)　B. CREATE TABLE t AS SELECT ...
    C. CREATE OR REPLACE TABLE t (...)　D. CREATE OR REPLACE TABLE t WITH COLUMNS (...)

    答えを見る

    C。決め手は「関係なく」の一語です。A は既存があると作り直さないので「関係なく」を満たしません（型①）。B は CTAS なので SELECT の結果が入り、空になりません。D の WITH COLUMNS は実在しない句（型④）。→ DDL / DML — 公式サンプル問題

  • Q5【S3・公式サンプル問題】 日ごとの請求額合計と、ユニークな請求書数を集計する。正しいのは？
    A. sum(amount), sum(billing_id)　B. sum(amount), count_distinct(patient_id)
    C. sum(amount), count_distinct(billing_id)　D. col(amount), count(billing_id)

    答えを見る

    C。「ユニークな」は count_distinct。最も紛らわしいのが B で、関数は合っていますが列が違います（患者数であって請求書数ではない）。これが型⑤です。A は ID を合計しており意味がありません。D は集計関数になっていません。→ PySpark の要点

  • Q6【S3】 Declarative Pipelines の Expectations で ON VIOLATION を指定しなかった。違反行はどうなるか？
    A. 削除される　B. パイプラインが失敗する　C. NULL に置換される　D. テーブルに入る（件数が記録される）

    答えを見る

    D。既定は記録するだけで、行は残ります。A を選んでしまうのは「品質ルールに違反したのだから除外されるはず」という思い込みで、これは Expectations の守備範囲を広く見積もる型③の裏返しです。除外したいなら DROP ROW、止めたいなら FAIL UPDATE を明示します。→ Declarative Pipelines と Expectations

  • Q7【S4】 Declarative Pipeline を毎晩スケジュール実行したい。必要なものは？
    A. パイプライン単体で設定できる　B. cron を書いたノートブック　C. Lakeflow Jobs の Pipeline タスク　D. SQL Warehouse

    答えを見る

    C。Declarative Pipelines は単体ではスケジュールできません。「宣言的に書ける＝実行まで面倒を見てくれる」と思い込むと A を選びます（型③）。定期実行は Jobs の役割で、Pipeline タスクとして呼び出します。→ タスクの種類

  • Q8【S5】 複数の開発者が同じバンドルを触る。互いのデプロイが衝突しないようにしたい。
    A. mode: production　B. 全員が同じ target を使う　C. mode: development　D. デプロイを1人に限定

    答えを見る

    C。development ではリソース名にユーザー名が付くので、同じバンドルを配っても衝突しません。あわせてスケジュールが停止されるため、dev のジョブが勝手に走ることもありません。D は運用でカバーする発想で、仕組みで解決できるのに人を縛る型②寄りの選択です。→ Automation Bundles

  • Q9【S6】 ストレージ使用量を削減したい。ただし Time Travel は今後も利用したい。
    A. 保持期間を最短にして VACUUM　B. OPTIMIZE を実行
    C. 必要な期間を RETAIN して VACUUM　D. テーブルを作り直す

    答えを見る

    C。この試験で最も典型的な2条件問題です。A は「削減したい」だけを満たし、Time Travel で戻れる範囲を捨てています（型①）。B は小さなファイルの統合であって容量は減りません（型③）。「ただし」が出てきたら条件は2つ、と数える練習に最適な問題です。→ VACUUM と Time Travel

  • Q10【S6】 巨大テーブルで customer_id による絞り込みと MERGE が遅い。新ガイドが示す方向は？
    A. パーティションを customer_id で切る　B. VACUUM　C. メモリ増強　D. Liquid Clustering

    答えを見る

    D。旧教材なら ZORDER BY が答えになっていた場所ですが、新ガイドに ZORDER の記載はありません。A は高カーディナリティ列でのパーティションで、小さなファイルが大量に生まれて破綻します。B は削除の機能で無関係（型③）、C は型⑥。→ Liquid Clustering ／ ZORDER BY の立ち位置

  • Q11【S7・公式サンプル問題】 analyst グループに sales_data スキーマの読み取り専用アクセスを与える（USE CATALOG / USE SCHEMA は付与済み）。
    A. GRANT ALL PRIVILEGES ON SCHEMA sales_data TO analysts
    B. GRANT INSERT ON SCHEMA sales_data TO analysts
    C. GRANT SELECT ON SCHEMA sales_data TO analysts
    D. GRANT MODIFY ON SCHEMA sales_data TO analysts

    答えを見る

    C。A は読めるようにはなりますが、書き込みも削除もできてしまう型②（広すぎる）の代表例です。「できる」と「適切である」は違います。B と D は書き込み系で、読み取り専用になりません。→ GRANT / REVOKE / DENY

  • Q12【S7】 分析チームにはメールアドレスを伏せたい。ただし件数は見せてよい。
    A. row filter　B. column mask　C. REVOKE SELECT　D. テーブルを分ける

    答えを見る

    B。分ける一文は「件数は見せてよいか」です。A の row filter は行ごと消えるので件数が変わってしまい、後半の条件を落とします（型①）。C は何も見えなくなり、D は運用が増える過剰な作り替え（型②）。→ 行フィルタと列マスク

ステップ4 — 2周目の解き方

同じ模試をもう一度解くとき、答えを覚えてしまっているのは避けられません。 だから、解き方のほうを変えます。

  1. 他の3つがなぜ誤りかを言う — 正解が分かっていても「A はなぜ違うのか」を説明する
  2. 誤答が6型のどれかを判定する — 条件を1つ外している型か、守備範囲を外している型か
  3. 問題文を自分で言い換えてみる — これがいちばん効きます

3つ目が効く理由は単純で、本番は同じ意味を違う言葉で聞いてくるからです。 模試とまったく同じ表現は出てきません。言い換えの練習として、下の対応を作ってみてください。
