Unity Catalog の階層構造

Unity Catalog は、Databricks 上のデータや AI 資産を一元管理するガバナンス層です。 Metastore → Catalog → Schema → Table という入れ子が、権限・Lineage・監査すべての土台になります。

ユニティカタログとは何か一言でいうと

Unity Catalog は、Databricks 上のデータや AI 資産を一元管理するガバナンス層です。 テーブルの名前を並べるための入れ物ではなく、権限・Lineage・監査がぶら下がる土台だと考えてください。

メタストアからテーブルまで基本の4段

 
Metastore
  └─ Catalog
      └─ Schema  ├─ Table  ├─ View  ├─ Volume  └─ Function など

3階層名でテーブルを指す名前が構造そのもの

 
SELECT * FROM main.sales.orders;

なぜこの階層が必要なのか名前の管理だけではない

単にテーブル名を管理するだけではなく、次のことをまとめて管理するためです。

問い階層が答えるもの
誰がアクセスできるか権限（Catalog / Schema / Table のどの層に付けるか）
どの部署・用途のデータかCatalog と Schema の切り方そのもの
どこから来てどこへ流れたかLineage（UC 配下のオブジェクト間で記録される）
監査上どの操作が行われたかAudit log（対象オブジェクトは3階層名で記録される）

権限も Lineage も監査も、この階層の上に乗ります。 だから階層の切り方が、そのままガバナンスの切り方になります。

環境と業務領域で分けるよくある設計

 
Metastore ├─ prod → sales（orders, customers） / finance（invoices）
          └─ dev  → sales（orders_test）

ワークスペースとの違い混同しやすい

 
Workspace     = Notebook / Job / Pipeline を実行する作業空間
Unity Catalog = Table / Volume / Model などの管理・権限制御

試験でどう問われるかDEA試験でのポイント

「テーブルにアクセスさせたい」「権限を付与したい」「どのレベルでオブジェクトを整理するか」という問題では、 Catalog / Schema / Table の階層をまず頭に置くこと。

問題文の言い回しまず思い出す層
「このテーブルを読ませたい」Table — ただし上位の Catalog / Schema を通り抜けられるかも要る
「この業務領域のデータをまとめて扱いたい」Schema
「本番と開発を分けたい」Catalog
「どこに何があるか一意に指したい」3階層名（catalog.schema.table）

どの層に対して操作するのかが決まれば、選択肢はかなり絞れます。 逆に階層が頭に入っていないと、正しそうな用語がいくつも並んで見えます。

覚え方一行で持ち帰る

Unity Catalog = Databricks 全体のデータ資産の住所録 ＋ 権限管理 ＋ 監査・Lineage

住所録という言い方がしっくりきます。どこに何があるかを一意に指せて、そこに権限と履歴がぶら下がっている、という形です。

権限と継承をどう設計するかは ep012、Lineage と Audit log は ep013 で扱います。 この回は、その土台になる階層の形だけを持ち帰ってください。
