Unity CatalogのLineageとAudit

どちらも「追跡」の仕組みなので混ざりやすいのですが、追いかけている対象が違います。 Lineage は「データがどこから来てどこへ流れたか」、Audit は「誰が何をしたか」。 見分け方は、問いの主語がデータか人かの一点に尽きます。

追いかけている対象が違うこの回の主張

Lineage = データの系譜／Audit = 操作の記録。 この2行を先に頭へ入れておくと、どちらを答えるかはほとんど決まります。

リネージュはデータの系譜依存関係を追跡する

Databricks 上で実行された処理から、Table・Column・Notebook・Job・Dashboard などの依存関係を追跡できます。

代表用途（主語はすべてデータ）答えたい問い
Impact Analysis / Root Cause Analysis変えたらどこが壊れるか / 原因はどの上流にあるか
機密データの追跡 / 上流・下流の依存関係の把握個人情報はどこまで流れたか / 前後には何があるか

オーディットは操作の記録誰が・いつ・何をしたか

Audit は「誰が・いつ・どの操作をしたか」を追うための情報です。データの中身ではなく、 人とシステムの行動が残ります。

userA が tableX を参照した
adminB が権限を変更した
service-principal-C がJobを実行した

注目してほしいのは3つ目です。Job や Pipeline は人ではなく Service Principal として動くので、 Audit にも人の名前ではなく Service Principal の名前で残ります。 「誰も触っていないのに更新されている」の答えが、ここに出てくることがあります。

出てこないものを押さえる

Lineage 側に「誰が」は出てきません。逆に Audit 側に「どのテーブルから作られたか」という系譜は出てきません。 同じ画面から辿れても、記録している軸が違います。

混同しやすいポイント問いの主語で切る
問い主語見るもの
このGold TableはどのSilver Tableから作られた？ / この列を消したら何が壊れる？データLineage
誰がこのTableの権限を変更した？ / このテーブルに誰がアクセスした？人Audit

テーブル名が2つ出てきたら Lineage、人や Job の名前が出てきたら Audit、と読み替えても構いません。

Lineage 側の制約

Lineage が記録されるのは Unity Catalog 配下のものだけです。管理の外に置いたものは、そこで系譜が途切れます。 第8回で触れた「Unity Catalog の外に置かれるものを減らす」という方針が、ここでも効いてきます。

メールアドレスが流れたとき使い分けの具体例

顧客のメールアドレスが、誤って Dashboard まで流れてしまった場合を考えます。やることは2つです。

試験で問われる形DEA 試験ポイント
問題文に出てくる言葉答え
依存関係 / 上流・下流 / どこから来たか / 影響範囲Lineage
ユーザー操作 / アクセス履歴 / 監査 / 誰が変更したかAudit

覚え方

Lineage = データの家系図。Audit = 人間・システムの行動履歴。

家系図なので、親と子――つまり上流と下流が分かる。行動履歴なので、いつ・誰が・何をしたかが分かる。 迷ったら問いの主語を見る。
