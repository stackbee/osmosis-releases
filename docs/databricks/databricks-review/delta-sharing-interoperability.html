Delta Sharing と Interoperability

Delta Sharing は、Databricks 内外の相手にデータを安全に共有するための仕組みです。 コピーを配るのではなく、その場から読ませる。 Lakehouse Federation との違いは、データが誰の管理下にあるかで決まります。

外へ渡すための仕組み一言でいうと

Delta Sharing は、Databricks 内外の相手にデータを安全に共有するための仕組みです。 登場するのは3つで、提供する側から Share を通って、受け取る側へ渡ります。

提供する側と受け取る側基本用語
用語意味Unity Catalog 上の姿
PROVIDERデータを提供する側共有元。Share を作り、資産を載せる
SHARE共有するデータ資産をまとめた単位Securable Object（→ 下の「Share も Unity Catalog の管理対象」）
RECIPIENTデータを受け取る側共有先。Share を公開する相手

真ん中の SHARE が分かりにくいところ。 これは相手そのものでも、テーブルそのものでもありません。渡すものをひとまとめにした、荷物の側の単位です。

毎日 CSV を送らない具体例

自社の Databricks に、次の Gold Table があるとします。これを取引先に渡したい。

prod.sales.monthly_sales

CSV を毎日メール送信するのではなく、Delta Sharing で共有します。 手順は3段です。

Unity Catalog Table  →  Share に載せる
Share                →  Recipient へ公開する
Recipient            →  取引先が参照

ここで押さえたいのは、共有元データを毎回コピーして別システムへ配布する、という発想とは異なることです。

運搬そのものが消えるファイルコピーとの違い

相手も Databricks の場合Databricks-to-Databricks

相手も Databricks を使用している場合、受信した Share を Catalog として取り込み、 通常の Unity Catalog オブジェクトに近い感覚で参照できます。

Provider Databricks
      ↓   Delta Sharing
Recipient Databricks
      ↓   受信した Share を Catalog として取り込む
Catalog  →  SELECT ...

つまり相手にとっては、外から来たデータが、自分の Catalog の並びに入るということです。

相手が Databricks でなくてもOpen Sharing

Delta Sharing はオープンな共有方式を持つため、受信側が必ずしも Databricks である必要はありません。

外へ渡すか、外を見に行くかLakehouse Federation との違い

Share も Unity Catalog の管理対象セキュリティ

Share そのものも Unity Catalog の Securable Object です。 そのため、誰が Share を作れるか、どの資産を追加できるか、といった管理が Unity Catalog の権限モデルと結びつきます。

第8回「ガバナンスとセキュリティ」では、権限が効く単位として Catalog / Schema / Table を並べました。 Share も、その同じ並びに入るものだと考えてください。

外への共有が、別の仕組みの設定ではなくいつもの権限管理の延長線上にある。 ここが、統合されていることの意味です。
