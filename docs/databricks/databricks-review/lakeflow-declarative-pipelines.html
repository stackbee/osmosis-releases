Lakeflow Spark Declarative Pipelines

宣言するのは「最終的にどんなデータセットを作りたいか」。 依存関係と増分処理は Databricks 側が引き受けます。

宣言するのは結果一言でいうと

Lakeflow Spark Declarative Pipelines は、SQL や Python で 「最終的にどんなデータセットを作りたいか」を宣言し、 依存関係や増分処理を Databricks 側に多く任せる仕組みです。旧称は DLT。

宣言するのは結果の姿であって、実行の手順ではありません。 この段の一つ一つが、宣言されたデータセットです。

Procedural との違い順序を書くか、導かせるか

通常の Job では Task A → Task B → Task C のように処理手順を明示します。 Declarative Pipeline では依存関係を定義すると、Pipeline が DAG を解決して実行します。

中核概念は5つこの語彙だけ押さえる
概念位置づけ
Pipeline全体をまとめる単位
Flowその中でデータを運ぶ処理の単位
Streaming Table作られるデータセット — 到着分を足す側
Materialized View作られるデータセット — 結果を作り直す側
SinkPipeline が外へ書き出す先

試験で差が出るのは真ん中の2つ。Streaming Table と Materialized View です。

増分か、作り直しかStreaming Table と Materialized View
典型例Streaming TableMaterialized View
作り方 Cloud Storage → Auto Loader → bronze_orders → silver_orders silver_orders → GROUP BY → sales_daily

Bronze から Gold まで具体例で1本通す

 
CREATE OR REFRESH STREAMING TABLE bronze_orders AS SELECT * FROM STREAM read_files('s3://.../orders/');
CREATE OR REFRESH MATERIALIZED VIEW gold_daily_sales AS SELECT ... FROM silver_orders GROUP BY order_date;

Delta との関係できあがるのは Delta テーブル

Pipeline が作成・管理するテーブルは Delta を基盤にし、 ACID や Time Travel など Delta Lake の性質を利用します。

宣言的パイプラインは、別の保存形式を持ち込む仕組みではありません。 できあがるのは Delta テーブルです。トランザクションや履歴の話とそのまま繋がります。
