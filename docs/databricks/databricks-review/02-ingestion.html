データの取り込み

データが入ってくるところです。道具は4つありますが、覚えるべきは個々の仕様より「どれを選ぶか」の判断です。ガイド自身が objective に Prioritize between… と書いているため、選ばせる問題が来ると読めます。

全体像 — まず二分するファイルが置かれる側か、接続して取りにいく側か

取り込み元は2種類しかありません。最初にここで半分に絞ると、以降の判断が楽になります。

取り込み元性質使う道具
クラウドオブジェクトストレージ
（S3 / ADLS / GCS）		誰かがファイルを置いていく。拾いにいくCOPY INTO / Auto Loader
企業システム
（SaaS / DB / 業務アプリ）		ファイルにならない。接続して取りにいくLakeflow Connect / JDBC・REST

取り込みパターンは3つ、問われるのは1つ

取り込みのパターンは バッチ / インクリメンタル / ストリーミング の3つですが、 試験で問われるのはインクリメンタルです。

パターンやること例試験での比重
バッチ決まったタイミングで、まとまった量を一度に取り込む毎晩、前日分の全件を読む低い（単純だから）
インクリメンタル前回からの差分だけを取り込むまだ処理していないファイルだけを読むここが中心
ストリーミング到着したそばから連続的に処理するイベントが届くたびに処理する中くらい

比重が偏る理由は単純です。バッチは「全部読めばいい」ので迷いません。 ストリーミングも「来たものを処理する」で一貫しています。 難しいのはインクリメンタルだけです。 「前回からの差分だけ」を実現するにはどこまで処理したかを覚えておく必要があり、 さらに同じデータを二度取り込まないことを保証しなければなりません。 そして、その実現方法が道具ごとに違います。だから問題になります。

ですので、このドメインを学ぶときの視点は1つに絞れます。 「この道具は、二重取り込みをどうやって防いでいるのか」。 これが評価の中心軸です。

道具は4つ

道具何者か書く言語増分の持ち方
COPY INTOSQL でファイルを増分ロードするコマンドSQL読んだファイル名を記録
Auto Loader新着ファイルを継続的に検出するストリーミングソースPython / Scalaチェックポイント
Lakeflow ConnectSaaS・DB に接続する取り込みコネクタ設定（managed）コネクタが面倒を見る
JDBC / ODBC / REST汎用の接続手段。ノートブックから直接叩くPython / SQL自分で作る

着地先は常に Unity Catalog

ガイドの ingestion objective は、ほぼすべてが …into Unity-Catalog–governed tables で終わっています。 COPY INTO の項目も、Auto Loader の項目も、Lakeflow Connect の項目も、JDBC の項目も、全部そう書かれています。 つまり「どこに置くか」で悩ませる問題は出ません。問われるのはどう運ぶかだけです。

ここから実践的な読み方が1つ導けます。選択肢に「UC 管理外に置く」ものが混ざっていたら、ほぼ誤答。 ガバナンスを外す方向の選択肢は、この試験では選ばれません。

COPY INTOSQL だけで完結する、冪等な増分ロード

ガイドの記述はこうです。 Incrementally load files from cloud object storage (ADLS, S3, GCS) into Unity-Catalog–governed tables using the COPY INTO command. キーワードは incrementally（増分） です。

COPY INTO prod.bronze.orders
FROM 's3://landing/orders/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true')
COPY_OPTIONS  ('mergeSchema' = 'true');

ディレクトリを指定していますが、毎回まるごと読み直すわけではありません。 読んだファイル名を記録しており、実行のたびに照合して未読のファイルだけを読みます。 ここが COPY INTO のいちばん大事な性質です。

冪等性の仕組み — 記録と照合

「まだ読んでいないファイル」をどう判定しているか。記録しているだけです。順を追うとこうなります。

タイミングディレクトリの中身COPY INTO の動き取り込まれるもの
1回目file_A / file_B2つとも読み、「読んだ」と記録するfile_A / file_B
（file_C が置かれる）file_A / file_B / file_C——
2回目file_A / file_B / file_CA・B は記録にあるのでスキップ。C だけ未読と判定file_C のみ
3回目
（新着なし）		file_A / file_B / file_C全部が記録にある。何も読まないなし

この性質を冪等（べきとう）と呼びます。同じ状態で2回実行してもデータが二重になりません。 実運用では、これがリトライに効きます。 冪等でなければ、ジョブが失敗したときに「どこまで処理したか」を人間が確認しなければなりません。 冪等であれば、原因を直してそのまま再実行するだけで済みます。 Jobs のリトライ設定が意味を持つのも、取り込みが冪等であることが前提だからです。

構文の骨格

COPY INTO <catalog>.<schema>.<table>
FROM '<cloud-storage-path>'
FILEFORMAT = <CSV | JSON | PARQUET | AVRO | ORC | TEXT | BINARYFILE>
FORMAT_OPTIONS ('key' = 'value', ...)   -- ファイルをどう解釈するか
COPY_OPTIONS   ('key' = 'value', ...);  -- コマンドがどう振る舞うか
FILEFORMAT中身型の情報
CSVテキストの表形式持たない。オプションで補う
JSON半構造化。ネストしうる弱い。既定では string 寄り
PARQUET列指向のバイナリファイル自身が持つ
AVRO行指向のバイナリスキーマを同梱する
ORC列指向のバイナリファイル自身が持つ
TEXT1行＝1レコードの生テキスト無し（1列として読む）
BINARYFILEファイルをそのままバイナリで無し（画像・PDF 等）

2種類のオプションを区別する

句役割覚え方
FORMAT_OPTIONSヘッダの有無、区切り文字、スキーマ推論ファイル側の話：どう解釈するか
COPY_OPTIONSスキーマ追随、強制再読込コマンド側の話：どう振る舞うか

名前が似ているので混ざりますが、FORMAT はファイル側、COPY はコマンド側と覚えれば分かれます。

FORMAT_OPTIONS の代表例

オプション対象意味
'header' = 'true'CSV1行目を列名として扱う
'delimiter' = '|'
'sep' = '|'		CSV区切り文字を変える（既定はカンマ）
'inferSchema' = 'true'CSV / JSON型を推論させる。指定しないと文字列寄りに倒れる
'multiLine' = 'true'CSV / JSON1レコードが複数行にまたがる形式を読む
'nullValue' = 'NULL'CSVこの文字列を NULL として扱う
'escape' = '"'CSV引用符のエスケープ文字
'encoding' = 'SJIS'CSV / JSON文字コードを指定する
'mergeSchema' = 'true'PARQUET 等ファイル群の間でスキーマを突き合わせる（COPY_OPTIONS の同名とは別物）

COPY_OPTIONS は2つだけ覚える

COPY_OPTIONS挙動使う場面
mergeSchema = true新しい列が来たら、テーブルに列を足して取り込む取り込み元に列が増えることがある
force = true読み済みの記録を無視して全部読み直すテストのやり直しなど。冪等性を意図的に外すスイッチ

force がなぜ用意されているのか。 たとえば取り込んだあとに変換ロジックのバグが見つかり、テーブルを作り直して最初から入れ直したい—— こういうときに使います。冪等性を外すためのスイッチだと理解しておくと、 「通常は使わないもの」という位置づけがはっきりします。

-- 列が増えることがある CSV を、ヘッダ付きで増分ロードする
COPY INTO prod.bronze.orders
FROM 's3://landing/orders/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true', 'inferSchema' = 'true')
COPY_OPTIONS  ('mergeSchema' = 'true');

-- テーブルを作り直したので、記録を無視して全部読み直す（例外的な操作）
COPY INTO prod.bronze.orders
FROM 's3://landing/orders/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true')
COPY_OPTIONS  ('force' = 'true');

得意と不得意

向いている向いていない
SQL だけで完結させたいファイルが数百万規模ある
ファイル数が数千規模まで到着のたびに継続的に処理したい
決まった時刻にまとめて流すディレクトリの一覧そのものが重い
リトライ可能にしたい低遅延にしたい

規模が大きくなると何が起きるか。 「どのファイルが未読か」を調べること自体が重くなります。 COPY INTO はディレクトリを一覧して記録と照合します。数千なら一瞬ですが、数百万あると 一覧するだけで時間もお金もかかり、しかもそれを実行のたびに繰り返します。 この問題を設計で解いたのが、次の Auto Loader です。

Auto Loader数百万ファイルでも未読だけを取り出せる仕組み

 
(spark.readStream
  .format("cloudFiles")                        # ← これが Auto Loader
  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", "/chk/orders/schema")
  .load("s3://landing/orders/")
 .writeStream
  .option("checkpointLocation", "/chk/orders")  # ← 進捗の記録先
  .trigger(availableNow=True)
  .toTable("prod.bronze.orders"))

format("cloudFiles") と書いた時点で Auto Loader です。 それ以外は通常の Structured Streaming の書き方そのもので、 Auto Loader は Structured Streaming のデータソースの1つにすぎません。 まったく新しい仕組みではなく、「ファイルの取り込みに特化したソース」と理解しておくと、頭の整理が楽になります。

主要オプション一覧

cloudFiles. で始まるものが Auto Loader 固有、それ以外は Structured Streaming 共通です。 この切り分けができると、オプション名を丸暗記しなくても意味が推測できます。

オプション所属役割
cloudFiles.formatAuto Loader元ファイルの形式（json / csv / parquet / avro / text / binaryFile）
cloudFiles.schemaLocationAuto Loader推論したスキーマの保存先。形の記録
cloudFiles.schemaEvolutionModeAuto Loader新しい列が来たときの振る舞い（後述）
cloudFiles.inferColumnTypesAuto Loadertrue にすると実際の型を推論する（既定は string 寄り）
cloudFiles.schemaHintsAuto Loader一部の列だけ型を指定する。残りは推論に任せる
cloudFiles.useNotificationsAuto Loadertrue で file notification 方式に切り替える
cloudFiles.includeExistingFilesAuto Loader開始時点で既に置かれているファイルを含めるか（既定 true）
cloudFiles.maxFilesPerTriggerAuto Loader1回のマイクロバッチで扱うファイル数の上限。流量を絞る
checkpointLocationStructured Streaming 共通進捗の記録先
trigger(...)Structured Streaming 共通連続実行か、1回で止まるバッチ実行か
toTable(...)Structured Streaming 共通書き込み先の UC テーブル

2つの記録場所を混同しない

オプション何を覚えているか消すとどうなるか
checkpointLocationどこまで読んだか（進捗）最初から全部読み直す
cloudFiles.schemaLocationどんな形だったか（スキーマ）推論をやり直す

進捗と、形。役割が違い、別々の記録として管理されています。 名前が似ているうえに、パスの指定先も近い場所に置くことが多いので、ここは意識して分けてください。

チェックポイントの中身

チェックポイントは、ただのフォルダではなく3種類の記録を持っています。 「消すと全部読み直す」の理由が、ここを見ると分かります。

中身何が入っているか無くなると
オフセット
（offsets）		「次はここからを1バッチとして処理する」という計画次にどこから読めばよいか分からなくなる
コミット
（commits）		どのバッチまで完了したか完了済みかどうかが判定できない
処理済みファイルの台帳どのファイルを読んだか。専用のキー値ストアで持つすべてのファイルが未読扱いになる

この台帳が、大量ファイルに強い理由の1つです。 COPY INTO は実行のたびにディレクトリを一覧して記録と照合するため、ファイルが増えるほど照合のコストが線形に増えます。 Auto Loader は処理済みファイルを専用のキー値ストアで管理しているので、 膨大な数になっても照合が効率的に行えます。 さらに、そもそも一覧しないで済ませる手段（file notification）も持っています。

「最初から取り込み直したい」ときは、チェックポイントを消せば実現できます。 COPY INTO の force = true に相当する操作です。 ただし書き込み先のテーブル側も一緒に整理しないとデータが二重になります。必ずセットで考えてください。

Auto Loader ＝ 常時起動、ではない

ガイドの objective は Use Auto Loader … in batch modes と明記しています。 trigger(availableNow=True) を指定すると、 今ある未処理を全部処理して停止します。 Lakeflow Jobs から日次で叩けば、増分の管理だけ借りて、実行はバッチという使い方ができます。 「常時起動だから使えない」という思い込みがあると、選択肢を切り間違えます。

trigger の指定動きクラスタ使いどころ
trigger(processingTime="5 minutes")5分ごとに新着を拾いにいく動き続ける低遅延にしたい
trigger(availableNow=True)今ある未処理を全部処理して停止処理中だけ動く日次バッチ。Jobs から叩く

スキーマ推論の挙動

推論・強制・進化は別の概念です。まずここを分けます。

推論
Inference
ファイルを覗いて、どんな列があってどんな型かを推測する。 初回にサンプリングして推論し、結果を schemaLocation に保存する。 2回目以降は毎回推論し直さず、保存済みのものを使う。
強制
Enforcement
決めたスキーマに合わないものを弾く。
進化
Evolution
新しい列が来たときに追随する。

ガイドが名指ししているのは schema enforcement and schema evolution、 つまり強制と進化です。推論はその前提として動いているもの、という位置づけになります。 弾くことと受け入れることを、状況で使い分けられるかが問われます。

JSON / CSV は既定で全部 string

安全側に倒しているためです。サンプリングした範囲では数値に見えても、 後から文字が混ざったファイルが来るかもしれない。そのときに壊れないよう、最初から文字列として扱います。 ただし実務では、金額の列が文字列だと集計できず困ります。解き方は2つです。

オプションやること効き方
cloudFiles.inferColumnTypes = true実際の型を推論させる全列に効く。int / double などが付く
cloudFiles.schemaHints一部の列だけ型を指定する指定した列だけ。残りは推論に任せる
(spark.readStream
  .format("cloudFiles")
  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", "/chk/orders/schema")
  .option("cloudFiles.inferColumnTypes", "true")
  # 要所だけ固定する。残りは推論に任せる
  .option("cloudFiles.schemaHints", "order_id INT, amount DOUBLE, ordered_at TIMESTAMP")
  .load("s3://landing/orders/"))

選択肢に「全部のスキーマを手書きで定義する」が混ざることがあります。 技術的には可能ですが、答えとしては不自然です。 Auto Loader を使う理由の1つがスキーマ管理を任せられることだからで、 全部手書きするならその利点を捨てています。 こうした「できるけれど、目的に合わない」選択肢は切ってください。

スキーマ進化のモード

cloudFiles.schemaEvolutionMode で、新しい列が来たときの振る舞いを決めます。

値新しい列が来たとき止まるか使いどころ
addNewColumns
（既定）		列を足す。再起動すれば取り込むいったん止まる素直に追随したい
rescue列は足さず、_rescued_data に丸ごと退避止まらない止めたくない・失いたくない
failOnNewColumns失敗させる止まる（再起動しても同じ）変化を検知して人が判断したい
none無視する（新列は捨てる）止まらない形を固定したい

既定の addNewColumns は、自動で列が足されて何事もなく続くのではありません。 一度エラーで止まり、スキーマが更新され、再起動すると続きから動く——この挙動です。 「新しい列が届くと処理が止まる」は異常ではなく仕様です。 異常だと判断してクラスタやコードを調べ始めると、時間を失います。

_rescued_data の使い方

rescue で出てくる _rescued_data は、 スキーマに合わなかったデータを JSON 文字列として退避しておく列です。

退避先がない場合を考えると、価値が分かります。 型が合わないデータや想定外の列が来たとき、退避先がなければ静かに欠落します。 エラーにもならず、ただ消える。そして後日「あのデータ、どこにいったんだろう」となり、原因を追うのが非常に難しくなります。 _rescued_data があれば、取り込みは止まらず、かつデータも失われません。 後からこの列を調べれば、何が来ていたのかが分かります。

# 止めない・失わない設定
(spark.readStream
  .format("cloudFiles")
  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", "/chk/orders/schema")
  .option("cloudFiles.schemaEvolutionMode", "rescue")
  .load("s3://landing/orders/")
 .writeStream
  .option("checkpointLocation", "/chk/orders")
  .trigger(availableNow=True)
  .toTable("prod.bronze.orders"))
-- 退避されたものが無いかを、運用として定期的に見る
SELECT count(*) AS rescued_rows
FROM prod.bronze.orders
WHERE _rescued_data IS NOT NULL;

-- 何が来ていたのかを覗く（中身は JSON 文字列）
SELECT _rescued_data
FROM prod.bronze.orders
WHERE _rescued_data IS NOT NULL
LIMIT 20;

試験での引き方ははっきりしています。問題文に「データを失いたくない」と「処理は止めたくない」が同時に 出てきたら rescue です。片方だけなら他の選択肢もありえます。両方揃ったら rescue、と覚えてください。

最後の行が重要です。どちらも「二重に取り込まない」を実現しています。 違うのは実現方法と、耐えられる規模です。 ですので、問題文に「重複を防ぎたい」とだけ書かれていても絞れません。 規模や、SQL で書きたいのか、といった条件を合わせて読んでください。

ファイル検出方式ガイドが括弧付きで名指しした2つ

objective に (for example, directory listing or file notification) と 例示されています。わざわざ名前を挙げているということは、 この2つの名前と違いを知っている前提だ、ということです。どちらを選ぶかを問う出題は十分にありえます。

cloudFiles.useNotifications = true

directory listing は、ストレージのディレクトリに「今どんなファイルがありますか」と聞きにいき、 返ってきた一覧を処理済みの記録と照合して、記録にないものを未読として処理します。 設定が要らずすぐ動かせるかわりに、ファイルが増えるほど一覧のコストが増え、 しかもそれを実行のたびに繰り返します。COPY INTO の弱点とまったく同じ問題です。

file notification は考え方が違います。ディレクトリを見に行きません。 クラウド側の通知サービスが「新しいファイルが置かれました」というイベントを流し、Auto Loader はそれを受け取ります。 一覧していないので、ディレクトリに何百万ファイルあっても検出コストは変わりません。

AWSSNS ＋ SQS

(spark.readStream
  .format("cloudFiles")

  .load("s3://landing/orders/"))

判断の軸は2つ

「規模」と「準備できるか」です。 大規模だから常に notification、ではありません。 企業環境ではクラウドの設定権限がデータエンジニアに無いこともあり、その場合はそもそも選べません。 問題文に権限や設定の制約が書かれていたら、そちらも必ず読んでください。 「大規模」という言葉だけで反射的に選ぶと引っかかります。

directory listing 寄りになる条件file notification 寄りになる条件
すぐに始めたい。検証の段階である数百万ファイル規模である
ファイル数がそれほど多くない一覧そのものが遅い／コストがかかっている
クラウド側の設定権限がない到着から処理までの時間を短くしたい

よくある誤答

「検出が遅い → クラスタを大きくする」。直りません。 検出はファイルの探し方の問題であって、計算資源の問題ではないからです。 ディレクトリの一覧に時間がかかっているところに計算ノードを増やしても、一覧は速くなりません。 この「ボトルネックが違うのに増強する」型は、 この試験で最も繰り返し出てくる誤答です。

Lakeflow Connect と JDBC / RESTファイルになっていないものを取りにいく

ここまでの道具は「誰かがストレージにファイルを置いてくれている」前提でした。 では、そのファイルは誰が置いているのか。ここが実は大きな問題です。

Salesforce や SQL Server は、クラウドストレージにファイルを置いてはくれません。 API を叩いて取ってきて、ファイルにして、置く——その工程を誰かが作る必要があります。 Lakeflow Connect は、その工程ごと肩代わりします。 Salesforce、Workday、ServiceNow、SQL Server といった企業システムに接続して、直接データを持ってきます。 ファイルになっていないものを取ってくる道具、と理解してください。 なお、これは2026年5月改訂で新しく入った範囲で、旧版の教材には載っていません。

ガイドは Lakeflow Connect standard connectors, and Lakeflow Connect managed connectors と、 わざわざ両方を挙げています。この2語の区別は問われる可能性があります。

自前で作ると、何が必要になるか

Lakeflow Connect の価値は、「自前実装と比べて何が減るか」で測ると分かります。

つまり、評価の軸は「作る量」と「保守の責任」の2つで、その両方が減ります。 ガイドの objective にも reliably ingest data from diverse enterprise sources と、 reliably（信頼性をもって）という言葉が入っています。 自前で作ると「動くもの」は作れても、信頼性を保ち続けるのが大変です。そこを強調していると読めます。

コネクタが無いとき — JDBC / REST

ガイドはこう書いています。 …using JDBC/ODBC or REST clients within notebooks to land data into cloud storage or directly into UC tables, usually orchestrated and scheduled with Lakeflow Jobs. 末尾に注目してください。これ単体では完結しません。回す仕組みとセットで考える前提です。

Auto Loader や Lakeflow Connect は、取り込みの仕組みごと提供してくれます。進捗の管理もスケジュールも中に含まれています。 一方 JDBC や REST は素材だけです。「データを取ってくるコード」しかありません。 いつ動かすか、失敗したらどうするか、前回からの差分をどう取るか——全部自分で組む必要があります。 Lakeflow Jobs と必ずペアになる、と覚えておいてください。

df = (spark.read.format("jdbc")
  .option("url", "jdbc:postgresql://host:5432/db")
  .option("dbtable", "public.orders")
  .option("user", dbutils.secrets.get("scope", "db-user"))
  .option("password", dbutils.secrets.get("scope", "db-pass"))
  .option("partitionColumn", "id")     # ← これが無いと接続は1本
  .option("lowerBound", "1").option("upperBound", "1000000")
  .option("numPartitions", "8")
  .load())

df.write.mode("append").saveAsTable("prod.bronze.orders")

JDBC が遅い本当の理由

何も指定しないと接続は1本です。クラスタに何台ノードがあっても、 1つのタスクが全件を引いてきます。Spark を使っているのに分散処理になっていません。 partitionColumn / lowerBound / upperBound / numPartitions で範囲を分けて、はじめて並列に読みます。 上の例なら id を 1〜1,000,000 の範囲で8分割し、8本の接続で並列に引いてきます。

「クラスタを拡張したが変わらない」は、この状態の典型的な症状です。

REST クライアントの場合

import requests
res = requests.get(url, headers={"Authorization": "Bearer " + token})
df = spark.createDataFrame(res.json())

ここで注意すべきは動いている場所です。 requests はドライバ上で動きます。分散処理ではありません。 ドライバ1台で API を叩き、レスポンスを受け取っています。ですので、大量データの取得には向きません。

現実的には、組み合わせて使います。API でデータを取得し、ストレージにファイルとして落とし、 そのファイルを Auto Loader で取り込む。こうすると、API を叩く部分と大量データを処理する部分が分離できます。 この経路はガイドにも land data into cloud storage or directly into UC tables と明示されています。 選択肢に「API で取得してストレージに落とし、Auto Loader で取り込む」があれば、 遠回りに見えても自然な答えです。

選ぶ順番 — JDBC / REST は最後の手段

まず専用のコネクタがあるかを確認し、あれば Lakeflow Connect。 なければ、ファイルとして置かれるかを見て、置かれるなら Auto Loader か COPY INTO。 置かれないなら JDBC / REST ＋ Lakeflow Jobs。この順番です。

選択肢に「専用の仕組みがあるのに、手書きでコードを書く」ものが混ざっていたら、 たいてい誤答です。技術的にはできますが、この試験は「できるか」ではなく「適切か」を問うています。 保守の負担が大きい選択肢は選ばれません。

認証情報は必ず dbutils.secrets から。 ノートブックに直書きする選択肢は、この試験では常に誤答になります。 セキュリティに反する選択肢は、他がどれだけ合っていても選ばれません。

半構造化データの取り込みJSON・ネスト構造をどう受け止めるか

ここまではどうやって運ぶかの話でした。ここからは、 運ばれてくるものが JSON のような複雑な形をしているときどう受け止めるかの話です。 ガイドの記述はこうです。 Ingest semi-structured and unstructured data (for example, JSON and nested data) via Lakeflow Connect and other managed connectors into Unity-Catalog–governed Delta tables.

まず3分類を分ける

分類性質例置き場所
構造化行と列が決まっているCSV、DB のテーブルテーブル
半構造化形はあるが、固定ではないJSON、XML、ログテーブル（ネストのまま持てる）
非構造化そもそも表にならない画像、PDF、音声Volume（S1）

半構造化がなぜ「半」なのか。JSON ならキーと値という形はあります。 でも、レコードによってキーが増えたり減ったりします。形が固定されていない。だから半構造化です。 ガイドは半構造化と非構造化を並べて書いていますが、 置き場所が違う（テーブル / Volume）ので、混ぜないでください。

ネストは潰さずに保持できる

大事な前提です。Delta テーブルはネストした構造をそのまま持てます。平らにする必要はありません。

{"order_id": 1,
 "customer": {"id": "c01", "region": "JP"},
 "items": [{"sku": "A", "qty": 2}, {"sku": "B", "qty": 1}]}

この JSON は、Delta テーブルではこの形のまま持てます。

order_id  INT
customer  STRUCT<id: STRING, region: STRING>
items     ARRAY<STRUCT<sku: STRING, qty: INT>>

Bronze では無理に平らにしない

Bronze 層の役割は届いたものをそのまま受け止めることです。 ここで加工すると元の形が失われ、後から「あの項目も必要だった」となったときに取り直しになります。 平坦化は Silver 層で行います（メダリオンと explode() は S3）。

ですので、選択肢に「取り込み時にすべて平坦化して列に展開する」があっても、 Bronze の文脈なら基本は選びません。STRUCT / ARRAY のまま Bronze へが方針です。

ドット記法とコロン記法

ネストした構造の中身にアクセスする書き方が2つあります。 区別を問われる可能性があるところです。

ドット記法コロン記法
書き方customer.regionraw:customer.region
前提列が STRUCT 型である
＝もう構造として解釈済み		列が 文字列で JSON を持っている
＝まだ文字列のまま
使える場所SQL / PySpark とも同じ形主に SQL
どうしてそうなるか取り込み時にスキーマが推論されていれば STRUCT になる生の文字列としてそのまま取り込めば文字列のまま
-- ドット記法：customer が STRUCT のとき
SELECT order_id, customer.region
FROM prod.bronze.orders;

-- コロン記法：raw が JSON を持つ「文字列」のとき
SELECT event_id, raw:customer.region
FROM prod.bronze.raw_events;
# PySpark でも、STRUCT ならドットで降りられる
df.select("order_id", "customer.region")

同じ JSON でも、列の型がどちらになっているかで書き方が変わります。 「列の型を確認してから書き方を決める」。この順番を覚えておいてください。 なお、配列を1行ずつに展開する explode() は S3 で扱います。ここでは「配列のまま保持できる」ことを押さえます。

文字列の JSON を構造に変える — from_json

from pyspark.sql.functions import from_json, schema_of_json

schema = "order_id INT, customer STRUCT<id: STRING, region: STRING>"
df2 = df.withColumn("parsed", from_json("raw", schema))

# 構造になったので、以降はドット記法で降りられる
df2.select("parsed.customer.region")
関数やること前提
from_json文字列 → 構造（STRUCT）に変換するスキーマを渡す必要がある
schema_of_jsonサンプルからスキーマを推測させるスキーマが分からないときの補助

VARIANT 型

新しめの選択肢として VARIANT 型があります。 半構造化データをスキーマを固めずに格納でき、後からクエリで中を掘れる型です。 from_json のように事前にスキーマを決める必要がありません。

-- スキーマを固めずに保持し、後から掘る
CREATE TABLE prod.bronze.raw_events (
  event_id  BIGINT,
  payload   VARIANT
);

SELECT event_id, payload:customer.region AS region
FROM prod.bronze.raw_events;

試験でどこまで問われるかは読めませんが、名前だけは知っておいてください。 「スキーマを固めずに半構造化データを保持したい」という要件が出てきたら、VARIANT が候補になります。

8問です。先に自分で答えを言ってから開いてください。 言えなかったものは、上の該当セクションに戻る合図です。

  • Q1毎晩 S3 に置かれる CSV を、SQL だけで取り込みたい。ジョブが失敗したときは、どこまで処理したか調べずにそのまま再実行できるようにしたい。何を使うか。

    答えを見る

    COPY INTO。読んだファイル名を記録して未読だけを読むので冪等であり、そのまま再実行しても二重になりません。SQL だけで完結する点も条件に合います。

  • Q2S3 に数百万のファイルがあり、ディレクトリの一覧に時間とコストがかかっている。到着から取り込みまでの遅延も縮めたい。クラウド側の設定権限はある。どうするか。

    答えを見る

    Auto Loader ＋ file notification（cloudFiles.useNotifications = true）。通知方式は一覧しないので検出コストが件数に依存せず、低遅延にもできます。クラスタの増強では直りません——これはファイルの探し方の問題だからです。

  • Q3checkpointLocation と cloudFiles.schemaLocation は、それぞれ何を覚えているか。また、それぞれを消すとどうなるか。

    答えを見る

    checkpointLocation は進捗（どこまで読んだか）。消すと最初から全部読み直し、テーブル側を整理していなければデータが二重になります。
    cloudFiles.schemaLocation はスキーマ（どんな形だったか）。消すと推論をやり直します。

  • Q4Auto Loader で運用中、取り込み元に新しい列が現れた瞬間に処理が止まった。クラスタにもコードにも異常は見当たらない。原因は何か。

    答えを見る

    既定の cloudFiles.schemaEvolutionMode = addNewColumns の仕様です。新しい列が来るといったんストリームを止め、列を足し、再起動すれば取り込みを続けます。不具合ではありません。

  • Q5「取り込みを止めたくない。かつ、想定外のデータも失いたくない」と書かれている。何を選ぶか。

    答えを見る

    schemaEvolutionMode = rescue と _rescued_data 列。列は足さず、スキーマに合わなかったデータを JSON 文字列として退避します。「止めたくない」と「失いたくない」が同時に出てきたら rescue が目印です。

  • Q6JDBC で大きなテーブルを読んでいるが遅い。クラスタのノードを増やしても変わらない。原因と対処は。

    答えを見る

    何も指定しないと接続が1本しか張られず、1タスクが全件を引くため分散処理になっていません。partitionColumn / lowerBound / upperBound / numPartitions で範囲を分割すると、並列に読めるようになります。

  • Q7Salesforce のデータを毎日取り込みたい。パイプラインの保守に人を割けない。「requests で API を叩いて自作する」という選択肢は適切か。

    答えを見る

    適切ではありません。Lakeflow Connect の managed connector を使います。差分の取り方・スケジュール・API 仕様変更への追随・認証情報の管理を任せられ、作る量と保守の責任が減ります。「専用の仕組みがあるのに手書きする」は典型的な誤答パターンです。

  • Q8ネストした JSON を Bronze に取り込む。customer.region と raw:customer.region は、どう使い分けるか。

    答えを見る

    ドット記法は列が STRUCT 型のとき（＝もう構造として解釈済み）。コロン記法は列が文字列として JSON を持つとき（＝まだ文字列のまま）。文字列を構造に変えるなら from_json、スキーマを固めずに保持するなら VARIANT が候補です。なお Bronze では平坦化しないのが方針です。
