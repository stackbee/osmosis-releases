ガバナンスとセキュリティ

誰に何を見せるか。この改訂で最も入れ替わったドメインです。Delta Sharing と Lakehouse Federation が消え、代わりに行レベルセキュリティ・列マスキング・ABAC が入りました。旧教材の該当章は、ほぼ使えません。

このドメインの範囲旧版から最も入れ替わった領域
旧版で厚かったもの新版で入ったもの
Delta Sharing（範囲外）行レベルセキュリティ / 列マスキング
Lakehouse Federation（範囲外）ABAC ポリシー
—managed / external の相互変換

旧版のガバナンス領域は、体感でかなりの分量が Delta Sharing に割かれていました。 そこは丸ごと空振りになります。実務では使う機能なので知識として無駄ではありませんが、 この試験の対策としては優先度を大きく下げて構いません。 Lakehouse Federation も同様で、新しいガイドには記載自体がありません。 古い問題集をそのまま回すと、この2つに時間を吸われます。

ガイドが名指ししている項目

ガイドの記述（要点）対応する節
managed と external を区別し、作成・変更・削除・相互変換を行うmanaged と external
UI と SQL で GRANT / REVOKE / DENY を principal に、適切な階層で適用するGRANT / REVOKE / DENY
ユーザーグループに基づいて可視性を制限する列マスキングと行レベルセキュリティを理解する行フィルタと列マスク
centrally control するための ABAC ポリシーを理解するABAC ポリシー
データの来歴と操作の記録（lineage / audit log）lineage と audit log

動詞に注目してください。managed / external と GRANT は 「実行する（perform / configure）」＝手を動かすレベル。 行フィルタ・列マスク・ABAC は「理解する（understand）」＝ 何がどう効くかを説明できるレベル。ABAC の細かい DDL を暗記する必要はありません。 使いどころと効き方が問われます。

このドメインは3段階で理解する

GRANT（読める / 読めないの二択）→ 行フィルタ・列マスク（1テーブル内）→ ABAC（横断）。 適用範囲がだんだん広がっていきます。問題文の範囲の広さで、どの段を答えるかが決まります。 次の節で、この3段を1本の流れとして通します。

アクセス制御の3段階このドメイン全体を貫く1本の軸

このドメインに出てくる機能は、バラバラに並んでいるように見えて、 実際には「1つの要件を、どこまで細かく・どこまで広く効かせたいか」という 一本の軸の上に並んでいます。順番に見ると、全部が同じ話の続きだと分かります。

段仕組み効く単位答えられる要件限界
1段目GRANT / REVOKE / DENYオブジェクト（カタログ / スキーマ / テーブル）「このグループはこのテーブルを読んでよい」読める / 読めないの二択しか作れない
2段目row filter / column mask1テーブルの中の行と列「営業は自分の地域の行だけ」「メールは伏せて」テーブルごとに設定する＝増えると設定漏れが出る
3段目ABAC ポリシータグ（＝属性）を通じてカタログ / スキーマ配下すべて「PII タグの列は、全社どこでもマスク」個別の細かい例外は結局2段目で書く

段が上がるほど設定の場所が「対象そのもの」から遠ざかり、適用範囲が広がります。 1段目はテーブルを名指しします。2段目もテーブルを名指ししますが、中身の見え方を変えます。 3段目はテーブルを名指ししません。タグという属性を名指しするので、 まだ存在しないテーブルにも先回りして効きます。

問題文から段を決める2つの問い

① 全部見せるか、全部隠すかで足りるか。 足りるなら1段目（GRANT）。足りないなら2段目以降。
② 話は1テーブルで閉じているか。 閉じているなら2段目（row filter / column mask）。 「複数テーブル」「全社」「新しく作られるテーブルにも」なら3段目（ABAC）。

この3段は置き換えではなく積み重ねです。 ABAC を入れても GRANT は要ります。そもそもテーブルに SELECT が無い人には、 行フィルタも列マスクも出番がありません。1段目を通過した人に対して、2段目・3段目が効きます。 「ABAC を設定したのに、あの人はまだテーブル全体が読めてしまう」といった状況が問題文に出たら、 段の取り違えではなくタグの付け忘れを疑うのが筋です。

managed table と external table判別は一文で済む

判別の一文

「DROP TABLE したら、実データはどうなるか」 managed は消える。external は残る。ここだけで大半の問題が切れます。

なぜそうなるのかを押さえておくと、応用問題にも効きます。 managed table は、Unity Catalog が保存場所を決めています。 UC が実体を持っているので、テーブルを消せば実体も消します。 external table は、LOCATION で指定した場所にあるデータを「登録している」だけです。 登録を解除しても、データはそこに残ります。

managedexternal
作り方LOCATION を書かないLOCATION を書く
場所を決めるのはUnity Catalog自分
DROP したらデータも消える定義だけ消える
Predictive Optimization対象対象外
他システムからの直接読み書き想定しないできる（それが選ぶ理由）
確認方法DESCRIBE EXTENDED の Type 欄に MANAGED と出る同じく Type 欄に EXTERNAL と出る

作る

-- managed（LOCATION を書かない）
CREATE TABLE prod.silver.orders (
  order_id BIGINT,
  amount   DOUBLE,
  region   STRING
);

-- external（LOCATION を書く）
CREATE TABLE prod.bronze.raw_orders (
  order_id BIGINT,
  amount   DOUBLE
)
LOCATION 's3://existing-bucket/raw/orders/';

-- CTAS でも同じ。LOCATION の有無だけが分かれ目
CREATE TABLE prod.gold.daily_sales AS SELECT ... ;                    -- managed
CREATE TABLE prod.gold.daily_sales LOCATION 's3://.../gold/daily/'
AS SELECT ... ;                                                       -- external

分かれ目は LOCATION の一行だけです。 スキーマ定義でも CTAS でも、判定のしかたは変わりません。 なお external を作るには、その保存先に対応する external location / storage credential が用意され、 そこへの権限が必要です。「パスを書いたのに作れない」はこの不足です。

変更する・削除する

-- 名前を変える／コメントを付ける（managed でも external でも同じ）
ALTER TABLE prod.silver.orders RENAME TO prod.silver.orders_v2;
ALTER TABLE prod.silver.orders SET TBLPROPERTIES ('owner_team' = 'de');

-- 列を足す
ALTER TABLE prod.silver.orders ADD COLUMN channel STRING;

-- 削除。ここだけ結果が決定的に違う
DROP TABLE prod.silver.orders;      -- managed: 定義もデータも消える
DROP TABLE prod.bronze.raw_orders;  -- external: 定義だけ消える。ファイルは残る

Unity Catalog の managed table は、DROP した後も 一定期間は UNDROP TABLE で復元できます。 ただし「消えない」わけではありません。試験で問われるのはあくまで 「DROP でデータが消えるのはどちらか」という区別です。

相互変換する

ガイドは convert between managed and external tables とも書いており、 相互に変換できることまで範囲に入っています。一度決めたら変えられない、ではありません。

-- external → managed（実体を UC の管理領域へ移す）
ALTER TABLE prod.bronze.raw_orders SET MANAGED;

-- managed → external は「置きたい場所へ作り直す」のが確実
CREATE TABLE prod.bronze.raw_orders_ext
LOCATION 's3://my-bucket/bronze/raw_orders/'
AS SELECT * FROM prod.bronze.raw_orders;
変換の向き主な動機
external → managed既存データを UC の管理下に取り込む／Predictive Optimization の対象にしたい
managed → external実体を自分の決めた場所に置きたい／他システムから直接読ませたい

構文の細部よりも、「どちらの向きに、なぜ変換するのか」が問われる作りです。 「自動最適化を効かせたい」と書いてあれば managed 方向、 「外部システムからも同じ実体を読みたい」と書いてあれば external 方向です。 これは Liquid Clustering が ALTER で変えられるのと同じ流れで、 Databricks は全体として「後から変えられる」方向に進んでいます。

DESCRIBE EXTENDED の見方

DESCRIBE EXTENDED prod.silver.orders;
見る欄読み取れること
TypeMANAGED / EXTERNAL。この節の主役

Delta 固有の物理情報（ファイル数、サイズ、クラスタリング列など）を見たいときは DESCRIBE DETAIL のほうが向いています。 DESCRIBE EXTENDED は「どういうテーブルか」、 DESCRIBE DETAIL は「いま物理的にどうなっているか」。 このドメインで使うのは前者です。

新規作成は迷ったら managed。 「既にストレージにあるデータを登録したい」「他システムが同じ実体を直接読む」など、 外部に理由があるときだけ external を選びます。 なんとなく external を選ぶと、実体の管理を自分で背負い込むことになります。

GRANT / REVOKE / DENY公式サンプル問題あり。粒度と階層で殺しにくる

…applying GRANT, REVOKE, and DENY privileges to principals (users, groups, and service principals) at appropriate levels of the security hierarchy.

この一文に、問われる要素が3つ全部入っています。 3つの操作（GRANT / REVOKE / DENY）、 3種類の principal（user / group / service principal）、 そして適切な階層。順に潰します。

公式サンプル問題：analyst グループに読み取り専用アクセスを与える

（USE CATALOG / USE SCHEMA は付与済みという但し書きがある）

  • A GRANT ALL PRIVILEGES ON SCHEMA sales_data TO analysts — 権限が広すぎる
  • B（正解） GRANT SELECT ON SCHEMA sales_data TO analysts
  • C GRANT INSERT ON SCHEMA sales_data TO analysts — 権限の種類が違う（書き込み）
  • D GRANT SELECT ON ALL TABLES IN SCHEMA … — スキーマに対する標準形ではない

誤答の型は広すぎる／種類が違う／対象の書き方が違う。 そして但し書きの存在自体が、階層を理解しているかの確認になっています。

D をもう少し丁寧に見ておきます。Unity Catalog では スキーマに付与した権限は、その配下のテーブルに継承されます。 しかもあとから作られたテーブルにも効きます。 だから「全テーブルに1つずつ配る」という発想の書き方は、そもそも不要なのです。 継承を知っていれば B を選べる——という設計になっています。

権限できること主に付与する対象

読む系は SELECT、書く系は MODIFY、 通り抜けは USE。この3つの区別が付けば、 「読み取り専用にしたい」「書き込みも許したい」といった問題文から、 選ぶべき権限は一意に決まります。 INSERT のような単発の動詞を選ばせる選択肢は、 たいてい「種類が違う」型の誤答です。

書き方

-- 対象の種類を明示して付与する
GRANT USE CATALOG ON CATALOG prod TO `analysts`;
GRANT USE SCHEMA  ON SCHEMA  prod.sales TO `analysts`;
GRANT SELECT      ON SCHEMA  prod.sales TO `analysts`;   -- 配下のテーブルに継承される
GRANT SELECT      ON TABLE   prod.sales.orders TO `analysts`;
GRANT MODIFY      ON TABLE   prod.sales.orders TO `etl_sp`;

-- 取り消す / 禁止する
REVOKE SELECT ON TABLE prod.sales.orders FROM `analysts`;
DENY   SELECT ON TABLE prod.sales.salary FROM `tanaka@example.com`;

-- いま誰に何が付いているかを見る
SHOW GRANTS ON SCHEMA prod.sales;
SHOW GRANTS `tanaka@example.com` ON TABLE prod.sales.orders;

階層を通り抜ける権限が要る

USE CATALOG → USE SCHEMA → SELECT。 部屋の鍵をもらっても、エントランスと廊下を通れなければ部屋にたどり着けません。 Unity Catalog の3階層で扱った 「住所の形が、そのまま権限の形になる」が、ここで回収されます。

階層必要な権限建物のたとえ
カタログ prodUSE CATALOGエントランスを通る
スキーマ prod.salesUSE SCHEMA廊下を通る
テーブル prod.sales.ordersSELECT部屋の鍵

「SELECT を付与したのに読めない」は、ほぼ USE 権限の不足です。 実務でもよく起きます。逆に USE だけあって SELECT が無いと、 テーブルの存在は見えるのに中身が読めないという状態になります。 この2つの症状の違いは、切り分けの節で使います。

REVOKE と DENY の違い

REVOKE は「取り消す」、DENY は「禁止する」。 グループ経由で権限が来ている人には REVOKE が効きません（個人に直接与えていないため）。 グループから取り消せば、他のメンバーまで読めなくなります。 その人だけ見せたくないときに DENY を使います。

状況打つ手理由
個人に直接与えた権限を外したいREVOKE与えたものを無かったことにするだけで済む
グループ経由の権限を、1人だけ打ち消したいDENYREVOKE では対象がない。グループから外すと他の人が巻き込まれる
特定テーブルだけ、全員に見せたくないREVOKE で整理し直すDENY を積むと、あとで理由が追えなくなる

DENY は GRANT より強いと考えてください。 「GRANT したはずなのに読めない」の原因として、USE 不足の次に疑うのが DENY です。 常用するものではなく、例外を1人だけ切るための道具です。

principal は3種類

principal実体典型的な使い所
user個人アカウント一時的な例外。原則ここには付与しない
groupグループ定石。人事異動があってもメンバーを入れ替えるだけで済む
service principalシステム用の識別子CI/CD やジョブからの自動実行

付与は個人ではなくグループにするのが定石です。 問題文に「個人ごとに権限を付与している」という状況が書かれていたら、 それは改善対象として提示されています。 同じ理由で、CI/CD からの実行に個人のトークンを使うのも避けます。 その人が異動した瞬間にパイプラインが止まります。

UI でも同じことができる

ガイドは using the UI and SQL と、わざわざ両方を挙げています。 Catalog Explorer でテーブルやスキーマを開くと Permissions タブがあり、 principal ごとの権限一覧、付与できる権限の種類、 そしてカタログ→スキーマ→テーブルという階層と継承の状況が表示されます。 試験では SQL の形で出ることが多いですが、 「UI ではできない」と書いてある選択肢は誤りだと判断できます。

Unity Catalog の主要ロール権限を配れるのはオーナーか上位管理者だけ

前節は「どう与えるか」でした。ここは「そもそも誰が与えられるのか」です。

ロールできること守備範囲
アカウント管理者アカウント全体の設定、メタストアの作成、ユーザー・グループの管理アカウント全体
メタストア管理者そのメタストア配下の全オブジェクトを管理、カタログ作成、所有権の移譲データ側（カタログ / スキーマ / テーブル）
ワークスペース管理者そのワークスペースの設定、クラスタ・ジョブの管理環境側（コンピュート / ジョブ）

権限を与えられるのは、オーナーか上位の管理者だけです。 SELECT を持っているだけの人が、他人に SELECT を与えることはできません。 「自分が読めるから、他の人にも読ませてあげよう」は成立しない—— 権限を配る権限は、読む権限とは別物です。ここは素直に出題できるポイントです。

オーナーは既定で「作った人」になる

テーブルを作った人が、既定でそのテーブルのオーナーになります。 自分でテーブルを作れば、自分がオーナーです。 オーナーはそのオブジェクトにフルコントロールを持ち、権限を配ることも削除することもできます。 便利ですが、そのまま運用すると次の事故が起きます。

個人所有のままにすると詰む

田中さんがテーブルを作り、田中さんがオーナーのまま運用が続きます。 そして田中さんが異動・退職すると、誰も権限を変えられなくなります。 メタストア管理者が介入すれば解決しますが、 そういうテーブルが何百個もあれば手に負えません。

-- オーナーをグループへ移譲する
ALTER TABLE  prod.silver.orders OWNER TO `data_engineering_team`;
ALTER SCHEMA prod.silver        OWNER TO `data_engineering_team`;

定石はオーナーをグループへ移譲すること。権限を個人ではなくグループに付与するのと同じ発想です。 人に紐づけると、人がいなくなったときに壊れます。

逆引き

やりたいこと必要な立場
メタストアを作成したいアカウント管理者
カタログを作成したいメタストア管理者
自分が作ったテーブルの権限を他人に与えたいオーナー（＝自分）が GRANT
SELECT だけ持つ人が権限を配ろうとしているできない。オーナーではないため
担当者の異動で権限変更ができなくなったオーナーをグループへ移譲
クラスタの設定を変えたいワークスペース管理者

切り分けの軸は「データの話（メタストア側）か、環境の話（ワークスペース側）か」。 カタログ・スキーマ・テーブルの話ならメタストア側、 クラスタ・ジョブの話ならワークスペース側で、管理する人が違います。

行レベルセキュリティと列マスキングGRANT では作れない制御

GRANT は「読める / 読めない」の二択しか作れません。 「営業は自分の担当地域の行だけ」「分析チームにはメールアドレスを伏せて」には応えられず、 従来はテーブルやビューを分けるしかありませんでした。 その結果、同じデータが複数箇所にコピーされ、 元テーブルを直すたびに全部を直して回ることになります。

行フィルタと列マスクを使うと、1つのテーブルのまま、見る人によって中身が変わります。 行を絞るのが row filter、値を隠すのが column mask です。

どちらも「関数を作る → 適用する」の2ステップ

構文の細部を忘れても、この形さえ覚えていれば思い出せます。 row filter はテーブルに適用、column mask は列に適用。 関数はテーブルと同じく Unity Catalog のスキーマの下に置き、 catalog.schema.function の3階層で修飾します。

row filter — 行を絞る

-- ① 判定する関数を作る（true を返した行だけが見える）
CREATE FUNCTION prod.sec.region_filter(region STRING)
RETURN is_account_group_member('admin') OR region = 'JP';

-- ② テーブルに適用する
ALTER TABLE prod.silver.orders
SET ROW FILTER prod.sec.region_filter ON (region);

-- 外す
ALTER TABLE prod.silver.orders DROP ROW FILTER;

admin グループの人には全行が見え、それ以外には region = 'JP' の行だけが見えます。 ON (…) には関数に渡す列を並べます。 複数列を渡せば、条件を組み合わせられます。

-- 複数条件：担当者本人 or 管理職 or 監査グループ
CREATE FUNCTION prod.sec.order_visibility(region STRING, owner_email STRING)
RETURN is_account_group_member('admin')
    OR is_account_group_member('auditor')
    OR owner_email = current_user()
    OR (is_account_group_member('sales_jp') AND region = 'JP');

ALTER TABLE prod.silver.orders
SET ROW FILTER prod.sec.order_visibility ON (region, owner_email);

column mask — 値を隠す

-- ① マスクする関数を作る（列の値を受け取り、置き換えた値を返す）
CREATE FUNCTION prod.sec.mask_email(email STRING)
RETURN CASE WHEN is_account_group_member('pii_reader') THEN email
            ELSE '***@masked' END;

-- ② 列に適用する
ALTER TABLE prod.silver.customers
ALTER COLUMN email SET MASK prod.sec.mask_email;

-- 外す
ALTER TABLE prod.silver.customers ALTER COLUMN email DROP MASK;

マスクは「全部隠す」だけではありません。 部分的に残す、粒度を落とす、といった作り方もできます。 「完全に見せない」か「そのまま見せる」かの二択でない点が、GRANT との決定的な違いです。

-- 部分マスク：ドメインだけ残す
CREATE FUNCTION prod.sec.mask_email_domain(email STRING)
RETURN CASE
  WHEN is_account_group_member('pii_reader') THEN email
  WHEN email IS NULL THEN NULL
  ELSE '***@' || split_part(email, '@', 2)
END;

-- 粒度を落とす：生年月日を「年」だけにする
CREATE FUNCTION prod.sec.mask_birth(d DATE)
RETURN CASE WHEN is_account_group_member('pii_reader') THEN d
            ELSE date_trunc('YEAR', d) END;

判定に使う関数

関数返すもの使い方
is_account_group_member('グループ名')そのユーザーが指定グループのメンバーか（true / false）いちばんよく使う。グループ単位で見せ方を分ける
current_user()実行中のユーザー名「担当者列が自分と一致する行だけ」のような本人限定

グループで分けるなら is_account_group_member、 本人だけに絞るなら current_user()。 ガイドの記述が based on user groups となっているとおり、 出題の中心はグループ判定のほうです。

判別の一文

「件数は見せてよいか」。

row filter は行が消えるので件数も変わります。取引の存在自体を隠したいときはこちら。
column mask は行が残り、値だけ変わるので件数は分かります。 顧客数は知ってよいがメールアドレスは見せたくない、ならこちら。

運用上の注意を2つ。 ①関数を参照するユーザーに EXECUTE を配る必要はありません。 呼び出すのは Unity Catalog 側です。関数を作る側に CREATE FUNCTION が要ります。 ②フィルタやマスクが効いているとき、エラーにはなりません。 結果が静かに減る・変わるだけです。 「0件で返ってくるが権限エラーは出ない」は、権限不足ではなく row filter を疑う場面です。

ABAC ポリシーテーブルごとに設定するのをやめる

Understand Unity Catalog ABAC policies to centrally control row-level filtering and column masking for sensitive data.

ABAC は Attribute-Based Access Control（属性ベースのアクセス制御）の略です。 キーワードは centrally control——一元的に制御する、です。

前節のやり方には限界があります。customers.email、orders.email、 support.email… と1つずつ設定していくと、 新しいテーブルができたときに必ず設定を忘れます。そして忘れたことに気づく仕組みもありません。 気づくのは、たいてい漏れたあとです。

発想の転換

「どの列に設定するか」ではなく「どんな属性の列に効かせるか」。 「PII タグの付いた列は、pii_reader 以外にはマスクする」と1つ書いておけば、 新しい列にタグを付けるだけで自動的に効きます。

仕組みは2つの要素だけ

要素中身誰が用意するか
タグ（属性）列・テーブル・スキーマに付ける目印。pii、confidential などデータを持つチーム。APPLY TAG 権限が要る
ポリシー「このタグには、この制御（マスク関数 / フィルタ関数）」というルールガバナンス側。カタログ / スキーマ単位で定義

タグの付け方

-- 列にタグを付ける
ALTER TABLE prod.silver.customers
ALTER COLUMN email SET TAGS ('pii' = 'email');

ALTER TABLE prod.silver.customers
ALTER COLUMN phone SET TAGS ('pii' = 'phone');

-- テーブル単位・スキーマ単位でも付けられる
ALTER TABLE  prod.silver.customers SET TAGS ('confidential' = 'high');
ALTER SCHEMA prod.silver           SET TAGS ('domain' = 'sales');

-- 外す
ALTER TABLE prod.silver.customers ALTER COLUMN phone UNSET TAGS ('pii');

タグは Catalog Explorer の UI からも付けられます。 付けるだけなら SQL でも UI でもよく、 効かせる仕組み（ポリシー）と分離されているのがこの方式の要点です。 データに詳しい人がタグを付け、ガバナンスの人がポリシーを1本書く、と担当を分けられます。

適用範囲と継承

ポリシーを定義した場所効く範囲
カタログそのカタログ配下の全スキーマ・全テーブル・全列
スキーマそのスキーマ配下の全テーブル・全列
あとから作られたオブジェクトタグが付いていれば自動的に対象になる（設定作業は不要）

ここが継承です。上位に定義したものが下位に降りてきます。 この構造は Predictive Optimization とまったく同じで、 Unity Catalog の3階層が、権限・自動最適化・ABAC に共通の土台になっています。 L1.3 で構造を丁寧にやった理由が、ここで全部つながります。

個別に適用ABAC

新しいテーブル設定し忘れるタグを付ければ自動
ルールの変更全テーブルを回るポリシーを1つ直す
棚卸し全テーブルを確認タグの一覧を見る
適用範囲そのテーブルだけカタログ / スキーマ配下
例外対応書きやすいポリシーの条件かタグ運用で吸収する

棚卸し（「どこに個人情報があるか」）は、 タグを引けば済みます。system.information_schema のタグ関連ビューを SQL でクエリできるので、 「PII タグの付いた列を全カタログから列挙する」といった確認が一発です。 全テーブルを人力で見て回る運用とは、根本的に手間が違います。

ガイドの動詞は understand です。 ポリシー DDL の暗記より、「なぜ個別設定では回らないのか」「タグとポリシーで何が変わるのか」 を説明できるようにしてください。出題は、そこを突いてきます。

「権限をあげたのに使えない」という問題文は、このドメインの定番の出し方です。 症状を3つに分けると、疑う場所が一意に決まります。

切り分けの順序

① 誰として実行しているか → ② 通り抜けられるか → ③ 対象の権限があるか → ④ 打ち消されていないか → ⑤ 内容が絞られていないか

-- ① 誰として実行しているか（ジョブなら SP かもしれない）
SELECT current_user();
SELECT is_account_group_member('analysts');

-- ②③ 何が付いているか、階層ごとに確認する
SHOW GRANTS `alice@example.com` ON CATALOG prod;
SHOW GRANTS `alice@example.com` ON SCHEMA  prod.sales;
SHOW GRANTS `alice@example.com` ON TABLE   prod.sales.orders;

-- ⑤ フィルタ / マスクが付いていないか
DESCRIBE EXTENDED prod.sales.orders;

見落としやすい3つ

① 実行者が本人ではない。 ジョブやパイプラインはサービスプリンシパルとして動きます。 「自分では読めるのにジョブが失敗する」はこれです。権限は SP に付けます。
② エラーが出ないケースがある。 row filter と column mask は権限エラーを出さずに結果を変えます。 「エラーが出ていない＝権限は足りている」とは限りません。
③ 個人に付けたつもりがグループ側で打ち消されている。 DENY は GRANT より強く効きます。

試験の言い回しに直すと—— 「テーブルが一覧に出ない」＝ USE 不足、 「アクセスが拒否される」＝ SELECT 不足か DENY、 「結果が想定と違う」＝ row filter / column mask。 この3行がそのまま選択肢の切り分けになります。

lineage と audit logモノを追うか、ヒトを追うか

判別の一文

lineage は「モノ」を追う（データの流れ）。audit log は「ヒト」を追う（操作の記録）。

この2つは名前が並んで出てくるので混ざりがちですが、 追いかけている対象がまったく違います。 問題文が「どこから来たか」を聞いていれば lineage、 「誰がやったか」を聞いていれば audit log です。

lineageaudit log
記録するものデータの流れ（どのテーブルから作られたか）人の操作（誰がいつ何をしたか）
使い方①上流をたどる：数字がおかしい、どこから来た？個人情報へのアクセス監査
使い方②下流をたどる：この列を消したら何が壊れる？権限が変わった経緯の追跡
粒度列レベルまで追える読み取り・権限変更・削除・ログイン
登録の手間自動で記録される（宣言不要）自動で記録される
提供形態UI で可視化。システムテーブルからも取得可システムテーブルとして SQL で分析できる

lineage は下流方向がいちばん効く

記録されるのは、たとえば bronze.raw_orders → silver.orders → gold.daily_sales → ダッシュボード、といった繋がりです。 ノートブック・ジョブ・ダッシュボードまで含めて自動的に記録され、 「この列は、どの列から作られたか」まで列レベルで追えます。

実務でとくに効くのは下流方向です。 Silver の列を1つ削除したいとき、それを使う Gold やダッシュボードがあるかもしれません。 削除する前に影響範囲が分かる——これが、あって当たり前になると手放せない機能です。 上流方向は「ダッシュボードの数字が変だ。どこで狂ったのか」を遡るときに使います。

audit log は SQL で読める

audit log はシステムテーブルとして提供されます。 ログファイルを探しに行く必要はなく、 普通のテーブルと同じように SELECT でき、集計も結合もできます。

-- 先月、特定テーブルに誰が何回アクセスしたか
SELECT user_identity.email AS who,
       COUNT(*)            AS accesses
FROM   system.access.audit
WHERE  event_date >= current_date() - INTERVAL 30 DAYS
   AND request_params.full_name_arg = 'prod.silver.customers'
GROUP  BY 1
ORDER  BY accesses DESC;
audit log で答えられる問い典型的な用途
誰がこのテーブルを読んだか個人情報へのアクセス監査
誰が権限を変更したか「いつの間にか見られるようになっていた」の経緯追跡
誰がテーブルを削除したか事故の原因究明
誰がいつログインしたか不審なアクセスの検知

マスクをかけていても、「誰が見ようとしたか」の記録は別に必要です。 行フィルタ・列マスク・ABAC が予防だとすれば、 audit log は事後の説明責任を担います。役割が違うので、どちらも要ります。

どちらも Unity Catalog の機能で、 4段構造で言えば「統制」の層にあります。 「UC を使うと何が得られるか」を問う形なら、 権限・リネージ・監査ログの3つが答えの候補です。

確認問題答えを見る前に、口に出して言えるか

スライドも表も見ずに答えてください。 言葉に詰まったところが、そのまま本番で落とす場所です。

  • Q1managed table と external table の違いを、一文で言うと？

    答えを見る

    「DROP TABLE したら実データはどうなるか」。managed は消える、external は残る。理由は、managed は Unity Catalog が保存場所を決めて実体を管理しているのに対し、external は LOCATION にあるデータを登録しているだけだから。作るときの分かれ目は LOCATION を書いたかどうか、確認は DESCRIBE EXTENDED の Type 欄。

  • Q2external table を managed に変換したくなる、代表的な動機は？

    答えを見る

    Predictive Optimization の対象にしたいから。自動最適化の対象は managed table。ガイドにも convert between managed and external tables と書かれており、一度決めたら変えられない、ではない。

  • Q3公式サンプル問題：analyst グループに sales_data スキーマの読み取り専用アクセスを与える。正解の SQL と、他が誤りである理由は？

    答えを見る

    正解は GRANT SELECT ON SCHEMA sales_data TO analysts。ALL PRIVILEGES は広すぎる、INSERT は種類が違う（書き込み）、ON ALL TABLES IN SCHEMA は対象の書き方が違う。スキーマへの付与は配下に継承され、あとから作られたテーブルにも効くので列挙は不要。

  • Q4テーブルに SELECT を付与したのに読めない。まず疑うのは何か。また「一覧にすら出てこない」場合はどうか？

    答えを見る

    どちらも USE CATALOG / USE SCHEMA の不足。階層を通り抜ける権限が必要で、USE CATALOG → USE SCHEMA → SELECT が揃って初めて読める。SELECT だけ足りないなら「見えるが読めない（権限エラー）」、USE が足りないなら「そもそも見えない」。次に疑うのは DENY。

  • Q5REVOKE ではなく DENY を使うのはどんなときか？

    答えを見る

    グループ経由で来ている権限を、特定の1人だけ打ち消したいとき。個人に直接与えていないので REVOKE は効かず、グループから取り消すと他のメンバーまで巻き添えになる。DENY は GRANT より強く効くので、常用ではなく例外を切る道具として使う。

  • Q6row filter と column mask、件数が変わるのはどちらか。判別の一文は？

    答えを見る

    row filter。行そのものが結果から消えるので COUNT(*) も変わる。column mask は行が残り値だけ置き換わるので件数は変わらない。判別の一文は「件数は見せてよいか」。見せてよいなら column mask、レコードの存在ごと隠すなら row filter。どちらも関数を作る → 適用するの2ステップで、row filter はテーブルに、column mask は列に適用する。

  • Q7行フィルタ・列マスクの判定に使う関数を2つ挙げ、使い分けを言うと？

    答えを見る

    is_account_group_member('グループ名') と current_user()。グループ単位で見せ方を分けるなら前者、本人が担当する行だけに絞るなら後者。ガイドの記述が based on user groups なので、出題の中心はグループ判定のほう。

  • Q8ABAC が個別の行フィルタ・列マスクより優れている点は？

    答えを見る

    「どの列に設定するか」ではなく「どんな属性（タグ）の列に効かせるか」で書けること。結果として、① 新しいテーブルはタグを付けるだけで自動的に効く（設定漏れが起きない）、② ルール変更はポリシーを1つ直すだけ、③ 棚卸しはタグ一覧を見ればよい、④ カタログ / スキーマ単位で定義し配下に継承される。ABAC は行フィルタ・列マスクの代わりではなく、一元的に配る仕組み。

  • Q9lineage と audit log、追う対象の違いは？　また「この列を消したら何が壊れるか」を知りたいときはどちらか。

    答えを見る

    lineage は「モノ」（データの流れ）、audit log は「ヒト」（操作の記録）。影響範囲を知りたいときは lineage の下流方向。上流方向は「数字がおかしい、どこ由来か」に使う。lineage は自動記録で列レベルまで追え、audit log はシステムテーブルとして SQL で集計できる。

  • Q10このドメインで範囲外になったのは何と何か？

    答えを見る

    Delta Sharing と Lakehouse Federation。新しいガイドに記載自体がない。代わりに行レベルセキュリティ・列マスキング・ABAC、そして managed / external の相互変換が入った。

3つ以上詰まったら、順番に戻ってください。 managed と external → GRANT → 行フィルタと列マスク → ABAC → lineage と audit log。 このドメインは判別の一文が全部で4つあります。 そこだけは、暗記ではなく言えるようにしておいてください。
