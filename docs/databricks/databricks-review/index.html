この試験は何を測るか暗記ではなく、要件から機能を選ぶ判断

この試験は、機能の定義を答えさせません。業務のシナリオを読ませ、そこから要件を抽出して、 適切な機能を選ばせます。たとえば「VACUUM とは何か」ではなく、 「ストレージ使用量を削減したい。ただし Time Travel は今後も使う。このとき取るべき行動は」 という形で来ます。

基本スペックと、それが学習に与える制約

項目値学習への影響
採点対象の問題数45問1ドメインをまるごと落とすと、それだけで合格圏から外れる
試験時間90分1問あたり約2分。思い出す時間はなく、判断が反射で出る必要がある

受験料USD 200不合格でも再受験は同額。1回で通す前提で仕上げる
前提資格なし誰でも受けられる。ただし実務6か月相当の経験があることが想定されている
有効期間2年再認定は「そのときの現行試験」を受け直す。範囲は今後も動く

ここで効いてくるのが 45問 ÷ 90分 = 1問あたり約2分 という数字です。 2分は、問題文を読み、要件を掴み、選択肢を切り、答えを選ぶまでの全部です。 考え込んで正解にたどり着く力ではなく、判断が反射で出てくる状態が求められます。 本シリーズのゴールもそこに置いています。

作るべきは、機能と目的の「二方向」

学習も、機能名と説明文をセットで覚えるのではなく、次の二方向を作ることになります。 片方向しか作っていないと、機能名を見れば説明できるのに、問題文からは引けない、という状態になります。

  • 機能 → 目的：この機能は、どんな困りごとを解決するために存在するのか
  • 要件 → 機能：こういう困りごとが書かれていたら、どの機能か

本番で使うのは 後者だけです。前者は理解の確認、後者は得点の道具、と役割が違います。 仕上げ用の逆引き表は、この後者を1枚にまとめたものです。

誤答の作られ方 — 公式サンプル問題を分解する

公式が公開しているサンプル問題に、「新しいレコードを既存の Delta テーブルに追加したい」というものがあります。 選択肢は次の4つです。

① UPDATE VALUES (...) my_table
② UPDATE my_table VALUES (...)
③ INSERT VALUES (...) INTO my_table
④ INSERT INTO my_table VALUES (...)     ← 正解

注目してほしいのは、誤答が「まったく知らない機能」で作られていないことです。 違いは 動詞が UPDATE か INSERT か、INTO の位置がどこか、 その程度しかありません。③は INTO が1語ぶんずれているだけです。

「なんとなく正しそう」で選ぶと落ちる

似た形が4つ並んでいて、差は語順や単語1つ。これがこの試験の基本的な作りです。 だから本シリーズでは、正しいコードを1つだけ見せる、という書き方をしません。 正解と典型的な誤答を並べ、どこが違うのかを指摘します。その形で覚えたほうが本番で効きます。 誤答の型そのものは6種類に分類できるので、 仕上げの段階で型として覚えてしまうのが早道です。

合格ラインは公式に公表されていません。本シリーズでは 45問中32問（約70%）を安全圏の目安として扱っています。 これは「70%取れれば受かる」という保証ではなく、模試の到達度を測るための内部基準です。

2026年5月改訂の要点古い教材を使うと、丸ごと無駄になる範囲がある

2026年5月4日に、試験が 5セクションから7セクションへ 再編されました。 市販の教材・問題集・対策ブログの多くは、まだ旧構成のままです。 内容が誤っているわけではありませんが、新しく入った範囲が丸ごと抜けています。 抜けているものは、読んでいても気づけません。「載っていない」ことに気づく方法が無いからです。

扱い数項目

最大の要注意点 — ZORDER BY

旧版では「特定列での検索が遅い → OPTIMIZE ... ZORDER BY」が定番の答えでした。 新しい試験ガイドの本文に ZORDER BY の記載はありません。 明記されているのは Liquid Clustering と Predictive Optimization です。 手動で最適化する時代から、自動で最適化される時代へ、という方向で答えが入れ替わっています。 捨てる必要はありませんが、主役ではなくなりました。選択肢に両方が並んでいたら Liquid Clustering を選びます。

判定は「30秒で言えるか」

考え込んでから言えるのは、本番では言えないのと同じです。1問2分の試験なので、 要件を読んでから機能名が出るまでに使える時間は十数秒しかありません。 詰まったら、その場で該当ページに戻る。戻る場所を上の表に書いてあるのはそのためです。

読む順序後ろのページが前のページを回収する構造

順番に読む前提で構成しています。後ろのページが、前のページの内容を別の角度から回収するためです。 飛ばして読むと、2回当たるはずの内容に1回しか当たりません。

前半
基盤 → 取り込み → 変換。ここまでで範囲の半分近く。時間をいちばんかける場所です。
後半
Jobs・CI/CD → 監視と最適化。新範囲が集中し、古い教材が効かない領域です。
仕上げ
ガバナンス → 試験の解き方。逆引き表と誤答パターンで、判断を反射に落とします。

回収の例

  • 変換 → 最適化：ジョインの書き方を学んだあと、 「なぜこのジョインは遅いのか」として戻ってきます。答えは書き方ではなく、 データの偏りとシャッフルの話に変わります
  • 取り込み → Jobs：取り込み方式を学んだあと、「いつ動かすか」として戻ってきます。 ファイル到着で起こすのか、時刻で起こすのか、という別軸が足されます
  • 基盤 → 変換：Delta が更新を上書きしない仕組みが、 DELETE しても容量が減らない理由になり、そのまま VACUUM の必要性につながります
  • 基盤 → ガバナンス：Unity Catalog の3階層が、 GRANT の粒度と USE CATALOG の必要性として戻ってきます

つまずいたときの戻り方

間違いには3種類あり、対処がまったく違います。まず種類を判定してから戻ります。

最重要は略称の2つ — DLT と DAB

この2つは略称のまま流通しています。3文字の略語なので、記事の中に突然出てくると 何のことか分かりません。DLT はパイプライン、DAB はデプロイの仕組み。 これに Repos → Git folders、Workflows → Lakeflow Jobs を足した4つを押さえておけば、 調べ物でつまずくことはほとんどなくなります。

Hive metastore だけは性質が違います。改名ではなく、別の仕組みへの移行です。 古い環境では今も Hive metastore が動いていることがあり、その前提で書かれた記事も残っています。 試験では Unity Catalog 前提で考えてください。

改名されていないもの（古い記事をそのまま読める）： Delta Lake / Auto Loader / Structured Streaming / MERGE / OPTIMIZE / VACUUM / Expectations / COPY INTO。 3年前の記事でも、名前に関しては問題なく読めます。 ただし名前が同じでも、推奨されるやり方が変わっている場合があります。 ZORDER BY から Liquid Clustering への流れがまさにそれで、 「名前が同じ＝今も最善手」ではない点は切り分けて読んでください。

試験ガイド自身にも表記揺れがある

同じものが Automation Bundle (formerly Databricks Asset Bundles) と Declarative Automation Bundles (formerly Databricks Asset Bundles) の 2通りで書かれている箇所があります。Declarative が付いたり付かなかったり、単数だったり複数だったり。 どちらも同じもので、formerly Databricks Asset Bundles が付いていれば同一と判断して構いません。 公式ドキュメントですら揺れていると知っておくと、本番で選択肢の表記に迷わなくなります。

やり直しにはなりません。Delta Lake・Auto Loader・MERGE・メダリオンなどの中核は変わっていないためです。 必要なのは差分の手当てだけで、具体的には ①Delta Sharing と Lakehouse Federation を飛ばす、②旧称を新称に読み替える、 ③CI/CD・Spark UI 診断・Liquid Clustering・ABAC を新規に足す、の3つです。 古い教材の使い方を参照してください。
実務経験は必要か
前提資格はなく、実務経験も受験要件ではありません。ただし6か月相当の経験があることが想定された 問題文の書き方をします。「本番ジョブ」「日次バッチ」「BI から参照される」といった状況が説明なしに出てきます。 経験がない場合は、機能を覚える前に「その機能が誰の、どんな作業を楽にするのか」を 各ページの冒頭で確認してから読み進めてください。
教材は何を使うか
一次資料は公式 Exam Guide のみです。それ以外はすべて二次情報で、 2026年5月4日より前に書かれたものは新範囲が抜けていると考えてください。 判断基準は単純で、目次に CI/CD と Troubleshooting が独立して立っていなければ旧版向けです。
手を動かせる環境がない
この試験は選択式なので、コードは「書く」ではなく「読んで選ぶ」で対策が成立します。 本シリーズも正解1つと典型的な誤答を並べる形で書いてあります。 ただし Auto Loader のチェックポイント挙動や MERGE の副作用など、 「やって初めて分かる」型の理解は薄くなります。後で実務に使うなら、 取り込みと変換だけは別途触っておくと差が出ます。
何問取れば受かるか
合格ラインは公表されていません。本シリーズは 45問中32問（約70%）を目安に置いています。 模試で30問前後なら、落とした問題を上の 4種類に分類してから戻るのが最短です。 「もう一周読む」は、③読み落としが原因のときには効きません。
UI の画面は覚えるべきか
操作手順の再現は目的になりません。問われるのは 「どの画面のどの数字を見て、何を判断するか」です。 Lakeflow Jobs の run history、Spark UI の stage 指標、bundle の YAML、Unity Catalog の権限画面の4つは、 文字だけだと記憶に残りにくいので、実際の画面を一度は見ておく価値があります。
有効期間が切れたら
2年で失効し、再認定はそのときの現行試験を受け直す形になります。 今回のような改訂が今後もある前提です。だからこそ、機能名の暗記ではなく 「この要件にはこの種類の解決策」という形で覚えておくほうが持ちます。

確認問題ここで詰まったら、該当ページを先に読む

各ページに入る前の足切りです。答えを見る前に、口に出して言ってみてください。 言えなかった問題のリンク先が、あなたが最初に読むべきページです。

  • Q1大きなテーブルで、特定の列による絞り込みが遅い。2026年5月版の試験ガイドが想定している答えはどれか。

    答えを見る

    Liquid Clustering（CLUSTER BY）。旧版の定番だった OPTIMIZE ... ZORDER BY は、新ガイドの本文に記載がありません。選択肢に両方が並んでいたら Liquid Clustering を選びます。→ Liquid Clustering

  • Q2検索して出てきた記事が「DLT」という機能を解説している。試験ガイドに DLT の記載はない。これは範囲外か。

    答えを見る

    範囲内です。DLT（Delta Live Tables）は Lakeflow Spark Declarative Pipelines の旧称です。同様に DAB は Declarative Automation Bundles、Repos は Git folders、Workflows は Lakeflow Jobs の旧称。→ 旧称→新称 対応表

  • Q3旧版向けの問題集でガバナンス領域を一周した。どこが空振りになり、何が抜けているか。

    答えを見る

    空振りは Delta Sharing と Lakehouse Federation（新ガイド本文から削除）。抜けているのは 行レベルセキュリティ・列マスキング・ABAC ポリシーです。旧版ではガバナンスのかなりの分量が削除済みの2つに割かれていました。→ このドメインの範囲

  • Q4「ストレージ使用量を削減したい。ただし Time Travel は今後も使う」。このとき何を確認してから VACUUM するか。

    答えを見る

    どこまで過去に戻れれば足りるか（保持期間）を先に決めます。VACUUM は保持期間より古い、参照されていないファイルを物理削除するため、その期間より前のバージョンには戻れなくなります。「削減したい」だけを読んで保持期間を無視する選択肢が典型的な誤答です。→ VACUUM と Time Travel

  • Q5次の3つを取り込み方式に振り分けよ。(a) クラウドストレージに新着ファイルが継続到着し、ファイル数が数百万規模／(b) 既知のファイル群を SQL だけで冪等にロードしたい／(c) Salesforce や SQL Server から企業データを取り込みたい。

    答えを見る

    (a) Auto Loader、(b) COPY INTO、(c) Lakeflow Connect。判断材料は「ファイルか、ファイルでないか」「新着を検出し続けるのか、既知の集合か」の2軸です。→ 【判別】どれを選ぶか

  • Q6毎晩定時に走り、終わったら停止してよい本番 ETL。どのコンピュートを選ぶか。また、対話的にノートブックで探索する場合と、BI ダッシュボードから参照する場合は。

    答えを見る

    本番 ETL は Job Compute、対話的な探索は All-Purpose Compute、BI / SQL 分析は SQL Warehouse。運用そのものを手放したい場合は Serverless。判断軸は「人が使うのか、機械が使うのか」「終わったら止めてよいのか」です。→ コンピュートの選び方

  • Q7同じコードを dev / test / prod の3環境へ展開したい。新しい試験ガイドが想定している仕組みは何か。

    答えを見る

    Declarative Automation Bundles（旧 Databricks Asset Bundles）の variables と targets。YAML でジョブやパイプラインを定義し、Databricks CLI の validate / deploy / run で流します。ノートブックを環境ごとにコピーする選択肢は誤答です。→ Automation Bundles

  • Q8クエリが遅い。Spark UI を見ると、同じ stage の中で1つのタスクだけ極端に長い。ノードを増やせば解決するか。

    答えを見る

    しません。1つのタスクが重い状態（data skew）なので、並列度を上げても、その1タスクの実行時間は変わりません。この「遅い → 増強すれば直る」という誘導は、この試験で最も繰り返し出る誤答パターンです。→ 誤答は6種類しかない

8問中6問以上を答えを見ずに言えたなら、 改訂差分から順に通読して構いません。 5問以下なら、言えなかった問題のリンク先を先に読んでから1周目に入るほうが早く済みます。
