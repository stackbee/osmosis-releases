Liquid Clusteringの内部イメージ

クラスタリングキーの多次元的な「近さ」を保ちながらデータをファイルへ寄せ、 しかも必要な部分だけを増分的に再配置する仕組み。 固定ディレクトリを切る Partitioning とも、都度大きく並べ直す Z-ORDER とも違います。

一言でいうと2つの性質
近さを保つ
クラスタリングキーの多次元的な近さを保ちながら、データをファイルへ寄せる
増分で直す
必要な部分だけを増分的に再配置する

この2つを合わせたところが特徴です。固定ディレクトリを切る Partitioning でもなく、都度大きく並べ直す Z-ORDER でもない。その中間にあると考えてください。

何を最適化しているのかmin/maxを狭くする

WHERE purchase_date BETWEEN '2026-08-01' AND '2026-08-07' AND customer_id = 12345 のような検索が多いとき、CLUSTER BY (purchase_date, customer_id) の狙いは両方のキーが近いレコードを同じファイル群へ寄せることです。ファイル単位の min/max が狭くなり、Data Skipping で不要ファイルを落としやすくなります。

ファイルpurchase_datecustomer_id上のクエリで
File A8/1〜8/210000〜15000読む
File B8/1〜8/250000〜55000飛ばせる
File C8/10〜8/1210000〜15000飛ばせる

近い順にどう並べるのか空間充填曲線

2列をそのままソートすると purchase_date → customer_id の辞書順になり、片方の局所性は強くても、もう片方が崩れやすくなります。そこで多次元空間を1本の順序へ写像する Space-Filling Curve（空間充填曲線）を使います。

Z-ORDERとの違い曲線ではなく状態

Z-ORDER も「多次元の値を1次元へ変換して近い値を寄せる」という発想は同じです。本質の差は、別の曲線を使うことではありません。

新しいデータが増えたとき
Z-ORDERその時点の対象データを大きく再配置 → また OPTIMIZE ZORDER
Liquid Clusteringクラスタリング状態を管理 → 必要な部分だけ増分的に再クラスタリング

Liquid Clustering は「状態を持った増分クラスタリング」である。ここが大きな差です。

なぜLiquidなのか境界が固定されない

増分最適化の動き既存に触らない

現在の Databricks 公式ドキュメントでも、Liquid Clustering の OPTIMIZE は必要なデータだけを書き換える増分処理と説明されています。既存 10 TB + 新着 100 GB のケースで比べます。

10 TB の既存データ100 GB の新着
Z-ORDER 的な発想大きな範囲を再度並べ直す必要が出やすいまとめて処理
Liquid Clustering良好なレイアウトはなるべく触らない未整理・影響部分を中心に再クラスタリング

これが write amplification（書き込み増幅）を抑える大きな理由です。

ZCubeという考え方OSS Delta の設計

OSS Delta Lake 3.x の公開設計では、増分クラスタリングを実現するために ZCube という単位が使われます。ざっくり言えば「同じ OPTIMIZE で一緒にクラスタリングされたファイル群」という管理単位です。Delta Log のメタデータで「このファイル群はすでにクラスタリング済み」という状態を追跡するため、毎回すべてを並べ直す必要がありません。

断定しないこと

これは OSS Delta Lake の公開実装・設計の説明です。Databricks Runtime の Liquid Clustering は OSS Delta と完全に同一実装ではないと Databricks 社員からも説明されているため、「Databricks の Liquid Clustering ＝ 必ず内部で OSS と同じ ZCube 実装」とは断定しないほうが安全です。

Data Skippingとセットで索引ではない

Liquid Clustering 自体がインデックス検索をするわけではありません。本当の読み取り高速化は、Delta が持つファイル単位統計（min/max）と組み合わさって起きます。

File AFile BFile Ccustomer_id = 15000 なら
クラスタリング前1〜9999992〜9999983〜999997どのファイルも候補になる
クラスタリング後1〜1000010001〜2000020001〜30000File B を中心に読む

Liquid Clustering は、Data Skipping が効きやすいファイル配置を作る技術。

キーを変更できる理由段階的に移行

クラスタリングキーの変更抜粋

ALTER TABLE sales
CLUSTER BY (purchase_date, customer_id);

キーを変えた瞬間に過去データ全部を書き直す必要はありません。以後の書き込みや OPTIMIZE により、新しいレイアウトへ段階的に移行できます。必要なら OPTIMIZE FULL で全体を再クラスタリングする選択肢もあります。

段階的に移れるか、作り直しになるか。ここが Partitioning と大きく違うところです。

Automatic Liquid Clusteringキー選択も任せる

一言で覚えるDEA向け
仕組み一言で

Liquid Clustering近い値をファイルへ寄せる状態管理型・増分クラスタリング

複数キー → 多次元空間 → 近さを保つ順序へ変換 → 似たデータを近いファイルへ → ファイル統計の min/max が狭くなる → Data Skipping が効く → OPTIMIZE は必要部分だけ増分的に再配置。

Databricks の公開ドキュメントで確実に言えるのは、キーに基づきレイアウトを整理する / Partitioning と ZORDER を置き換える / OPTIMIZE は増分的 / キーを後から変更できる / Automatic ではキーを自動選択できる の5点です。
