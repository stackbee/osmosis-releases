Auto Loaderの実行パターンを具体例で

Auto Loader は、単純に「常時待ち受ける仕組み」と考えると分かりづらくなります。 Auto Loader がどう新着ファイルを処理するかと、Job や Pipeline が Auto Loader をいつ動かすかは別の話です。

常時待ち受けと考えない今回の軸

実運用では、主に次の3パターンで考えると整理しやすいです。 常時ストリーミング型。定期バッチ型。File arrival trigger と Auto Loader の組み合わせ。

Auto Loader の仕事
まだ処理していないファイルを特定して読む
Job / Pipeline の仕事
その Auto Loader をいつ、どのくらいの期間動かすか決める
3つの違いはどこか
同じ Auto Loader を使っていても、Job の起動方法と Streaming Query の寿命が違うだけ

実行パターンは3つ全体像

数秒おきに注文が届く① 常時ストリーミング型のシナリオ

EC サイトで注文イベントが数秒おきに発生し、JSON ファイルとして S3 に到着するとします。

到着時刻ファイル置き場所
10:00:03orders_100001.jsons3://shop-data/orders/incoming/
10:00:08orders_100002.json
10:00:15orders_100003.json

要件は「注文データが来たら、数十秒〜数分以内に Databricks に取り込みたい」。 この場合は、Auto Loader を長時間動かし続ける構成が自然です。

クエリはいつ始まるかNotebook に書かれるコード

 
df = (spark.readStream.format("cloudFiles")
        .option("cloudFiles.format", "json")
        .load("s3://shop-data/orders/incoming/"))
(df.writeStream.format("delta")
   .option("checkpointLocation", "s3://shop-data/checkpoints/orders/")
   .toTable("bronze.orders"))

readStream だけでは処理はまだ始まりません。 実際に Streaming Query が稼働し始めるのは、writeStream 側でクエリを開始した後です。

checkpointLocation に何が記録されているかは第35回で扱いました。 cloudFiles.schemaEvolutionMode によるスキーマ変化の扱いは第36回です。ここでは深追いしません。

処理が終わっても終了しないStreaming Query の寿命

人間が開きっぱなしにするのではないここは特に重要
誰が動かすかNotebook の役割結果
開発時人間セルを実行して確認する画面人間が見ている間だけ動く
本番Databricks JobJob から実行されるプログラムStreaming Query が長時間稼働

開発時には、確かに人間が Notebook を開いてセルを実行します。しかし本番では、Notebook は単なる「人間向け画面」ではありません。 人間が待っているわけではなく、Databricks 側の Job / Compute がストリーミング処理を動かし続けます。

1時間に1回で十分なとき② 定期バッチ型のシナリオ

全国100店舗から、POS の売上 CSV が ADLS に随時送られてくるとします。

到着時刻09:0509:1209:2009:4409:58
ファイルstore_001store_034store_087store_012store_055

しかしビジネス要件は「リアルタイムでなくていい。1時間に1回集計できれば十分」というものだとします。 この場合、Auto Loader を24時間動かし続ける必要はありません。 例えば Lakeflow Jobs を、毎時00分に実行します。

あるだけ処理して終わるAvailableNow のイメージ

定期バッチ型では、Auto Loader を「ずっと待つ」ようには使いません。 AvailableNow の考え方を使うと、今この時点までにある未処理ファイルを全部処理したら終了するという動きになります。

時刻起きること
10:00Job 起動 → Notebook 実行 → Auto Loader 起動
Checkpoint や新着ファイル情報を見て、まだ処理していないファイルを判断 → 5ファイルを処理
Delta に書き込み → Checkpoint 更新
10:03Job 終了。ここで Auto Loader も終了します

09:00 から 10:00 の間に来ていた store_001 から store_055 までの5本を、まとめて処理したことになります。

止まっている間に来ても平気取りこぼさない理由

来た時だけ動かす③ File arrival trigger と Auto Loader

もう1つ、非常に分かりやすい構成があります。それが、ファイルが到着したことを契機に Job を起動する構成です。 例えば ADLS に、13:17 に orders_5001.json が到着したとします。

13:17ファイル到着 → File arrival trigger が新着を認識 → Job 起動
Auto Loader が未処理ファイルを読む → Delta に書き込む → Job 終了

ファイルが来たら、その時だけ取り込み処理を動かすというモデルです。 Auto Loader を常時動かす必要はありません。また、1時間ごとの固定スケジュールを待つ必要もありません。

File arrival trigger そのものの仕組みと、Auto Loader の File Notification との違いは第60回で扱いました。

3パターンの比較ここが最重要
観点常時 Streaming定期バッチFile arrival + Auto Loader
Job長時間稼働毎回起動して終了ファイル到着で起動して終了
Auto Loader動き続ける必要な時だけ動く必要な時だけ動く
新着処理ほぼ継続的起動時に未処理分をまとめてファイル到着を契機に処理
レイテンシ秒〜分例えば最大1時間比較的短い
Compute基本稼働継続実行時のみ実行時のみ
典型例注文、IoT、ログ日次・時間単位の売上到着契機のファイル処理

たとえで覚える3つの店番
パターンたとえAuto Loader の動き
常時 Streamingコンビニ。ずっと店を開けていて、客が来たらすぐ対応長時間稼働させて、ファイルが来たらすぐ処理する
定期バッチ郵便受けを定期的に見に行く。1時間に1回見て、入っている郵便を全部回収1時間ごとに起動し、未処理ファイルをまとめて読む
File arrival trigger郵便が来たらインターホンを鳴らしてもらう。鳴った時だけ見に行くtrigger が Job を起動し、その Job の中で Auto Loader が取り込む

ファイルイベントの位置づけ役割を分ける

最後に一言で整理覚え方
パターン一言で
常時 StreamingAuto Loader をずっと動かす
定期バッチAuto Loader を定期的に起動して未処理分だけ処理する
File arrival triggerファイルが来た時だけ Job を起動し、その中で Auto Loader を動かす

File Events は「いつ Job を起動するか」ではなく、Auto Loader が「どのファイルが新着か」を効率よく知るための仕組み。 この役割分担で考えると、常時 Streaming・定期バッチ・File arrival trigger の違いが整理しやすくなります。
