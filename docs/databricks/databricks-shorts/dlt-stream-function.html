STREAMは読む側の指定

DLT（現 Lakeflow Declarative Pipelines）の SQL で、STREAM(...) は 入力テーブルを増分ソースとして読むための指定です。 CREATE STREAMING LIVE TABLE のほうは出力側に何を作るかの指定で、 役割が違います。

作る側と読む側役割が違う

例を読んでみる1文に両方入る

DLT / SQL全文

CREATE STREAMING LIVE TABLE loyal_customers AS
SELECT customer_id
FROM STREAM(LIVE.customers)
WHERE loyalty_level = 'high';
テーブル立場どこで指定されているか
loyal_customers作られる側CREATE STREAMING LIVE TABLE
customers読まれる側STREAM(...) で増分ソースとして読む

STREAMを付ける意味新着分だけ

STREAM(LIVE.customers) は、customers を毎回まるごと読み直すのではなく、前回の処理以降に追加・到着した分を増分として扱うという意味です。

付けない場合との違い書き方で変わる
書き方どう読まれるか
FROM LIVE.customers通常のテーブル参照として扱われる
FROM STREAM(LIVE.customers)この入力をストリーミング／増分ソースとして読む、という宣言になる

同じテーブルを指していても、書き方で読み方が変わります。ここが要点です。

試験での見分け方読む側を見る

STREAM(...) を付ける理由を聞かれたら、まず読む側のテーブルを見ます。紛らわしい選択肢は、どちらも出力側やデータの状態に目を向けさせるものです。

選択肢
✗出力テーブルが streaming table だから
✗データがたまたま更新されたから
○参照している入力テーブルをストリーミングソースとして増分で読むため

STREAM は読む側、CREATE STREAMING LIVE TABLE は作る側。前者は「どう読む？」、後者は「何を作る？」に答えています。
