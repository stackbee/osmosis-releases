ETL と ELT を具体的に理解する

違いは一点だけ。Transform を Load の前にやるか、後にやるか。 Databricks ではどう実現するのか、Bronze / Silver / Gold まで具体的に追いかけます。

まず一言で違いは一点

具体例：EC の注文データ題材

元データ（CSV）5行

order_id, customer_id, amount, order_date, status
1001, C001, "1,200", 2026/08/18, completed
1002, C002, "900",   2026/08/18, completed
1002, C002, "900",   2026/08/18, completed   ← 重複
1003, C003, NULL,    2026/08/18, cancelled
整える
amount を文字列 → 数値／日付を標準フォーマットへ／重複行を除去／NULL の扱いを決める／cancelled を除外
足す
customer master と JOIN／店舗別・日別に集計／売上、平均単価、顧客ランクなどの派生列を作る

これらがまとめて Transform。ETL と ELT は、この作業をどこで、いつやるかだけが違います。

ETL は先に変換するタイミング

変換してから保存先へ入れる。元DBから注文データを取り出したあと、ETLサーバーやETLツール上で整形・結合・集計し、完成したデータだけをDWHへ入れる。

ETL の利点と弱点両面

メリット

保存先には最初から整ったデータだけ入る。不要データを持ち込まずに済む。昔のDWHではよく使われた形です。

デメリット

Transform用の別コンピュートが必要。元データを削りすぎると後から再利用しにくい。変換ロジック変更時に、元データから取り直しが必要になることがある。

手元に残っているのが変換後のデータだけだと、やり直しの起点が自分の外にしかない、ということになります。

ELT はまず保存するタイミング

まず生データを保存して、その後で変換する。PostgreSQL から取ったデータをまず Bronze に入れ、その後 Databricks 上で Silver / Gold を作ります。

Databricks とメダリオンなぜ自然か

Databricks では、ELT 的な設計がかなり自然。理由は、Lakehouse 自体が大量データの保存場所でもあり、Spark / Photon で変換処理もできるから。置く場所と計算する場所が同じところにあります。

Bronze
生データに近い状態
Silver
検証・整形・重複除去・JOIN
Gold
集計・BI向け・業務指標

まず Bronze へ Load し、その後 Databricks 上で Transform する。この流れは ELT 的。

Extract して Bronze へ具体例 1・2
1. Extract
PostgreSQL / MySQL、SaaS、REST API、S3 / ADLS / GCS、Kafka / Event Hubs から取得。道具は Lakeflow Connect、JDBC、Auto Loader など
2. Load
まず Raw に近い状態で Delta に保存。source orders → Bronze.orders_raw。ここでは変換は最小限

Bronze でやってよいこと

列名を最低限整える／ingestion timestamp を付ける／source file 名を記録する／JSON をそのまま VARIANT で保持する。データの中身は削らない。

Silver と Gold を作る具体例 3・4
3. → Silver
Bronze.orders_raw → Silver.orders_clean。型変換／NULL処理／重複除去／異常値除去／CDC反映／customer masterとのJOIN／schema整形
4. → Gold
Silver.orders_clean → Gold.daily_sales。日次売上／顧客LTV／商品カテゴリ別売上／KPI／BI向けマート

Silver（PySpark）→ Gold（SQL）5行

silver = (bronze.dropDuplicates(["order_id"]).filter("status = 'completed'")
    .withColumn("amount", col("amount").cast("decimal(10,2)")))
SELECT order_date, store_id, SUM(amount) AS total_sales,
       COUNT(*) AS order_count, AVG(amount) AS avg_order_value
FROM silver.orders_clean GROUP BY order_date, store_id;

呼び名としての ETL言葉の罠

Databricks で ETL もできるのか。できる。公式ドキュメントでも、Lakeflow pipelines や Auto Loader を使った処理を ETL pipeline と呼んでいます。

言葉と物理的な順序はずれる

言葉として ETL と呼んでいても、物理的な処理順序は ELT 的になっているケースが多い。Source → Bronze へ Load → Silver へ Transform → Gold へ Transform、は概念的には ELT です。

試験やドキュメントでは、ETL＝データパイプライン全般を指す広い言葉として使われることもあります。名前で判断せず、Load と Transform のどちらが先かを見ます。

二つを並べて比べる比較
観点ETLELT
処理順序 / Transform場所Extract → Transform → Load ／ 外部ETL基盤Extract → Load → Transform ／ 保存先 / DWH / Lakehouse
Rawデータ保持 / 再処理しないことも多い / 元システムから再取得が必要なことも保持しやすい / Bronzeから再構築しやすい
大規模データ / 相性昔は苦手 / 可能得意 / 非常に良い

Transform の範囲は広い中身

Transform は単なる「加工」ではなく、かなり広い。

分類中身
データ品質NULL除去 / 不正値除去 / 重複除去 / schema validation / expectation
型・形式string → date / string → decimal / timestampのtimezone統一 / JSON展開
構造変更列追加 / 列削除 / rename / explode / pivot / unpivot
データ統合 / 集計JOIN / UNION / MERGE / CDC ／ GROUP BY / SUM / AVG / COUNT / Window Functions
業務ロジック顧客ランク / 解約判定 / 売上区分 / KPI計算 / LTV

Lakeflow pipelines なら Source → Streaming Table（Bronze）→ Materialized View（Silver / Gold）と、SQL / Python で依存関係を宣言してパイプライン化できます。ingestion・変換・JOIN・集計・データ品質チェック・CDC をまとめてオーケストレーションできます。

覚え方とまとめDEA向け

一番短く覚えるなら3行

ETL … T が先 → 変換してから保存
ELT … L が先 → まず保存してから変換
Databricks: Source → Bronze → Silver → Gold

本質的な違いは Transform のタイミング

ETL は先に変換してからターゲットへ Load。ELT はまず Raw を Load して、その後ターゲット側で Transform。Bronze に Raw を保持するため、再処理・再利用しやすい。

Databricks では ELT 的な設計が自然。ただし公式ドキュメントでは、広い意味で「ETL pipeline」と呼ばれることもある——この2つを一組で覚えておくのが実務でも試験でも効きます。
