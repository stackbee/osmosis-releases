AQE は実行しながら計画を変える

AQE（Adaptive Query Execution）は、Spark がクエリを実行しながら実際のデータ量や偏りを見て、実行計画を途中で調整する仕組みです。 本質は、最初に立てた計画を絶対視しないこと。

実行しながら計画を変える予想と現実がずれるから

Spark はクエリを実行する前に実行計画を立てます。この Join は Sort Merge Join にしよう、 Shuffle はこのパーティション数で処理しよう、というように、走り出す前に決めておきます。

ジョインの方式を切り替える働き 1/3

最初は両方のテーブルが大きいと推定されていて、Sort Merge Join が選ばれたとします。 ところが実行中に、片方が実際には十分小さいと分かった。このとき AQE が Broadcast Hash Join に切り替えることがあります。

シャッフルの分割数をまとめる働き 2/3

Spark では GROUP BY や JOIN などで Shuffle が発生します。 このとき最初に細かすぎる数のパーティションを作ると、1つ1つが小さすぎる Task になり、 Task の起動や管理そのものが無駄になります。

データの偏りに対応する働き 3/3

スキューとは、特定のキーにデータが偏ることです。 たとえば customer_id ごとに処理していて、ほとんどのキーは小さいのに1つだけ非常に大きい、という状態です。

最初の計画を絶対視しないAQE の考え方
従来のイメージAQE
計画を立てるのは実行前だけ実行前＋実行中に見直し
根拠にするもの事前の統計（推定）実行中に得た実際の統計
途中で変わるか変わらない。最後までその計画必要なら作戦変更して実行を続ける

一言でいうと、AQE は Spark が実際のデータを見ながら、その場で作戦を修正する仕組みです。

試験で押さえる三つ代表的な働き
働き何を見て何をするか
Join 戦略の変更実行中の実サイズSort Merge Join → Broadcast Hash Join
Shuffle partition の調整実際のデータ量小さいパーティションをまとめる
Skew の最適化パーティションの偏り巨大なものを分割して分散する

Broadcast Join と関連づけるなら、この流れで押さえておくと理解しやすくなります。 最初は Broadcast できるか分からない → 実行中に実サイズが判明 → 十分小さい → AQE が Broadcast Join へ変更する場合がある。

ひとことで覚えるまとめ

AQE = 実行前の予想ではなく、実行中の現実を見て最適化する。

Databricks や Spark のパフォーマンス問題を考えるときは、固定的な実行計画だけを見ていても足りません。 このように実行中にも自動で最適化が働いている、という点が重要です。

「切り替わることがある」「分割する場合がある」という言い方をしているのは、 AQE が必ずそう動くとは限らないためです。実行中に得られた統計が条件を満たしたときに働きます。
