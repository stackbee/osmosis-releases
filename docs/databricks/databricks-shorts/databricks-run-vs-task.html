%run と Task の違い

%run はコードを分割する仕組み、 Task は実行単位を分割する仕組みです。 ノートブックを分けても、Jobs の実行単位は増えません。

分けているものが違う%run と Task

Databricks でノートブックを分割していると、見た目上は処理が複数に分かれているので、 つい「Task も分かれている」と考えたくなります。 しかし %run と Task 分割はまったく別物です。

一番大事な考え方

%run ＝ コードを分割する仕組み
Task ＝ 実行単位を分割する仕組み

%run は何をしているのか1つの Task の中で順番に実行される

ノートブックを複数ファイルに分けても、Jobs の実行単位が自動的に増えるわけではありません。

失敗単位は分かれないTask 1 が失敗、としか見えない

 
%run ./load_data      %run ./clean_data      %run ./aggregate_data
ノートブック実際の状況Jobs から見えるもの
load_data成功Task 1 が失敗（1つの実行単位としてしか見えない）
clean_data失敗
aggregate_data未実行

途中から再開できない

load_data をスキップして clean_data から再実行する、 といった Task 単位の再実行はできません。基本的には最初からやり直します。

Task を分けると切り分けられるA → B → C

 
Job   ├─ Task A: load_data   ├─ Task B: clean_data   └─ Task C: aggregate_data
依存関係:  A → B → C
Taskノートブック結果再実行できるか
Task Aload_data成功成功済みなのでスキップ
Task Bclean_data失敗ここからやり直せる
Task Caggregate_data未実行B のあとに実行される

A、B、C が別々の実行単位になっているので、失敗した Task B からやり直せます。 この「失敗を切り分けられる」という点が、Task を分割する大きな理由の1つです。

並列実行の単位にもならない%run は上から順に動くだけ

%run は「別ノートブックを呼び出す」だけの仕組みです。 並列にしたいなら、Task に分けて依存関係を書く必要があります。

表で整理する共通しているのは1点だけ
観点%runTask
コードを分割できるできるできる
実行単位を分けるできないできる
失敗単位を分けるできないできる
個別再実行できないできる
並列実行の単位になるならないなる
依存関係を持てる持てない持てる
Jobs が別処理として管理するしないする

ノートブックを分ける と Task を分ける最も混同しやすいポイント
ノートブックを分けるTask を分ける
目的コード整理・再利用Jobs の実行構造そのものを分ける
Jobs から見た実行単位必ずしも分かれない分かれる
得られること読みやすさ・再利用しやすさ 失敗箇所の切り分け／Task 単位の再実行／依存関係の定義／独立した Task の並列実行

巨大な1ファイルに全部書くより、役割ごとに分割した方が読みやすく、再利用もしやすくなります。 ただしそれはコード整理の話で、Jobs の実行構造とは別の層の話です。

本にたとえる1冊を章に分ける / 3冊に分ける

 
%run  →  1冊の本   ├─ 第1章   ├─ 第2章   └─ 第3章
Task  →  本A       本B        本C

章が3つに分かれていても、「1冊の本」であることは変わりません。 一方、Task 分割は本そのものを3冊に分けるイメージです。 別々の本なので、本Bだけやり直す・本Bと本Cを同時に処理する・本Aが終わったら本Bを開始する、 といった管理ができます。

試験対策としての覚え方Data Engineer Associate

この区別だけ押さえる

%run はコードの整理・再利用。
Task は Jobs における実行・失敗・再実行・並列化の単位。

「ノートブックを分けた ＝ Task を分けた」ではありません。 失敗単位を分けたい・並列実行したい・依存関係を管理したい場合は、 %run ではなく Task を分けて依存関係を構成する、と考えます。

ひとことで覚えるソースコードの整理 / 実行の整理

これが一番シンプルな理解

%run ＝ ソースコードの整理
Task ＝ 実行の整理

Job・Task・DAG それぞれの定義と、依存を書けば並列が導かれる話は ep056「Job / Task / DAG の全体像」で扱っています。
