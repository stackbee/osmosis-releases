日次バッチETLのシナリオ

シナリオ回の1本目です。個別技術の解説ではなく、「日次バッチETLという状況で、どの部品をどう組み合わせるか」を扱います。 大量のファイルを一定間隔でまとめて取り込み、Bronze → Silver → Gold と段階的に整形し、最終的に BI で使える形にする王道パターンです。

取り込みから配置まで一本道このパターンの本質

シナリオで考えるというのは、部品の仕組みを覚え直すことではありません。要件を聞いたときに、どの部品が要るのか、そしてそれがどういう順番で並ぶのかを言えるようにすることです。

100店舗の POS 売上を毎晩処理する基本シナリオ
要件 1
全国100店舗が毎日閉店後に CSV を ADLS へ送信する
要件 2
翌朝までに売上集計を完成させたい
要件 3
Power BI から店舗別・商品別の売上を見たい

この3つが出そろった時点で、答えの形はだいたい決まります。定期起動があって、取り込みがあって、段階的な整形があって、最後に BI の入り口がある。要件から部品を逆算する——これがシナリオ問題の解き方です。

夜2時に何が動くか1日の流れ

Job・Task・DAG の定義は第56回で扱いました。ここで大事なのは、A から B へ、B から C へという依存を書けば、走る順番は Jobs のほうが決めてくれるという点だけです。3つの Task に分ける理由は2つ——どこで失敗したのかが分かること、そして失敗した段から作り直せること。取り込みは終わっているのに集計だけやり直したい、という形が作れます。

Notebook は人が開くものではないここで大事な理解

Notebook は人間が毎晩開くものではありません。夜中の2時に誰かが出社してセルを上から順に実行していく——そういう運用を想像してしまうと、シナリオ全体が読めなくなります。

実際には、Job が Notebook や Python コードを Task として自動実行します。人が書くのは中身と依存関係だけ。いつ動かすか、どの順で動かすかは Job の仕事です。ここを分けて考えられるかどうかが、この先のシナリオを読む土台になります。

1時間ごとに刻む派生シナリオ 1

日次では遅いため、毎時 00 分に Job を起動します。同じ処理を、扱う時間帯だけずらして繰り返す形です。

起動処理する範囲向いているケース
09:00 Job08:00〜09:00 分ほぼリアルタイムまでは不要 / 1時間程度の遅延で十分 / 常時 Compute を動かしたくない
10:00 Job09:00〜10:00 分
11:00 Job10:00〜11:00 分

Auto Loader の AvailableNow のような実行方式を使うと、今ある未処理ファイルを処理して終了できます。動かし続けるのではなく、起動して、溜まった分だけ片づけて、止まる。バッチの形のまま、間隔だけを詰めたものだと考えてください。

毎朝1回、決まった時刻に派生シナリオ 2

 
06:00 ERP export → ADLS → 06:30 Scheduled Job → Delta へ取り込み
注意点何が起きるか
タイムゾーン設定同じ指定でも解釈が違えば起動時刻がずれる
遅延到着06:30 の時点でまだファイルが揃っていない
届かなかった日の扱い空で走らせるのか、止めるのか、待つのかを決めておく

非常に典型的な固定スケジュール型——ファイルが出てくる時刻が分かっているので、その少しあとに起動を置くだけです。スケジュールの書式（Quartz cron）とタイムゾーンの解釈そのものは第58回で扱いました。ここで言いたいのは、時刻を決めるということは、来なかったときにどうするかまで決めることだという点です。

複数ソースをまとめて取り込む派生シナリオ 3

ここでは Task を分離すると、データソースごとの失敗や再実行がしやすくなります。在庫のファイルだけ届かなかった——そういうときに、売上まで巻き添えにして止めなくて済みます。ひとつの Task に全部詰め込むと、この分け方ができません。

溜まったデータを流すだけ覚え方

日次バッチETL = 「定期的に起動して、溜まったデータを Bronze → Silver → Gold へ流す」

試験で意識したいのは、部品そのものではなく組み合わせです。スケジュール、Auto Loader、Delta、Medallion、Jobs、Task / DAG——この6つが同じ問題文の中に一緒に出てきます。

シナリオを読むときの順番も同じです。まず、いつ動くのか。次に、何をどこへ取り込むのか。そして、どこまで整形して誰に渡すのか。この3つを順に埋めていけば、答えの形は見えてきます。
