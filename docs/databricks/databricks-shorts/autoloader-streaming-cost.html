Auto Loaderの常時ストリーミングとコスト

Auto Loader を常時ストリーミングで動かすと、Streaming Query を実行する Compute が稼働し続けます。 基本的には、ファイルが来ていない待機時間にも Compute コストが発生します。

待機時間にもコストが出るまず結論

設計では、次の2点を分けて考えると分かりやすいです。

問い ①
本当に24時間待ち受ける必要があるのか
問い ②
待ち受けるなら、負荷に応じて Compute をどこまで縮小・拡張できるか

低レイテンシの見返りがあるかどうかで決まります。同じ「常時起動」でも、注文が数秒おきに来る現場と、1日数回しか来ない現場では意味がまったく違います。

常時待機させない形第70回で扱った3つの形

リアルタイム性がそれほど重要でなければ、Auto Loader を一過性の処理として利用できます。

形起動のきっかけAuto Loader の使い方Compute
常時ストリーミングずっと動かすStreaming Query が生き続ける基本的に稼働継続
定期実行 + AvailableNow毎時 Job 起動現在ある未処理ファイルを処理して Job 終了Job 終了で停止
File arrival trigger + AvailableNowファイル到着未処理ファイルを取り込んで Job 終了Job 終了で解放

次回起動時に Checkpoint などを利用して未処理分を取り込むので、止まっている間に来たファイルも取りこぼしません。 File arrival trigger は「ファイルが来るまで Compute を寝かせ、必要になったら起こす」という設計に近い形です。 3つの形の具体例は第70回、trigger 自体の仕組みは第60回で扱いました。

待機中は小さく、処理時は大きくWorker 数で伸び縮みさせる

Scale Up と Scale Out用語として重要
用語別名やること例
Scale Up垂直スケール1台あたりの CPU・メモリなどを強くする小さい Worker → 大きい Worker
Scale Out水平スケールWorker の台数を増やすWorker × 2 → Worker × 10

Databricks の一般的なクラスタ Autoscaling で中心になるのは後者の Scale Out です。 「待機時は低コスト、本格処理時はリソースを増やしたい」という考え方は正しいのですが、 従来型クラスタでは「Worker のサイズを変える」より「Worker 数を変える」と考えた方が近いです。

Streaming と Autoscaling縮小が進みにくい

通常の Structured Streaming Job に一般的なクラスタ Autoscaling を組み合わせる場合、 Streaming 特有の事情によって Worker の縮小が期待どおりに進みにくい場合があります。

そこで
新しいストリーミング処理では Lakeflow Declarative Pipelines と Enhanced Autoscaling を組み合わせる構成が重要になります
何を見るか
Enhanced Autoscaling では Task の利用状況や Queue などを考慮し、必要な Worker 数を調整します
