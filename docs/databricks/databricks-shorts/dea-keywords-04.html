16. Lineage / Audit / Governance追跡するもの・記録するもの
観点キーワード意味・用途
追跡Data Lineage / Upstream / Downstream / Column-Level Lineageどこから来て、どこへ流れ、何に使われたかを追跡。前段が Upstream、後段が Downstream。列単位まで追うのが Column-Level
記録Audit Log / System Tables誰が何をしたかの監査ログ。運用・利用状況等を SQL で確認するシステム提供テーブル群
履歴Query History / Access History実行された SQL・実行時間・利用 Compute 等の履歴。誰がどのデータへアクセスしたかの追跡。
統制Data Discovery / Data Classification / Data Governance / Data Ownership資産を見つけ、種類・重要度を分類し、権限・監査・Lineage・品質で統制し、責任者を明確にする

「何を実行したか」なら Query History、「誰がどのデータに触れたか」なら Access History。Lineage は粒度がテーブルか列かを確認します。

18. Managed / External保存場所を誰が持つか
対象キーワード意味・用途
TableManaged Table / External Table保存場所とライフサイクルまで UC が管理するか、外部ストレージに残して UC はメタデータ・権限だけ管理するか
VolumeManaged Volume / External Volumeファイル保存場所も同じ分かれ方。考え方は Table と同じ
接続Storage Credential / External LocationCloud Storage へアクセスする認証情報と、それにパスを組み合わせた UC オブジェクト
物理Cloud Storage / S3 / ADLS / GCSAWS・Azure・GCP のオブジェクトストレージ。Delta の物理データが置かれる
 
Managed  = Databricks / Unity Catalog が保存場所・ライフサイクルまで管理
External = データの場所は外部ストレージ側で明示的に管理し、
           Unity Catalog はメタデータ・アクセスを管理

19. DevOps / CI/CDGit と環境の区分
観点キーワード意味・用途
バージョン管理Git / GitHub / Repository変更履歴を管理する分散バージョン管理システムと、そのホスティング。Repository はプロジェクト単位
Databricks 側Git FolderWorkspace 内で Git Repository と同期して開発する仕組み・作業領域
変更の流れBranch / Commit / Pull Request変更を分岐して並行開発し、1回の変更スナップショットを積み、レビューして統合する
自動化CI/CD / Deploymentテスト・検証・Deploy を自動化する。定義を対象環境へ反映するのが Deployment
環境Development / Staging / Production / Environment開発・検証、本番相当条件での確認、実利用の本番。実行・配置先の区分が Environment

19. Bundles と CLI何をどうデプロイするか
観点キーワード意味・用途
道具Databricks CLI / Databricks SDKコマンドラインから操作。SDK は Python 等のコードから
名前Declarative Automation Bundles / Databricks Asset Bundles宣言的に定義して Deploy する仕組み。Asset Bundles は旧名称
単位と設定Bundle / databricks.yml / targets / resourcesコード・設定・リソース定義をまとめた Deploy 単位
中身Target / Resource / Variable / OverrideDeploy 先環境設定、Job や Pipeline、再利用する値、上書き
検証と実行Validation / validate / deploy / runDeploy 前の検証、Workspace への反映、Job 等の実行

正本は GitHub、定義は Bundle、動くのは Workspace。変更履歴とレビューは GitHub、何をどう Deploy するかは Bundle、実際の Deployment・実行先が Workspace です。

20. 取り込み方式と処理の保証全件か差分か・まとめるか流すか
観点キーワード意味・用途
全件か差分かFull Load / Incremental Load / CDC全件読み込む（初回向き）。前回以降の追加・更新分だけ処理する。CDC は INSERT/UPDATE/DELETE を捕捉して下流へ反映
まとめるか流すかBatch / Streaming / Micro-batch一定量・一定時刻でまとめる。到着に応じて継続的に増分処理する。Micro-batch は短いバッチの連続
再実行の前提Idempotency / Replayability複数回実行しても最終結果が変わらない性質。障害時に Source を再度読み直せる性質
重複と遅れDeduplication / Late-arriving Data重複を除去する。遅れて到着するデータは State/Watermark 設計と関係
到達保証Exactly-once重複や欠落なく1回だけ反映された状態を目指す処理保証

Idempotency と Replayability が揃って、はじめて Exactly-once に近づきます。

20. 変化と障害への備え現象と、その手当て
観点キーワード意味・用途
入力の変化Schema Drift → Schema Evolution列追加・型変更など入力スキーマが変化する現象が Drift。Target 側を進化させる仕組みが Evolution
品質Data Qualityデータが正確・完全・期待条件に合う状態を保つ考え方
止まったときPipeline Failure / Recovery / Retry正常完了しない状態。Checkpoint や Retry で障害後に復旧する。一時的失敗には再実行
続きからCheckpointStreaming の進捗・State 等を保存し、再起動後に処理を継続する
埋め戻しBackfill過去期間の未処理・不足データを後からまとめて処理する

起きたことが Schema Drift、手当てが Schema Evolution。現象と仕組みを分けておけば、選択肢で迷いません。
