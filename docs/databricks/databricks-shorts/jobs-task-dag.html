Job / Task / DAG の全体像

Job は実行とスケジュールの単位、Task は1つの処理、DAG はタスク間の依存関係を示す有向非巡回グラフです。 順序と並列度を自分で指定することはありません。依存を書けば、Jobs がそこから導き出します。

Job と Task はそれぞれ何の単位かまず3つの語を分ける

Databricks Jobs を読むとき、混ざりやすいのが Job・Task・DAG の3語です。 指しているものの粒度が違うので、先に切り分けます。

Job
実行とスケジュールの単位。「毎朝5時に動かす」「今すぐ実行する」の対象はこれ。 失敗の通知も、リトライの設定も Job に付きます。
Task
1つの処理。ノートブック1本、SQL 1本、パイプライン1本といった中身を指します。 Job は複数の Task を抱えられます。
DAG
タスク間の依存関係を示す有向非巡回グラフ（Directed Acyclic Graph）。 Task をどうつないだか、という関係のほうを指す語です。実行される「もの」ではありません。

つまり Job が箱、Task が中身、DAG が中身同士のつなぎ方です。 「DAG を実行する」という言い方はしません。実行するのは Job です。

DAG は依存関係を表したグラフ有向・非巡回の2語が効いている

DAG という語は3つの単語でできていて、それぞれが制約を1つずつ足しています。

語意味ここから決まること
Directed（有向）辺に向きがあるA → B は「A のあとに B」。逆には流れない
Acyclic（非巡回）ループが無いA → B → A のような循環は作れない。必ず終わる
Graph（グラフ）点と辺の集まり一本道である必要はない。枝分かれも合流もできる

並列は書かない。依存から導かれる今回いちばんのポイント

書くのは「このタスクは何の完了を待つか」だけです。 そこから実行順序も並列度も Jobs 側が決めます。

タスク何をするか依存実行のされ方
Task Aデータを取り込むなし最初に走る
Task B / Task CSilver に変換する / 別ソースから取り込むAA の完了を待つ。B と C は並列
Task DGold の集計を作るB、CB と C の両方の完了を待つ

よくある誤解言い換えると引っかかりにくい
誤解実際
タスクを並べた順に上から実行される画面上の並び順は関係ない。走る順は依存だけで決まる
並列にしたいので並列の設定を入れる依存を書かなければ並列になる。並列を指定する項目ではない
D は B が終われば走れるB と C の両方を待つ。片方でも走らない
DAG を実行する実行の単位は Job。DAG は Task 同士のつなぎ方の呼び名
ループを組んで繰り返せる非巡回なのでループは作れない。必ず先行から後続へ一方向に流れる

3行目が特に落としやすいところです。合流するタスクは AND 待ちで、 先に終わったほうに引っ張られて先行することはありません。

試験に効く覚え方3語を1文にまとめる

Job が実行とスケジュールの単位、Task が1つの処理、DAG がその依存関係。 依存を書けば、順序も並列度も Jobs が決める。

この「関係を書けば順序は導出される」という考え方は、 Declarative Pipelines（宣言的パイプライン）と同じです。 テーブル間の依存を書けば実行順が決まる、という点で発想が揃っています。 手続きを並べるのではなく、関係を宣言する——ここを掴んでおくと、 両方まとめて答えられます。

依存が無いタスク同士は自動的に並列化されます。並列度を上げるために設定を触るのではなく、 不要な依存を書かないことが結果的に効きます。

非巡回（Acyclic）であることは、実務上は「必ず終わる」ことの保証でもあります。 循環が作れないので、依存をたどっていけば必ず起点のタスクに行き着きます。
