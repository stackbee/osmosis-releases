器と道具の名前1. 基礎 — 紛らわしいのは名前が並ぶところ
キーワード意味・用途
Databricks Data Intelligence Platformデータエンジニアリング、分析、AI/ML、ガバナンスを統合するプラットフォーム
LakehouseData Lake の柔軟性と Data Warehouse の管理性・SQL 性能を組み合わせるアーキテクチャ
Data Lake / Data Warehouse大量の構造化・半構造化・非構造化データを保持する基盤／分析向けに整備された構造化データを SQL で高速に扱う基盤
Delta LakeParquet に Transaction Log を組み合わせ、ACID や MERGE、Time Travel などを実現するテーブル形式
Apache Spark / Spark SQL分散データ処理エンジン／Spark 上で SQL を実行する仕組み。DataFrame API と同じ実行エンジンにつながる
PySpark / DataFramePython から Spark を操作する API／行列形式の分散データ構造。Spark では遅延評価される

引き方 — アーキテクチャなら Lakehouse、テーブル形式なら Delta Lake。

いつ動くか — 遅延評価1. 基礎 — 返るものが分かれ目
キーワード意味・用途
Lazy EvaluationTransformation をすぐ実行せず、Action が来た時にまとめて実行計画を作る仕組み
TransformationDataFrame を別の DataFrame へ変換する処理。例: select, filter, join
Action実際の計算を開始させる操作。例: count, collect, show, 書き込み
DataFrame行列形式の分散データ構造。Spark では遅延評価される

返ってくるもので引く

DataFrame が返るなら Transformation。値やファイルが返るなら Action。「フィルタを書いたのに何も起きない」も「表示しただけなのに時間がかかる」も、どちらも正常です。

どこで動くか — 二重に紛らわしい2組1. 基礎 — 実データがどちらにあるか
キーワード意味・用途
Driver / WorkerSpark ジョブ全体を計画し、Stage/Task へ分解して Worker へ仕事を割り振る司令塔／Driver から割り当てられた Task を実行する計算ノード
Cluster / ComputeSpark や SQL などの処理を実行する計算リソース
Control PlaneDatabricks の管理・制御側。Workspace、Job、Compute 制御、認証などを担当
Compute Plane実データを使った処理を実行する側。Driver/Worker などの Compute が存在する

2組は別のレイヤーの話

Driver と Worker は、ひとつの計算リソースの中の役割分担。Control Plane と Compute Plane は、管理する側とデータを触る側の境目。判断の軸は実データがどちらにあるかです。

Compute の選び分けと課金1. 基礎 — 構成の細かさ × 用途
キーワード意味・用途
Serverless Computeインスタンス選択やスケーリングを Databricks 側に任せる Compute 方式
Classic ComputeVM サイズや Worker 数などをユーザー側でより細かく構成する Compute 方式
Job ComputeJob 実行用の Compute。処理開始時に起動し、終了時に停止する構成が基本
All-Purpose ComputeNotebook など対話的な分析・開発で使う Compute
PhotonDatabricks の高性能なベクトル化実行エンジン。SQL や DataFrame 処理を高速化する
DBUDatabricks Unit。Databricks 利用量・課金を表す単位の一つ

引き方 — 決まった時刻に走るバッチなら Job Compute。人が触りながら試すなら All-Purpose Compute。「起動しっぱなしのコストを避けたい」という文脈が出てきたら Job Compute を疑う。

Delta Table の実体2. Delta Lake — Parquet + トランザクションログ
キーワード意味・用途
Delta TableDelta Lake 形式で管理されるテーブル。Parquet ファイル + _delta_log で構成される
Parquet列指向のファイル形式。分析系クエリで必要列だけ読みやすい
_delta_logDelta Table の Transaction Log を保存するディレクトリ
Transaction Logどのファイルが有効か、どんな変更が行われたかを記録するログ
Snapshot / Transactionある時点で有効な Delta ファイル集合（クエリはスナップショットを読む）／複数の変更を一つの整合した単位として扱う処理
Optimistic Concurrency Controlまず処理し、コミット時に競合を検出する方式

先にロックを取るのではなく、後から気づいて弾く。これが「楽観的」と呼ばれる理由です。

ACID とスキーマの守り2. Delta Lake — 名前が近く、向きが逆
キーワード意味・用途
ACIDトランザクションの信頼性を表す4特性。Atomicity, Consistency, Isolation, Durability
Atomicity処理が全部成功するか、全部なかったことになるか
Consistencyトランザクション前後でデータ整合性を保つ
Isolation同時実行トランザクション同士が不正に干渉しない
Durabilityコミット済みの変更が失われない
Schema Enforcement / Schema Evolution既存テーブルと不整合なスキーマの書き込みを防ぐ／新しい列などのスキーマ変更を許容してテーブルを進化させる

引き方 — 「弾いてほしい」なら Enforcement。「増えた列も受け入れたい」なら Evolution。

消しても消えない、そして消える2. Delta Lake — 書き換え・履歴・掃除
キーワード意味・用途
INSERT / UPDATE / DELETE新しい行を追加／既存行を更新／条件に合う行を論理的に削除する（古いファイルはすぐには物理削除されない）
MERGE / Upsert条件に応じて INSERT/UPDATE/DELETE をまとめて行う（Upsert や CDC で重要）／既存なら UPDATE、なければ INSERT
Time Travel / VERSION AS OF / TIMESTAMP AS OF過去バージョン・時刻の Delta Table を参照する機能／特定バージョンを読む／特定時刻時点を読む
DESCRIBE HISTORY / Table History更新履歴を確認する SQL／テーブルに対して行われた更新履歴
VACUUM / Retention Period参照されなくなった古いデータファイルを保持期間後に削除する／その保持期間

VACUUM を実行すると、それより前へは戻れない

消えないのは掃除するまで。掃除したら戻れない。DELETE が論理削除だから Time Travel が成立し、VACUUM が走ると成立しなくなる — この順で覚えます。

小ファイルと読み飛ばし3. レイアウト — 整理と Data Skipping は地続き
キーワード意味・用途
Small File Problem / Small Files小ファイルが増えすぎてメタデータ処理や I/O 効率が悪化する問題
Compaction / File Compaction多数の小ファイルを少数の大きめファイルへまとめること
OPTIMIZE小さいファイルの統合や、Liquid Clustering されたテーブルの再編成などを行う
Data Skippingファイル統計を使い、条件に絶対合わないファイルを読まない最適化
File Statisticsファイル単位の min/max/null 数など。Data Skipping の判断材料

整理と読み飛ばしは別々の話ではありません。ファイルが細かく散らばっているほど、統計も効きにくくなります。

配置最適化には世代がある3. レイアウト — 併用ではなく世代違い

世代の並び併用ではなく世代違い

Partitioning → Z-ORDER（旧来） → Liquid Clustering（現在の推奨）
キーワード意味・用途
Partitioning / Partition Pruning列値ごとに物理ディレクトリを分ける従来型の配置／不要なパーティションディレクトリを読まない最適化
Z-ORDER / Bloom Filter Index複数列の値が近いデータを近いファイルへ寄せる旧来のレイアウト最適化／以前の検索補助インデックス。どちらも現在は主力ではない
Liquid Clustering / CLUSTER BY / Automatic Liquid Clusteringクラスタリングキーを指定してデータ配置を最適化する現在の推奨方式／キーを指定する構文／キー選択を自動化する方向の機能
Clustering Key / Cardinality配置最適化の軸に使う列／列に含まれる値の種類数（高カーディナリティ列は候補になりやすい）

実行計画と、自動で効いているもの3. パフォーマンス — 計画を直す / 読む量を減らす / 運用を消す
系統キーワード意味・用途
計画を直すQuery OptimizationSQL/DataFrame の実行計画をより効率的な形へ変換する仕組み全般
Catalyst OptimizerSpark SQL の論理/物理実行計画を最適化するオプティマイザ
Adaptive Query Execution / AQE実行時統計を使い、Join 戦略や Shuffle Partition 数などを途中で調整する
読む量を減らすPredicate PushdownWHERE 条件を可能な限りデータ読み取り側へ押し込み、不要データを早期除外する
Column Pruning必要な列だけ読む最適化。Parquet の列指向と相性が良い
Cache再利用されるデータをメモリ等に保持し、再読み込みを減らす
運用を消すPredictive Optimization / Predictive I/OUnity Catalog managed table の保守操作を Databricks 側で自動化する仕組み／Photon と連携して I/O を効率化し、不要データの読み取りを減らす最適化

Shuffle が重い理由と、その周り3. パフォーマンス — 性能の問題は Shuffle に帰着する
キーワード意味・用途
ShuffleGroupBy や Join などでデータを Worker 間移動・再配置する処理
Data Skew一部キーにデータが集中し、特定 Task だけ重くなる偏り
Broadcast Join小さいテーブルを各 Worker へ配り、大きいテーブル側の Shuffle を減らす Join
Sort Merge Join両側をキーで Shuffle/Sort して結合する大規模 Join の代表方式
Repartition / Coalesceデータを Shuffle してパーティション数や分布を作り直す／主に Shuffle を抑えてパーティション数を減らす用途

要件から引く

片側が十分に小さいなら Broadcast Join、どちらも大きいなら Sort Merge Join。パーティション数は増やすなら Repartition、減らすだけなら Coalesce。

PySpark の入口と出口4. PySpark — ストリームかバッチかで対になる
キーワード意味・用途
spark.read / spark.readStream / spark.tableバッチデータを読み込む入口／Structured Streaming のストリームソースを読み込む入口／カタログ上のテーブルを DataFrame として読む
df.write / df.writeStreamバッチ DataFrame を書き込む／Streaming DataFrame を書き込む
save / saveAsTable / tableパス等へ書き込む／カタログ上のテーブルとして保存する／writeStream.table(...) などでテーブルへ出力する
append / overwrite / ignore / errorIfExists新規行を追加／既存データを置き換え／既存なら書き込みを無視／既存ならエラー
partitionBy書き込み時に物理 Partitioning 列を指定する

ストリームかバッチかで read / readStream、write / writeStream が入れ替わります。片方だけ間違えている選択肢がよく出ます。

列を触るのか、行をまとめるのか4. PySpark — 何を変える操作かで分ける
キーワード意味・用途
select / selectExpr / withColumn / drop必要列を選択・式で変換／SQL 式を文字列で書いて select／列を追加または既存列を置換／不要列を削除
col / lit / cast / alias列を Column オブジェクトとして参照／固定値を Column として扱う／データ型を変換／別名を付ける（Join 時に便利）
when / otherwise条件分岐で値を作る（SQL の CASE WHEN 相当）／一致しなかった場合の値を指定する
filter / where条件に合う行だけ残す／ほぼ同義。SQL に近い表現
split / explode文字列を区切り文字で配列へ分割する／配列や Map を複数行へ展開する
groupBy / agg / sum / avg / countキーごとに行をまとめて集計／複数の集計式を指定／合計・平均・件数
distinct / dropDuplicates / orderBy / sort完全重複行を除去／指定列を基準に重複行を除去／全体を指定列で並べ替える（Shuffle が発生しやすい）

結合はどれを選ぶか4. PySpark — 見分け方は「返る列」
キーワード返る行返る列
join / Inner Join2つの DataFrame をキーや条件で結合／両側にマッチする行だけ両側
Left Join / Right Join左側の全行 + 右側のマッチ行／右側の全行 + 左側のマッチ行両側
Full Outer Join両側の全行（マッチしない側は NULL）両側
Left Semi Join右側にマッチが存在する左側行左側だけ
Left Anti Join右側にマッチが存在しない左側行左側だけ
Cross Join左×右の全組み合わせ（行数が爆発しやすい）両側
union / unionByName行方向に結合（基本的に列位置ベース）／列名を基準に行方向結合

Window Function は行を潰さない4/5 共通 — groupBy との違い
キーワード意味・用途
Window Function行を潰さず、グループ内順位や移動計算を行う。元の行を残したまま集計・順位・前後行参照
OVERWindow Function の対象範囲を定義する
PARTITION BYWindow 内でグループを区切る。テーブルの物理 Partitioning とは別概念
ROW_NUMBERWindow 内で 1,2,3… と一意な連番を付ける
RANK同順位を許し、次順位を飛ばすランキング
LAG / LEAD同じ Window 内の前の行の値を参照／次の行の値を参照

引き方 — 「順位を付けたいが明細も残したい」なら Window Function。重複を許さないなら ROW_NUMBER、同点を同じ順位にしたいなら RANK。過去を見るのが LAG、先を見るのが LEAD。

SQL の骨格5. SQL — 単語より「どの順で効くか」
キーワード意味・用途
SELECT / FROM取得する列・式を指定する／読み取り元を指定する
WHERE / HAVING集計前の行を条件で絞る／GROUP BY 後の集計結果を条件で絞る
GROUP BY / ORDER BY / JOINキー単位で行をまとめ集計する／結果を指定列で並べ替える／複数テーブルをキー・条件で結合する
CTE / WITH / Subquery1つの SQL 文内で一時的な名前付き中間結果を定義する／SQL 文の中に埋め込む別の SELECT
Aggregate Function / Window FunctionSUM/AVG/COUNT など複数行を1値へ集約（行が減る）／元の行を残して集計・順位・前後行参照（行は減らない）
CASE WHEN / CAST / COALESCE / MERGE INTO条件分岐で値を生成／データ型を変換／最初の非 NULL 値を返す（NULL 補完）／条件一致・不一致ごとに UPDATE/INSERT/DELETE を行う

集計結果に条件を付けたいのに WHERE を使っている選択肢は、そこで落とせます。違いは「集計の前か後か」だけ。

テーブルとビュー、そして次の一歩5. SQL — 実体を持つか持たないか
キーワード意味・用途実体
CREATE TABLE / CREATE OR REPLACE TABLE新しいテーブルを作成する／既存テーブルを置換して作り直すあり
CREATE VIEW / Temporary ViewSQL 定義を保存した論理ビューを作る／セッション等に限定して使う一時ビューなし
Materialized Viewクエリ結果を保持し、パイプラインで更新される実体化ビューあり
Streaming Tableストリーミング入力を増分処理して維持するテーブルあり

この後の使い方

引き方は「定義だけ残したいなら VIEW、結果を保持して速く返したいなら Materialized View、増分で入り続けるなら Streaming Table」。まずは各用語を「説明できる / 名前だけ知っている / 未理解」の3段階でチェックすると、弱点が見つけやすくなります。
