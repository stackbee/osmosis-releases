常時ストリーミングのシナリオ

データが継続的に発生し、数秒〜数分の低遅延で取り込みたいときに、Auto Loader / Structured Streaming を継続稼働させる形です。 処理が終わっても Query は終了せず、次のデータを待ち続けます。

止めずに流し続けるこのパターンの本質

発生源からデータが継続的に生まれ、Cloud Storage や Event Source に届く。それを Auto Loader / Structured Streaming が受け取り、 Bronze → Silver と流してリアルタイム分析につなげます。

選ぶ条件
データが継続的に発生し、数秒〜数分程度の低遅延で取り込み・加工したい。
形
Auto Loader / Structured Streaming を継続稼働させる。処理後も終了しない。
この回の役目
個々の部品の仕組みではなく、どの部品をどう組み合わせるかと判断の順序。

注文を数分で反映する基本シナリオ

EC サイトの注文データをほぼリアルタイムで処理する形を考えます。要件は3つです。

要件そこから決まること
注文ファイルが S3 へ数秒〜数十秒おきに到着入口はファイル。Auto Loader が候補になる
数分以内に売上ダッシュボードへ反映したい日次バッチでは間に合わない。低遅延が要る
人間が Notebook を開き続ける運用にはしないJob / Pipeline からの無人実行にする

低遅延で処理したいという要件と無人で動かしたいという要件が同時にあるとき、常時ストリーミングの形が選ばれます。

起動のされ方と、ファイルの見つけ方は別の話です。 常時ストリーミングでは起動は最初の一度きりで、ファイルの検出だけが動き続けるあいだ繰り返されます。 File arrival trigger との対比と、通知でファイルを見つける経路は ep060 で扱いました。 Checkpoint の中身は ep035、通知基盤そのものは ep037 です。ここでは深追いしません。

入口も出口も違いますが、継続稼働させて新着を順次処理するという骨格は同じです。

大きな流れに小さなマスタを足す派生シナリオ 3

注文ストリームに商品カテゴリを付加したい、という形です。 orders stream は大量に流れてきて、products master は小さい。この非対称がそのまま判断材料になります。

小さいマスタを Broadcast できれば、大規模 Shuffle を避けやすい。 ここで Broadcast Join、AQE、Shuffle などの性能知識につながります。 常時ストリーミングは、シナリオとしては単純に見えて、性能の話と地続きです。

待機があるか、終了があるか定期バッチとの違い

継続稼働で順次処理する覚え方

常時ストリーミング = 「Auto Loader / Structured Streaming を継続稼働させ、新着を低遅延で順次処理する」

もう一つ、運用の側で大事な理解があります。 Notebook は開発・定義の場所であり、本番では Job や Pipeline から無人実行する。 ここを取り違えると、人が Notebook を開き続ける運用になってしまいます。

低遅延が要るか。無人で動かすか。この2つがそろったら、常時ストリーミングを検討してください。
