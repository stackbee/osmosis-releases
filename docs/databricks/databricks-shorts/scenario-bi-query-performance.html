BI分析基盤とクエリ高速化のシナリオ

BI から叩かれるクエリが遅い、という状況で、どの部品をどう組み合わせるか。 Compute を大きくする前に、「読む量」「動かす量」「計算量」に分解する。 シナリオ回6本の最終回です。

最終回は分析基盤の高速化今回の主張

大量の Delta Table を Power BI やダッシュボードから繰り返し検索する。この状況では、 単純に Compute を大きくするだけでなく、読み取り量・データ配置・実行エンジンを意識して高速化する。

50億行を Power BI から基本シナリオ
データ
sales テーブルは50億行。
使われ方
Power BI で日付・顧客・地域を絞り込む。
期待
ユーザーは数秒〜十数秒程度の応答を期待している。
SELECT customer_id, SUM(amount)
FROM sales
WHERE sale_date >= '2026-08-01' AND region = 'Tokyo'
GROUP BY customer_id

日付で絞り、地域で絞り、顧客ごとに合計する。BI から飛んでくる代表的な形です。

クエリが通る道処理イメージ
段そこで起きること遅くなるとしたら
Power BISQL を投げるフィルタが効いていない
SQL WarehouseQuery Plan を作るCompute が小さい
Delta Table必要なファイルだけ読む読むファイルが絞れていない
Photon集計して結果を返すShuffle が大きい / 計算が重い

短い道のりに見えて、遅くなる場所はこの中に分かれて存在します。 どこが遅いのかを言えないまま Compute だけを大きくしても効きません。

まず何ギガ読んでいるかここがいちばんのポイント

大量テーブルの性能問題では、まず「何 GB / TB 読んでいるか」を考える。原因は3つに分かれます。

顧客番号での検索が多い派生1

分析ユーザーが頻繁に WHERE customer_id = 12345 で検索する。 データ配置がバラバラだと、多数の Parquet ファイルを確認する必要があります。

日付で絞るレポート派生2

ほとんどのクエリが WHERE sale_date BETWEEN ... を含む場合。古典的な Delta Partitioning を使っているテーブルなら、 日付のような低〜中程度のカーディナリティ列で物理的に分ける設計が考えられます （sales/date=2026-08-01/ のようにディレクトリが分かれる形）。 ただし新しい設計では、従来型 Partitioning だけに固定せず Liquid Clustering を検討します。

仕組み何を飛ばすか
Partition Pruning不要な Partition を飛ばす
Data Skipping不要な ファイル を飛ばす

働きは同じでも飛ばす単位が違います。どちらも「読む量を減らす層」に並ぶ道具です。 Partition の仕組みは第23回、ZORDER との物理的な違いは第24回、論理的な違いは第25回、 指定の仕方と誤解は第55回で扱ったので、ここでは深追いしません。

小さいファイルが増えすぎた派生3

ストリーミングや頻繁な書き込みで、小さい Parquet ファイルが何万個も増える （part-00001 が 2MB、part-00002 が 3MB、part-00003 が 1MB…）。 ファイルを開くオーバーヘッドが増え、読み取り効率が悪化します。 そこで OPTIMIZE などでファイルサイズを最適化し、より大きなファイルへ再編します。

コマンド何をするか
OPTIMIZE現在のデータファイルの配置・サイズを改善する
VACUUM参照されなくなった古いファイルを保持期間後に削除する

OPTIMIZE は VACUUM とは違う。 名前が並んで出てくると混ざりますが、触る対象がまったく違います。

読む量を絞っても遅いとき派生4

ファイル読み取りは十分絞れていても、GROUP BY customer_id で巨大な Shuffle が起きる場合があります。 読み取り量は少ない。それでも GROUP BY で Shuffle が大量に出て、結果として遅い。

この場合、Clustering だけでは問題が完全には解決しません。 ここでは AQE、Shuffle Partition、Skew、Compute といった別レイヤーを見る必要があります。 読む量の層ではなく、動かす量の層に降りるということです。

実行エンジンの層まで降りるSQL Warehouse と Photon

Power BI から SQL が来て、SQL Warehouse が Query Plan を作る。その中で Photon が動き、Delta / Parquet を読みにいく。

用語正体
SQL WarehouseSQL を実行する Compute 環境。BI・SQL 分析用として利用される
Photonその中で処理を高速化する 実行エンジン。対応する処理を高速に実行する

Photon とは何かは第16回、なぜ高速なのかは第19回で扱いました。ここで押さえたいのは層の違いだけです。 Compute の器と、その中で回る実行エンジンは別のもの。

毎回計算しないという手もう1段手前

ここまでは「来たクエリをどう速く処理するか」の話でした。もうひとつ、別の方向の手があります。 事前に計算しておくことです。同じ集計が何度も走るなら、その結果をあらかじめ作って持っておく。 Materialized View はその考え方の道具です。

読む量も、動かす量も、計算量も、クエリの時点では発生しなくなります。 手前の3つが実行時の工夫だとすると、これは実行前に済ませておく工夫。段が1つ違います。 CTE / View / Materialized View の違いは第27回で扱いました。

読む量、動かす量、計算量覚え方

BI高速化 = 「Compute を増やす」より前に、「読む量」「動かす量」「計算量」を分解して考える。
