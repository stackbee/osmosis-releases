Delta Lake の Parquet はどこに置かれるのか

Delta Table の実体は、クラウドのオブジェクトストレージ上にある Parquet ファイルと _delta_log です。 Databricks の中に専用の保存領域があるわけではありません。

実体はクラウドストレージにあるまず結論から

Delta Lake は、複数の Parquet ファイルと _delta_log を組み合わせて1つのテーブルとして扱う仕組みです。 では、その Parquet ファイル自体はどこに置かれるのか。クラウドのオブジェクトストレージ上です。

クラウド置き場所役割
AzureADLS Gen2名前は違うが役割は同じ。ファイルを置いておくための入れ物。テーブルとしての性質はその上に Delta Lake が作る
AWSAmazon S3
GCPGoogle Cloud Storage

Databricks を使っていても、データが Databricks の中に吸い込まれるわけではありません。 置き場所は自分のクラウドアカウントのストレージのままです。

コンテナの下に incoming/ と delta/ が並んでいる形を考えます。 前者は外部システムが置いた元ファイル、後者が Delta Table の実体です。

Auto Loader は置き換えないよくある誤解

外部システムがクラウドストレージに CSV や JSON を置き、Auto Loader がその新着ファイルを検出して読み取ります。 読み取った結果は Spark で変換され、Delta Table に書き込まれます。

Auto Loader は元のファイルをその場で Parquet に置き換えるわけではありません。 元ファイルは置かれた場所にそのまま残り、変換結果は別の場所に書き出されます。

「取り込んだら元ファイルが Delta になる」と思っていると、 どちらを見ればいいのか分からなくなります。読む場所と書く場所は最初から別です。

入力元と保存先は別の場所ここがいちばんのポイント

ここを同じものだと思っていると、「テーブルの実体を見たい」と思ったときに どちらのパスを開けばいいのかが分からなくなります。

External Table は場所を明示する保存場所の決まり方 1/2

保存場所の決まり方には2つのやり方があります。1つ目が External Table で、 保存場所を自分で明示します。

クラウド指定するパスの形
AWSs3://my-bucket/delta/orders/
Azureabfss://container@account.dfs.core.windows.net/delta/orders/

このパスの下に Parquet ファイルと _delta_log が置かれます。 つまり External Table は、この Delta Table の実体はこのクラウドストレージ上のパスにあります、と宣言する形です。

Managed Table は任せるだけ保存場所の決まり方 2/2

2つ目が Unity Catalog の Managed Table です。利用者が毎回、保存パスを明示する必要がありません。 保存場所は Databricks と Unity Catalog の側が管理します。

Managed Table だからといって、Databricks 専用の謎のディスクに保存されるわけではありません。 実データは最終的にはやはりクラウドオブジェクトストレージ上に保存されます。置かれるものも同じで、Parquet ファイルと _delta_log です。
