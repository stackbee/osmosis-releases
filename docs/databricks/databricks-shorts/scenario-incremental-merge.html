増分更新とMERGEのシナリオ

マスタデータを増分で更新し続ける、という場面の組み立て方。 毎回テーブル全体を作り直すのではなく、届いた変更分だけを既存の Delta Table へ当てる。 その受け口から反映までを一本の線にします。

作り直さずに差分を当てるこのパターンの本質

毎回テーブル全体を作り直すのではなく、新しく届いた変更分だけを既存の Delta Table へ反映する。 これが増分更新パターンです。MERGE は、既存行の UPDATE、新規行の INSERT、条件次第では DELETE まで、 1つの処理として扱えます。だから増分を受ける口として使われます。

やること
届いた変更分だけを既存の Delta Table へ当てる
使う道具
MERGE — 更新・挿入・削除を1回の処理にまとめられる
この回の範囲
構文そのものは第14回、遅いときの対処は第15回。ここは組み合わせ方と判断の順序

顧客マスタの日次更新基本シナリオ

昨日時点のテーブルに2行あり、今日そこへ変更ファイルが2行届く、という形です。

customer_id昨日時点今日届いた変更期待する結果
1001A / SilverA / GoldUPDATE — 既にいるので置き換える
1002B / Gold—そのまま — 触らない
1003—C / SilverINSERT — いないので追加する

更新と挿入が、同じ1回の処理で起きてほしい。ここが出発点です。

一致すれば更新、無ければ挿入分岐は2本だけ

 
MERGE INTO customers t USING customer_updates s ON t.customer_id = s.customer_id
WHEN MATCHED THEN UPDATE SET *   WHEN NOT MATCHED THEN INSERT *

受け口から反映までを一本にする組み立ての順序

MERGE の直前に「当てる用のテーブル」を1枚挟む。 増分更新で怖いのは、変な行をそのまま本体へ当ててしまうことです。

価格変更は上書きでいいのか派生1 — 商品マスタ

10番の商品に価格の変更が届いたとします。旧価格は 1,000円、新価格は 1,200円。 ここで組み合わせ方が2つに割れます。

要件組み立て方
最新値だけあればいい届いた変更を MERGE で当てて current_price を更新。それで終わり
過去の価格履歴も残したい上書きすると前の値が消える。履歴テーブルを別途設計するなど、単純な上書き MERGE とは違う設計になる

つまり最初に確かめるべきは「最新値だけでいいのか、履歴も要るのか」。ここを決めずに書き始めると、後から作り直しになります。

消えた行をどう扱うか派生2 — ソースから削除

外部システムのほうで顧客が無効化されたとします。すると Target には行があるのに Source にはいない、という状態になります。 更新でも挿入でもない、3つ目の形です。

WHEN NOT MATCHED BY SOURCE THEN UPDATE SET active = false

いきなり物理削除にしない。行そのものを消すのではなく active = false に倒すほうが、 業務上は扱いやすいケースが多いです。消してしまうと、いつ消えたのかが後から分からなくなります。

操作種別が付いて届く場合派生3 — CDC

変更データキャプチャ（CDC）からデータが届くときは、行に操作種別が付いてきます。

operationcustomer_idnameDelta 側での処理
INSERT1003C挿入
UPDATE1001A更新
DELETE1002B削除、または無効化

CDC = 変更イベントを受け取る仕組み。MERGE = その変更を Delta Table へ反映する代表的な方法。 受け取る側と当てる側で役割が分かれています。

なぜデルタと相性がいいのか下で起きていること

上書きではなくログを重ねる、というこの考え方は第9回で扱いました。 この作りのおかげでACID な更新と Time Travel が成り立ち、増分を何度も当て続ける用途と噛み合っています。

重くなったら何を見るか見る順番は決まっている

MERGE の対象が巨大になると、毎回大量のファイルを読むことになって重くなります。上から順に見ます。

順観点
①どのファイルを読んでいるか
②Join 条件は適切か
③データ配置は適切か
④不要な Shuffle がないか

遅いときの具体的な対処と、データ配置の直し方は第15回で扱いました。 ここで押さえたいのは、増分更新は毎日回るものなので、この遅さがそのまま毎日の遅さになるということです。

変更分だけ取り込んで当てる覚え方

増分更新パターン = 「変更分だけ取り込み、MERGE で既存 Delta Table へ反映する」
流れは1セットで覚える —— Auto Loader → Staging → MERGE → Delta。

そして、組み立てるときに最初に決めることが3つあります。 更新と挿入だけでいいのか。消えた行も扱うのか。履歴も残すのか。 ここが決まれば、あとは部品の当てはめです。
