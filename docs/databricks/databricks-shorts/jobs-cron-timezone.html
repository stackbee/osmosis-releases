Jobs の cron とタイムゾーン

Databricks Jobs の Scheduled trigger では、スケジュールは cron 式だけで決まるわけではありません。 同じ式でもタイムゾーンが違えば、実際の起動時刻は変わります。

cron 式とタイムゾーンは別物2つをセットで考える
設定決めていること
cron 式何時・何分に動かすか
timezoneその時刻をどこの地域の時計として解釈するか

スケジュールは、この2つをセットで考えます。片方だけでは、実際にいつ動くかは決まりません。

同じ式でも起動時刻が変わるAsia/Tokyo と UTC で9時間

0 0 2 * * ? は概念的には「毎日 2:00」ですが、それだけではいつ動くかは決まりません。

覚え方針を合わせる / どの時計を見る

 
cron     = 時計の針を何時に合わせるか
timezone = どこの国・地域の時計を見るか

2つそろって初めて決まる

cron ＋ timezone で、初めて「実際にいつ動くか」が決まります。

日本時間で毎日2時に動かす意識しないと9時間ずれる

 
cron       = 0 0 2 * * ?
timezone   = Asia/Tokyo      → 毎日、日本時間の午前2時
タイムゾーンを意識せず UTC のままだと時刻
設定したつもり日本時間 02:00
実際日本時間 11:00

Quartz cron であることにも注意先頭は「秒」

夏時間のある地域春と秋に時計が1時間動く

日本の Asia/Tokyo には現在夏時間がないため、比較的単純です。一方、 America/Los_Angeles や America/New_York のような 夏時間（DST）のある地域を指定すると、春と秋に時計が1時間動きます。

タイムゾーン指定で特に注意するのがこの夏時間です。ローカル時刻を基準にしたスケジュールは、この日だけ振る舞いが変わります。

存在しない時刻の日夏時間開始時

 
01:59  →  03:00      （02:00〜02:59 が存在しない）

時計がこのように進む地域では、02:30 という時刻そのものが存在しない日があります。 したがって「毎日 02:30」に実行するスケジュールは、その日だけ通常通り動かない可能性があります。

二度現れる時刻の日夏時間終了時

 
01:59  →  01:00      （01:00〜01:59 が2回来る）

逆に時計が戻る日は、同じ時刻帯が繰り返されます。 そのためローカル時刻を基準にすると、特定の時刻が二度現れるケースがあります。

ローカルと UTC の使い分け要件で考え方を分ける
要件選ぶもの
日本時間の毎朝6時 / ニューヨーク現地時間の毎朝6時
ビジネス上の「現地の時計」が重要		 現地タイムゾーン
Asia/Tokyo America/New_York など
必ず一定間隔で処理したい / DST の影響を受けたくない UTC

UTC は夏時間で時計が進んだり戻ったりしないため、絶対時間として安定しています。

cron + timezone で決まるまとめと試験対策

覚え方

cron = 何時に動かすか。timezone = どこの時計でその時刻を解釈するか。 現地の「朝6時」を守りたいなら現地タイムゾーン、絶対時間・一定間隔を守りたいなら UTC。

試験対策として押さえるポイント

  • Scheduled trigger では Quartz cron syntax を使う。cron 式とタイムゾーンは別設定
  • 同じ cron 式でもタイムゾーンが違えば実行時刻は変わる。Asia/Tokyo と UTC は9時間差
  • 夏時間のある地域では、時刻が存在しない日・繰り返される日がある
