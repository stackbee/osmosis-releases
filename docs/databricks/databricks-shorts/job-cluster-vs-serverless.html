Job ClusterとServerlessの使い分け

Job Cluster は Job 専用のクラスタを自分で構成して使うもの。Serverless は構成・起動・スケーリングを Databricks に大きく任せるもの。 現在の Databricks では、通常の自動化 Job ではまず Serverless を検討し、 満たせない特殊要件があるときに Job Cluster を使う、という順序が自然です。

まず結論どちらを先に考えるか

Job ClusterとはJob 単位で起きて落ちる

自分で決める項目細かく握れる
分類決める項目
ハードウェアVM / Instance Type、Worker 数、Autoscaling の最小・最大 Worker
実行環境Databricks Runtime、Photon の利用、Spark 設定、ライブラリ
インフラネットワーク関連設定

Compute を細かくコントロールできるのが、Job Cluster の強みです。

ServerlessとはDatabricks が管理

Serverlessの特徴5つ
管理
Compute 管理を Databricks に任せられる。クラスタ運用の負担が小さい
起動
起動が速い。クラスタの立ち上がりを待つ時間が短い
スケール
Autoscaling が自動。台数の下限・上限を自分で決めなくてよい
最適化
Photon などの実行最適化もプラットフォーム側に任せやすい

2つを比べる観点ごと
観点Job ClusterServerless
Compute 構成自分で決めるDatabricks が管理
VM / Instance Type指定する通常は意識しない
Worker 数指定 / Autoscaling 設定自動
Runtime自分で選択Databricks が管理
起動クラスタ起動が必要オンデマンドで高速
カスタマイズ性 / 運用負荷高い / 高め低め / 低い
向いている用途特殊要件標準的な自動化 Job

定期実行のシナリオA・B はどちらも Serverless
状況選択
A日次 ETL を定期実行。毎日 2:00 に Bronze → Silver → Gold。特別な VM や Spark 設定は不要Serverless
B毎時ファイル到着分だけ処理。File arrival → Auto Loader → Silver 変換。短時間の Job を頻繁に起動するServerless

クラスタ管理が不要で、起動が速く、自動でスケールする。日常運用が楽になるので、まずここから検討します。

特殊要件のシナリオC・D は Job Cluster
状況選ぶ理由
CGPU が必要な機械学習処理。特定 Instance Type 必須、特殊ライブラリありVM / GPU / Runtime を明示的に選べる
D特殊な Spark 設定。spark.sql.shuffle.partitions、executor 設定、独自 init script、JVM / ライブラリ要件実行環境を細かく調整できる

Serverless では Compute の細かな設定を Databricks に任せるため、自由度は低くなります。

ネットワークと対話利用E・F
状況選択
E高いネットワーク制御。特定 VPC / VNet 経路、特殊 Firewall 要件、オンプレ接続、特定 Private EndpointJob Cluster を検討（Classic Compute のほうが細かなインフラ要件に対応しやすい場合がある）
FNotebook を人が対話的に触る。データ探索、アドホック分析、試行錯誤対話用 Compute（All-purpose / Serverless Notebook Compute）

All-purpose Cluster は人間が対話的に使うもの、Job Cluster は Job 専用、Serverless Jobs は Job 用 Compute の管理を Databricks に任せるもの。F は Job Cluster と Serverless Job の比較とは別の話です。

判断フロー迷ったらこの順

コストの考え方安さの話ではない

Job Cluster ではクラスタ構成を自分で決めるので、VM サイズ / Worker 数 / 稼働時間 / DBU を自分で意識してコスト設計します。Serverless では割り当てやスケーリングを Databricks 側が管理するため、運用は簡単になります。

よくある誤解

「Serverless = 必ず安い」ではありません。ワークロード、実行時間、データ量、契約条件によって実際の料金は変わります。違いは価格ではなく、自分で最適化する自由度か、管理コストを減らして任せるかです。

Streamingでの注意自由度は同じではない

Serverless は便利ですが、すべての Structured Streaming パターンで Classic Compute と完全に同じ自由度があるわけではありません。

ケース
制約を確認常時 Continuous Streaming／特殊な Trigger／特殊なライブラリ／特殊な Runtime 設定
相性がよいAvailableNow／定期実行／ファイル到着時だけ起動、といった bounded な処理

覚え方レンタカーとタクシー

Job Cluster = 自分で運転するレンタカー。Serverless = 行き先だけ伝えるタクシー。車種や走り方まで決めたいならレンタカー、行き先だけ決めて運転を任せたいならタクシーです。

ケース選択
普通の日次 ETL ／ 短時間の定期 Job ／ Auto Loader + AvailableNowServerless（まず検討）
GPU / 特殊 VM ／ 特殊 Spark 設定 ／ 特殊ネットワーク要件Job Cluster
Notebook の対話利用Job Cluster ではなく対話用 Compute

試験でも実務でも、「Serverless を使えない理由があるか？」を先に考えると整理しやすくなります。
