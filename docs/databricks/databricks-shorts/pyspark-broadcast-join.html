broadcast join

小さい方の DataFrame を各 Worker に配布して、大きい表側の大規模シャッフルを避ける結合最適化。 JOIN の種類ではなく、JOIN の実行方法のヒントです。

大きな表を普通にJOINするとシャッフルの発生

大きな注文テーブル orders が1億行、小さな地域マスタ region_master が 50行だけあるとします。普通に JOIN すると、Spark は同じ結合キーのデータを同じ Worker に 集めるため、ネットワーク越しに大量のデータを移動する場合があります。これが shuffle（シャッフル）です。

小さい表を各Workerに配るbroadcast join

region_master が十分小さいなら、こちらを各 Worker に丸ごと配ってしまえます。 大きい orders を結合キーごとに大きく動かさずに済むので、JOIN が 高速化しやすくなります。

region_master（小さい）
  ↓ 各 Worker にコピー
Worker 1 / 2 / 3 がそれぞれ手元で orders の一部と結合
from pyspark.sql.functions import broadcast
result = orders.join(broadcast(region_master),
                     on="region_id", how="left")

broadcastはJOINの種類ではない結合方法 vs 結合種類

ここは重要です。inner / left / cross といった指定と broadcast() は、決めていることが違います。

決めること
inner / left / cross結果にどの行を残すか
broadcast()どうやって JOIN を実行するか

broadcast() は結合方法のヒント・最適化であり、結合の種類とは別の軸の話です。 試験でも問われやすい要点です。

join の種類そのものは PySpark の join を図解で理解する で扱っています。

自動判定と明示的なbroadcastヒントを与える書き方

Spark / Databricks は、小さいテーブルなら自動的に broadcast join を選択することがあります。 教材では spark.sql.autoBroadcastJoinThreshold の既定値として 10 MB が示されることがあります。

明示的な broadcast() は、その自動判定とは別に、「この表は broadcast してよい」と ヒントを与える書き方です。

broadcastが向いている場面典型例
大きい表小さい表
トランザクション表地域マスタ
売上表商品カテゴリマスタ
イベント表コード変換表

共通しているのは、片方が明らかに小さいという条件です。

broadcastする側の大きさに注意Workerのメモリ圧迫

大きすぎる broadcast は逆効果

broadcast する側が大きすぎると、各 Worker のメモリを圧迫します。 小さいはずの表が実は大きい場合は、かえって不利になります。

覚え方はこうです。broadcast = 小さい表を各 Worker に配り、 大きい表の shuffle を避ける、です。
