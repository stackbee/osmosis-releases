データスキューはなぜ効くのか

データスキューとは、特定のキーにデータが偏り、一部の Partition や Worker だけ処理量が極端に大きくなる状態です。 問題はデータ量そのものではなく、その分布にあります。

偏りは量とは別の問題今回の主張

大量データ処理では、単にデータ量が多いことよりも、データの分布が偏っていることのほうが問題になるケースがあります。

症状
一部の Partition / Worker だけ処理量が極端に大きくなる
原因
特定のキーにデータが集中している
効かない対策
Worker の台数を増やすこと。分散できていない問題は台数では解けない

一つのキーだけ桁が違う具体例

customer_id ごとに売上を集計するとします。件数がこうなっていたとします。

customer_id件数
11,000ここまでは似たような規模
2900
31,100
99950,000,000桁が4つ違う

ほとんどのキーは千件前後なのに、1つのキーだけ5000万件。これがスキューです。

同じ百ギガでも結果が変わるここがいちばんのポイント

どんな処理で起きやすいかShuffle を伴うもの

特定のキーを基準にデータを集める処理で起きやすくなります。代表的なものはこれです。

処理何を基準に集めるか
GROUP BYグループ化のキー
JOIN結合キー
Window 関数の PARTITION BY区切りのキー
repartition() / dropDuplicates() / distinct()指定した列、または行全体
 
df.groupBy("customer_id").sum("amount")

同じ customer_id をまとめる必要があるため、特定の ID にデータが集中していると、 その Partition だけ巨大になります。

未登録顧客に集まる実務で厄介な形

注文テーブルを customer_id で JOIN するとします。通常の顧客は数千件程度。 ところが customer_id = 0 を「未登録顧客」として使っていて、そこに数億件が集中しているとします。

すると JOIN のときに、0番のデータだけ異常に大きな処理単位になります。

設計上の都合で作った、特別な意味を持つ値。ここにスキューが生まれやすい——というのは覚えておく価値があります。 未登録・不明・その他・デフォルト値。どれも1つの値に大量の行が集まる形です。

ワーカーを増やしても空くだけ効かない対策

シャッフルとの関係偏りが姿を現す場所

同じ customer_id のデータを同じ Partition へ集める必要があるので、 各 Worker が持っているデータをキーごとに再配置します。これが Shuffle です。 通常はこれである程度均等に分散します。ところが特定キーだけ巨大だと、Shuffle した後がこうなります。

実行時に救済する仕組みAQE との関係

こうした偏りに対しては、AQE が実行時に対処してくれる場合があります。 巨大な Partition を見つけると、条件次第でそれをさらに分割し、複数の Task で処理できるようにします。 AQE の Skew 対策 = 偏りすぎたデータを実行時に救済する仕組みと考えると分かりやすいです。

AQE そのものの働き（Join 戦略の変更・Shuffle partition の調整・Skew の最適化）は第62回で扱ったので、 ここでは深追いしません。大事なのは、救済してもらう前に、偏っていること自体に気づけるかどうかです。

入出力特定の Task だけ Shuffle Read が非常に大きい / Spill が一部の Task に集中する

全部重いか、一部だけ重いか覚え方

Data Skew = 特定キーにデータが集中して、一部の Partition / Worker だけ極端に重くなること。 さらに短くすると、Skew = データの偏り。

大量データ処理で Job が遅いとき、見るべき分かれ道があります。 全 Worker が重いのか。それとも一部の Worker だけが重いのか。

後者なら、Compute 不足よりも、まず Data Skew を疑ってください。 台数を増やす前に、分布を見る。ここが順番です。
