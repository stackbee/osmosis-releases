BundleをGitで丸ごと管理する

「Git では主にソースコードを管理し、Job や Pipeline は Bundle で管理する」という説明は、実際の運用では少し誤解を招きやすいものです。 Git / GitHub では、ソースコードだけでなく Databricks Bundle プロジェクト全体をバージョン管理します。

「ソースコードだけ」ではない今回の軸

役割を単純化した説明としては「Git = ソースコード、Bundle = Job / Pipeline」で分かりやすいのですが、実際の運用では誤解を招きます。

より正確には

Git / GitHub では、ソースコードだけでなく Databricks Bundle プロジェクト全体をバージョン管理する。

Bundle は Git と競合する別の管理手段ではありません。 むしろ、Databricks の Job、Pipeline、ソースコード、デプロイ設定などを Git で管理しやすい形にまとめる仕組みです。

GitとBundleの役割大きく分けると
Git / GitHub の役割Bundle の役割
バージョン管理 / 変更履歴Databricks リソースを宣言的に定義する
Pull Request / コードレビューソースコードや Notebook をプロジェクトに含める
ブランチ管理Dev / Staging / Prod などのデプロイ先を定義する
CI/CD の起点Databricks へ一貫した形でデプロイする

Git = ソースコード / Bundle = Job / Pipeline という二者択一ではありません。 正しくは「Git → Bundle 全体を管理 → Databricks へデプロイ」です。

3つの層でつながるversion control と deploy

リポジトリに何を置くかBundle プロジェクトの構成例

 
sales-platform/
├── databricks.yml
├── resources/     ├── jobs.yml   └── pipelines.yml
├── src/           ├── ingest.py  ├── transform.py  └── aggregate.py
├── notebooks/     └── analysis.ipynb
├── tests/         └── test_transform.py
└── pyproject.toml

これをリポジトリ丸ごと GitHub へ格納します。 ディレクトリの中身は、紙面の都合で右へ畳んで並べています。

管理できる範囲単なる Python コードだけではない
GitHub で管理されるものBundle での置き場所
ソースコード / Notebooksrc/, notebooks/
Job 定義 / Pipeline 定義resources/jobs.yml, resources/pipelines.yml
Compute 関連設定 / デプロイ設定databricks.yml, 各リソースの *.yml
環境差分targets（dev / staging / prod）
テストtests/

Job設定にも履歴が残るスケジュールも YAML の中

例えば本番 Job のスケジュールを変更するとします。その設定は resources/jobs.yml の中にあります。

resources:
  jobs:
    sales_job:
      name: sales-job
      schedule:
        quartz_cron_expression: "0 0 2 * * ?"

resources の下に jobs があり、その下に Job 名が来ます。 運用上の設定が、リポジトリの中のテキストとして存在することになります。

変更が本番へ届くまで通常のソースコード変更と同じ流れ

UIで手作業する場合との違い再現できるもの・できないもの
GitHubDatabricks UI
置かれているものtransform.py などのコードJob 設定（Schedule / Task / Compute / Retry）
履歴残る残らない
再現コードは再現できるJob 設定は再現できない

Notebook や Python コードだけ Git 管理して、Job を Databricks UI から手作業で設定していると、この状態になります。

cloneすれば再現できるInfrastructure as Code に近い運用

環境ごとに別Bundleにしないtargets がある

Development / Staging / Production の3つを完全に別々の Bundle にすることも考えられますが、 Databricks Bundle には targets があるため、通常は1つの Bundle プロジェクトから複数環境へデプロイできます。

bundle:
  name: sales-platform
targets:
  dev:     { mode: development, workspace: { host: https://dev.example } }
  staging: { workspace: { host: https://staging.example } }
  prod:    { mode: production,  workspace: { host: https://prod.example } }

1つの定義から3環境へTarget ごとに差分だけ変える

再現性・履歴・レビューなぜ丸ごと Git 管理するのか ①〜③
メリット内容
① 再現性環境を壊してしまった場合でも、Git に Bundle 定義が残っていれば再デプロイしやすい
② 変更履歴Job や Pipeline の設定変更もGit の履歴として追跡できる
③ レビュー本番 Job のスケジュールや Compute 設定変更もPull Request でレビューできる

一貫性とCI/CDなぜ丸ごと Git 管理するのか ④⑤

④ 環境間の一貫性 — Dev / Staging / Prod を同じ Bundle 定義から作ることで、手作業による設定差異を減らせます。 ⑤ CI/CD — GitHub への変更を起点として、次のパイプラインを構築できます。

Source of Truthという考え方どちらを「正」とするか
UI で直接いじると

Git の定義 ≠ Databricks の実状態 になります。これを避けるため、 変更はできるだけ Git 上の Bundle 定義へ反映し、CI/CD を通してデプロイする運用が望ましいです。

「中にコードが定義される」の意味ここは少し注意する

YAML ファイルの中に Python コードそのものを大量に埋め込む、という意味ではありません。

src/transform.py という実際のソースファイルがあり、Bundle の Job 定義からそのコードや Notebook を参照します。

Bundle Project = 2つの合わせもの実体
YAML によるリソース定義databricks.yml, resources/*.yml
実際の Python / Notebook / Wheel などsrc/*.py, notebooks/*.ipynb, *.whl

3つのレイヤーで整理最終的にはこれで考える
GitHubDeclarative Automation BundleDatabricks
変更履歴 / レビューDatabricks プロジェクトの定義Bundle のデプロイ先
ブランチ / CI/CDJob / Pipeline / Compute 設定Job を実行 / Pipeline を実行
Source of TruthNotebook 参照 / ソースコードCompute を起動
Target / デプロイ設定実際のデータ処理を行う

関係は GitHub → (version control) → Bundle Project → (deploy) → Databricks です。

最後に一言で整理DEA 試験向けの覚え方

「Git はソースコードだけを管理する」とは覚えないほうがよい。

GitHubSource of Truth
BundleDatabricks プロジェクトを宣言的に表現する仕組み
Databricks Workspaceそのプロジェクトを実際に動かす場所

Bundle の YAML、Notebook、Python コード、Job / Pipeline などのリソース定義を Git でバージョン管理し、Bundle を使って Dev / Staging / Prod へ再現可能にデプロイする。 この3つは競合する仕組みではなく、組み合わせることで Databricks のプロジェクト全体を Git ベースの CI/CD へ載せられます。
