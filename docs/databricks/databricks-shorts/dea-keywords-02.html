DEA キーワード集 2/4 ストリーミングと Lakeflow

「取り込む」「変換する」「いつ動かす」を別レイヤーとして整理すると混乱しにくい。 Batch / Streaming、Auto Loader、Lakeflow Connect、Lakeflow Jobs、Lakeflow Spark Declarative Pipelines の5カテゴリを、紛らわしい組と一緒に並べます。

今回のテーマ5カテゴリの地図

この資料が用語の一覧を担当します。音声では、各カテゴリで押さえるべき判断だけを話しています。

Batch と Streaming違いは処理量ではなく区切り方
キーワード意味・用途
Batch Processingある時点までに溜まったデータをまとめて処理する方式。
Streamingデータ到着に合わせて継続的・増分的に処理する方式。
Structured StreamingSparkのストリーミング処理API。DataFrameベースで記述できる。
Micro-batch小さな時間単位で到着データをまとめて処理する基本方式。既定はこちら。
Continuous Processing低遅延を狙う継続処理方式。利用可能機能には制約がある。
readStream / writeStreamストリームソースを読み取る入口 / ストリーム結果を書き込む入口。
Source / SinkStreamingの入力元 / 出力先。例: Kafka、ファイル、Delta Table / Console。

進捗と状態はどこに残るかCheckpoint と State は別物
キーワード意味・用途
Checkpointどこまで処理したか等の状態を保存し、再起動後に復旧するための情報。
OffsetSource上でのデータ位置。Kafkaのoffsetなど。
Watermark遅れて到着するイベントをどこまで待つかを決める基準。
State集計や重複除去などで複数Micro-batchをまたいで保持する処理状態。
Stateful Processing過去状態を保持しながら行う処理。例: Window集計、重複排除。
Stateless Processing各レコードを独立して処理できる処理。例: filter、単純な列変換。
WAL / Write-Ahead Log処理前に進捗や予定を記録し、障害復旧に使うログという概念。

「一度だけ反映する」に要るもの書き込み側だけでは作れない
キーワード意味・用途
Exactly-once障害復旧を含め、最終的に各入力を一度だけ反映した状態にする性質。
At-least-once各データを最低1回は処理するが、重複処理の可能性がある性質。
Replayable Source障害時に過去データを同じ位置から読み直せるSource。
Idempotent Sink同じデータを再度書いても最終結果が壊れない出力先・書き込み設計。

片方だけの選択肢が必ず混ぜてある

Replayable Source と Idempotent Sink が揃って初めて Exactly-once が成立します。Sink の設計だけを挙げた選択肢は落とせます。

Output Mode と Trigger「何を出すか」と「いつ動かすか」
キーワード軸意味・用途
Output Mode何を出すかStreaming集計結果をSinkへどう出すかの方式。
append何を出すか確定した新規行だけ追加する。
update何を出すか前回から変化した行だけ出力する。
complete何を出すか集計結果全体を毎回出力する。
Triggerいつ動かすかストリーミング処理をどのタイミングで実行するかの設定。
Processing Time Triggerいつ動かすか一定時間ごとにMicro-batchを実行する。
Trigger AvailableNowいつ動かすか到着済みの未処理データを処理し終えたら停止する。

Auto Loader が引き受けること増分取り込みの中心
キーワード意味・用途
Auto Loaderクラウドストレージ上の新着ファイルを増分的に取り込む仕組み。
cloudFilesAuto Loaderで使うSource format。
cloudFiles.format入力ファイル形式を指定する。例: json, csv, parquet。
Incremental File Processing新規ファイルだけを処理し、既処理ファイルを原則再処理しない。
Checkpoint LocationAuto Loader/Streamingの進捗情報を保存する場所。
Exactly-once ingestionCheckpoint等を利用し、同じファイルを重複反映しにくくする設計。

「原則再処理しない」を支えているのは Checkpoint Location。書き方の工夫ではなく、進捗の保存先から来ています。

新着ファイルの見つけ方は二通り列挙するか、通知を受けるか
キーワード意味・用途
File Discovery新着ファイルを見つける処理。
Directory Listingディレクトリを列挙して新着ファイルを探す方式。
File Notificationオブジェクトストレージのイベント通知を利用して新着を検出する方式。
Managed File EventsDatabricks側でファイルイベント検出を管理する仕組み。
File Events新着ファイルをどう見つけるか、という検出レイヤー。

ファイル数が増えるほど列挙する側は不利になります。規模で選ぶ軸だと押さえてください。

キーワード意味・用途

スキーマの推論・進化・退避_rescued_data は信号
キーワード意味・用途

Lakeflow Connect は何をつなぐかファイル側ではなくシステム側

全件か、差分か、変更イベントか差分では DELETE が拾えない
キーワード意味・用途
Full LoadSourceの対象データを最初に全件読み込む。
Incremental Load前回以降に追加・更新された差分だけ取り込む。

INSERT / UPDATE / DELETE新規行追加 / 既存行更新 / 行削除。いずれもCDCで捕捉対象。
Snapshot特定時点のテーブル全体の状態。Full Loadや比較の基準になる。

Source / Destinationデータの取り込み元 / 取り込み先。DatabricksのDelta Tableなど。

PostgreSQL の変更捕捉を支える仕組み名前で問われる4語
キーワード意味・用途
WALPostgreSQLなどでDB変更を記録するWrite-Ahead Log。CDCの元情報になる。

Replication Slot は消さずに残す仕組み

「まだ取りに来ていないぶん」を保持するので、消費が止まったまま放置すると WAL が溜まり続けます。

Python での書き方現行の3つ
記法意味・用途
from pyspark import pipelines as dp現在のPython宣言型パイプラインAPIのImport方式。
@dp.tablePython APIでStreaming Table等を宣言するDecorator。
@dp.materialized_viewMaterialized Viewを宣言するDecorator。

増分で足すのか、作り直すのか

Streaming Table は増分ストリームを処理して維持し、Materialized View は結果を保持して更新する。この一点で書き分けが決まります。

旧 DLT 用語との対応古い教材で引っかかる
旧用語現在意味・用途
Delta Live Tables / DLTLakeflow Spark Declarative Pipelines旧製品名・旧API名。
import dltfrom pyspark import pipelines as dp旧DLT Python API。古い教材・コードで登場する。
STREAMING LIVE TABLEStreaming Table旧DLT用語。現在のStreaming Tableに相当する考え方。
LIVE TABLEMaterialized View旧DLT用語。現在はMaterialized View等へ用語整理された。

STREAM だけは旧用語ではありません。まとめて「古い書き方」と切ると間違えます。

品質ルールは3段階記録するか、捨てるか、止めるか

Expectations の一覧構文と動作の対応
キーワード動作意味・用途
Expectations—データ品質ルールを宣言する仕組み。
Data Quality—欠損・不正値・制約違反等を検出・制御する考え方。
EXPECTWarn品質条件を評価し、違反を記録する。処理は継続する。
EXPECT OR DROPDrop品質条件違反の行を除外し、処理を継続する。
EXPECT OR FAILFail品質条件違反があればパイプライン更新を停止・失敗させる。

Warn / Drop / Fail は動作の名前。構文の名前と混ぜて選択肢に並びます。
